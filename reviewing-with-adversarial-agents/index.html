    Reviewing with adversarial agents¶

    Before you ship a paper, grant, figure, plan, or chunk of code, the toolkit can run it past agents whose job is to find what's wrong, not to tell you it's fine. Here's the pattern and how to run it.

    Why adversarial, and why separate agents¶

    Ask the agent that wrote something to check its own work and it tends to agree with itself: it has committed to an approach and is poorly placed to see that approach's weakness. (You miss typos in your own drafts for the same reason.) A separate agent starts fresh and judges the work on its merits, which is why peer review catches more than self-review.

    So the reviewers are two things at once. Adversarial: told to break the work, assuming it's flawed until shown otherwise. Independent: a fresh context, not the agent that produced it. Run several in parallel and the catch rate rises, since each finds flaws the others miss.

    How to fire it¶

    You want to check… Use What it does
    Any artefact (figure, plan, design, code, draft) adversarial-review Spawns independent flaw-finders; returns a graded findings list (HALT / HIGH / MEDIUM / LOW / NIT), not a thumbs-up
    A paper, full pre-submission referee report /review-paper A 6-agent panel for a named journal — contribution, identification, consistency, maths, tables, claims
    A paper, fast pre-screen first /review-paper-light A ~1-minute 2-agent check (contribution + identification) before you spend time on the full report
    A grant proposal /review-grant A 6-agent funder-panel review
    Changed code /code-review Reviews the diff for correctness and cleanups

    You can also just describe it: "spawn two independent agents to find the weakest points in this, default to skeptical." That's how you check a plan before approving it (see Working with Claude Code).

    The heavyweight option: COARSE¶

    For a referee-grade review of a finished paper, the referee-report workflow runs COARSE under the hood — David van Dijcke's open-source multi-agent peer-review pipeline (coarse.ink). It simulates a real referee across many agents and returns a structured report. It's the most thorough option; the lighter skills above are for faster checks while you work.

    When to reach for it¶

    Run it before anything leaves your hands: a draft to co-authors, a figure going into the paper, a plan before you execute it, code before a merge. It costs a few minutes and saves you from shipping the flaw. Adversarial review is the default here; a balanced "tell me what's good" review is the exception you ask for.
