    One-click replication across languages¶

    A replication package is one-click when a third party can clone it, follow the data-availability statement to obtain raw data, and run one command to reproduce every table, figure, and in-text number in the paper — even when the pipeline spans Stata, R, and Python. If a replicator has to alternate between sessions, edit paths mid-run, or remember an undocumented order, the package fails the AEA bar.

    The AEA Data Editor's policy is direct:

    "The replication package should reproduce the tables and figures, as well as any in-text numbers, by running code without manual intervention. The only exception to this rule is a single change to set a small number of program and data directory paths."

    The "single change to set paths" is the only manual edit the replicator is allowed to make. Everything else has to run by itself.

    The shape¶

    The chain is linear and file-mediated — each step reads what the previous step wrote.

    data/raw/  →  code/01_clean.{R,do,py}  →  data/processed/
data/processed/  →  code/02_analysis.{R,do,py}  →  output/tables/, output/figures/
output/  →  paper/paper.tex  →  paper.pdf

    Each phase can be in a different language. The handoff is the file system: cleaning writes data/processed/main.dta; analysis reads it. Languages communicate through the data files they share, not through in-memory state. (.dta and .csv are the canonical handoff formats; reach for Feather or Parquet only when the data is large and numeric.)

    Three valid patterns¶

    Pick the one that fits the project's complexity.

    1. Single-language pipeline (the simple case)¶

    00_setup → 01_clean → 02_analysis, all in one language. A 99_run_all.{R,do,py} at the top of code/ calls each in order. Most projects start here.

    2. Cross-language, file-mediated (the natural extension)¶

    Each phase is in its own language; downstream phases read upstream's output files. The replicator runs each language's main script in order — listed step by step in the README's Instructions to Replicators section, exactly the format the AEA template prescribes:

    1. Open Stata, run code/01_clean.do          →  writes data/processed/main.dta
2. Open R,     run code/02_analysis.R        →  reads main.dta, writes outputs

    Right pattern when there are 2–3 phases in 2 languages. No top-level orchestrator yet. (When cleaning itself spans languages — e.g. svy weights in Stata then text features from PDFs in Python — name them 01a_clean.do → 01b_clean.py, both writing to data/processed/, and order them in the README.)

    3. Cross-language with a master orchestrator (≥5 steps)¶

    The Social Science Data Editors guidance is explicit:

    "If more than 4–5 manual steps, please wrap a main program/Makefile around them, in logical sequences."

    Default: a shell script (run_all.sh) that calls stata -b do code/01_clean.do, then Rscript code/02_analysis.R, then python code/03_figures.py. Simple, portable across Linux / macOS / WSL, no extra concepts.

    Alternatives when they fit:

    • A Makefile with explicit dependencies (02_analysis.R depends on data/processed/main.dta which depends on 01_clean.do). The AEA Data Editor's own template uses this pattern; best when steps can be re-run incrementally. Caveat: Stata .do files don't expose their outputs to make cleanly, so target dependencies in a Stata-heavy project have to be hand-encoded — if most steps are Stata, the shell-script default ages better.
    • A single-language driver (e.g. 99_run_all.do that shells out via shell Rscript code/02_analysis.R). Works when one language dominates.

    The "single allowed change" — make it mechanical¶

    The AEA's exception ("a single change to set a small number of program and data directory paths") needs an actual mechanism, or replicators will edit 00_setup or _dataroot.do directly — a manual edit of a versioned, distributed file, which defeats the point.

    The convention: a gitignored path-roots file that the replicator copies and edits once.

    • The repo ships code/_dataroot.template.do (and its R / Python siblings) — tracked, with placeholder paths and a one-line edit instruction.
    • The replicator copies it to code/_dataroot.do (gitignored) and edits the single line for their machine. The cleaning / analysis scripts do / source / import _dataroot.do — they never see the template.
    • A code/_dataroot.do already on disk is left alone.

    That isolates the only manual edit to an untracked file with one line. Everything else runs by itself.

    Reproducibility across languages (version pinning + random seeds)¶

    The chain above can be file-perfect and still fail at the replicator's machine if software versions or stochastic steps aren't pinned. Both are AEA requirements.

    • Pin the software environment in 00_setup for every language present:
    • Stata: version 17 (or 18, etc.) before the first command — fixes the dialect.
    • R: renv::snapshot() produces renv.lock; renv::restore() is the replicator's first call. Or document the exact R version + a sessionInfo() snapshot.
    • Python: requirements.txt or environment.yml (conda) pinned to exact versions; pip install -r requirements.txt is the replicator's first call.
    • Set seeds immediately before every stochastic step: Stata set seed 20260622, R set.seed(20260622), Python np.random.seed(20260622). A seed at the top of 00_setup is not enough — a bootstrap or simulator that loads a package which itself seeds the RNG will overwrite it. Seed at the point of use.

    A "one-click" pipeline without these two pins is silently irreproducible across machines.

    Tiering: long-runtime projects¶

    Real econometric projects routinely have 6–48h cleaning steps (UCDP geocoding, MCMC, ML auxiliaries). A single "one command" against the full pipeline is correct in principle but operationally hostile — a replicator wants a fast path that rebuilds tables from data/processed/, and a full path that goes from data/raw/.

    If any step exceeds ~30 minutes, the master script should expose at least two targets:

    • make all — raw → exhibits, the full pipeline.
    • make analysis — data/processed/ → exhibits, the fast path.

    The README must state expected runtime for each. Cached intermediates in data/processed/ are AEA-allowed if produced by code in this project (per data-provenance) and documented in SOURCES.md.

    What this rules out¶

    • "Run cell 7 of the notebook, then go back and re-run cell 3 with the parameter from cell 7's output." Hidden manual loop — not one-click.
    • "Edit a path constant in 02_analysis.do before running." Beyond the single allowed change (the gitignored _dataroot.do set above), every other manual edit is a defect.
    • "We don't actually have a master script; just run things in whatever order someone remembers." If it isn't written down, it doesn't reproduce.
    • A Jupyter notebook used interactively (run a cell, edit a value, re-run) as the analysis "script." A notebook executed top-to-bottom from the command line (jupyter nbconvert --execute …, quarto render) called by the master script is fine — at that point it is a script.

    How to set it up¶

    • Day one: 00_setup, 01_clean, 02_analysis in your project's language(s) via /init-replication or /bootstrap-project.
    • Cross the 4–5-step / multi-language threshold: add a master orchestrator. Start with the shell-script default.
    • Pre-submission: /audit-reproducibility walks the chain backwards from manuscript numbers through 02_analysis → 01_clean → data/raw/ and flags any break.
