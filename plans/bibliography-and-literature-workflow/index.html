    Bibliography & literature workflow¶

    Status: Phases 1-3 shipped + validated on a real project (mining-narratives, 2026-05-26). Last substantive revision: 2026-05-26 (post v1.3.9, three-mode architecture). Audience: Kai, future-Kai, co-authors, PhD students.

    Legend for forward-references throughout this plan: - [shipped] — implemented in kai-team-claude AND validated in production - [exists] — implemented but not yet production-tested - [designed] — specified here, not built yet - [partial] — partly covered; needs extension

    TL;DR — what shipped, what didn't¶

    Phase Deliverable Status (2026-05-26)
    1 Principles + onboarding docs + this plan [shipped]
    2 /bootstrap-project with multi-library YAML, paper.tex skeleton, .gitignore, legacy-bib migration [shipped]
    2.5 install/install-better-bibtex.md with formula + fixture [shipped]
    3 /sync-bib end-to-end (scan + BBT fetch + regenerate + orphans + collisions) [shipped] for bib-canonical mode; [partial] for formula-aligned; [designed] for per-project-export
    4 /sync-pdfs (copy PDFs from local Zotero to literature/<citekey>.pdf) [designed]
    5 /lit-review (LLM-driven candidate search + cross-library check) [designed]
    6 /fix-bib-in-zotero (style-hygiene writeback + WP-published transition) [designed]

    Architectural pivot during Phase 3 implementation (v1.3.0 → v1.3.9): the original "BBT is the canonical citekey source" assumption failed against the modal academic case (multi-project users with different citekey conventions across projects). The shipped architecture uses three modes, recorded per-project in CLAUDE.md zotero.formula_mode:

    • bib-canonical (default for multi-project users): bib is source of truth; /sync-bib runs hygiene checks only, no BBT fetch.
    • formula-aligned: BBT is source of truth; /sync-bib fetches from BBT and regenerates the ZOTERO zone. Safe only when the user's global BBT formula matches the project's.
    • per-project-export: BBT auto-exports to a project-specific file; /sync-bib reads the file. Advanced.

    See §3a below for the full three-mode design.

    1. Goal¶

    Establish a written principle doc plus sync scripts (/sync-bib, /sync-pdfs) that together make Zotero the source of truth for every project's references, while remaining workable for co-authors who use only Overleaf or only LaTeX without Claude Code. Enable LLM-assisted literature review without losing track of provenance (which library, which DOI, when added). A new PhD student should be able to add a first citation correctly within 1 day of onboarding.

    2. Background¶

    Current state in kai-team-claude¶

    • install/mcp-add-zotero.md [exists] — one-off MCP setup; configures Claude's access to one Zotero library at a time (the user's personal user-ID OR a group ID — switching between them requires zotero_switch_library).
    • bootstrap-project [exists] in project-workflow plugin — asks an open-ended Q8 about Zotero (accepts personal or group), records what the user gives in CLAUDE.md. No convention for multi-library declarations.
    • principles/academic-writing.md [exists] §E1-E3 + agents/bibliography-auditor.md [exists] — partial coverage of bib hygiene (auditing existing entries). No principle doc for bib sourcing and sync.
    • docs/per-project-onboarding.md [exists] — currently tells co-authors "For bibliography updates, just push to GitHub", implying hand-edits to the .bib are normal. This contradicts the new design and must be updated when this plan ships.
    • No /sync-bib, /sync-pdfs, or /lit-review commands [designed].
    • No specified file layout for the per-project bib/PDF mirror [designed].

    Gaps identified through discussion¶

    1. Bootstrap's Zotero question accepts only one library; real workflow uses 2-3 (personal + project group + topic libraries).
    2. References live "in Zotero" only for some users — co-authors without MCP can't access metadata, drives ad-hoc hand-editing of .bib in Overleaf.
    3. No PDF mirror — co-authors browsing the repo see citation keys but no PDFs.
    4. LLM-driven literature reviews produce ad-hoc bib files with no clear path from "candidate paper" to "citable entry."
    5. PDFs from paywalled sources are hard to download via LLM (gates, captchas, auth). Need clean fallback to manual Zotero add.
    6. No explicit list of "papers I still need to add to Zotero" — easy to lose track during a lit review.
    7. No cross-library check: a paper already in Kai's personal Zotero but not in the project library gets re-added.
    8. Citation keys typed by hand in Overleaf may not match Better BibTeX-generated keys → silent breakage on next sync.

    3. Design¶

    3.1 Zotero is the eventual source of truth, but three contribution paths coexist¶

    The end state: every citable reference lives in Zotero. The path there is flexible:

    • Path 1 — Full Zotero. Co-author has Zotero + Connector; adds papers via Connector; runs /sync-bib. Their additions land in the ZOTERO zone of references.bib (§3.3a).
    • Path 2 — Manual bib edit. Co-author has no Zotero, knows LaTeX. Hand-adds an entry directly to the MANUAL zone of references.bib. Entry survives /sync-bib; gets promoted to Zotero later via /fix-bib-in-zotero (Phase 6) or by anyone who chooses to.
    • Path 3 — Citation-only. Co-author just writes \cite{key} in .tex, no bib touch at all. Orphan detection (§3.8) catches it and writes a todo block; whoever runs the next /sync-bib decides what to do.

    All three paths converge: every citation eventually has a Zotero entry, but no one is forced into a tool they don't use.

    The one rule everyone follows: when typing a citation in .tex, use the authorYEARkeyword key format. The orphan/reconciliation machinery handles the rest.

    What the system never does: - Silently rename a citekey already present in .tex (always rewrite-tex or rename-Zotero with user approval). - Clobber a MANUAL-zone entry. - Write a fake references.bib entry for an orphan citation (orphan stays unresolved + visible until sourced).

    3.0a The three formula modes (architectural pivot, v1.3.9)¶

    Discovered during v1.3.6-v1.3.8 testing on the mining-narratives project. The original /sync-bib design assumed BBT citekeys are stable canonical IDs across the team. They're not — BBT's citekey-generation formula is global per Zotero install, not per project or per library. An academic working on multiple papers with different citekey conventions (the typical case) cannot satisfy all of them simultaneously by changing the BBT formula.

    The shipped architecture handles this via a per-project formula_mode field in CLAUDE.md's zotero block:

    Mode bib-canonical — recommended default for multi-project users¶

    • Treat the bib (specifically the MANUAL zone, which contains all entries) as source of truth.
    • /sync-bib runs: zone parsing, orphan detection, citekey collision detection, DOI collision detection, summary. Skips BBT fetch + ZOTERO zone regeneration entirely.
    • New citations: hand-add to MANUAL zone (Path 2 in the workflow), OR use /add-cite-from-zotero <item_key> (v1.3.10, not yet built) which pulls a single BBT entry and inserts using the project's recorded formula.
    • This is what runs on the mining-narratives project today.

    Mode formula-aligned — for single-project users¶

    • BBT is source of truth. The user's global BBT formula matches the project's zotero.bbt_formula field.
    • /sync-bib runs the full pipeline: fetch from BBT via JSON-RPC (cited-only, via Phase 1's citekey list passed to item.export), regenerate the ZOTERO zone, detect orphans for keys BBT didn't recognise.
    • Safe only when the user runs ONE project, or all their projects share one citekey convention.
    • Switching to this mode mid-project requires changing the global BBT formula
    • clicking "Refresh BibTeX key" in Zotero per-library. WARNING: affects every other paper that draws from the same Zotero install.

    Mode per-project-export — advanced¶

    • BBT auto-export configured for a project-specific collection with a project-specific formula via BBT's per-translator config.
    • /sync-bib reads the static .bib file produced by BBT instead of querying BBT directly.
    • Bypasses the global-formula constraint entirely.
    • Implementation deferred; documented for future work.

    Mode unspecified¶

    • First-run state when CLAUDE.md doesn't have formula_mode set yet.
    • /sync-bib prompts the user with the three-way choice on first invocation, records the answer back to CLAUDE.md.

    Detection at bootstrap¶

    /bootstrap-project (Phase 2 deliverable) detects this case when the project has an existing bib at bib_output: it samples a few entries, looks them up in BBT to see whether BBT's current keys match the bib's, and surfaces the three-way prompt if they don't. The user's answer is recorded as zotero.formula_mode.

    3.2 Multi-library declaration per project¶

    In each project's CLAUDE.md, a structured YAML block records which libraries this project draws from, plus project-level governance:

    zotero:
  libraries:
    - {type: personal, scope: user-local, label: "bib_keeper personal library"}
    - {type: group, id: "1234567", label: "<project name> (project)"}
    - {type: group, id: "8901234", label: "<topic> (topic)"}
  bib_output: <discovered>   # bootstrap greps .tex for \bibliography{} and uses that path
  pdf_mirror: literature/    # local PDF copies, citekey-named, copies (never symlinks)
  bib_keeper: <github-username or initials>  # who is authorized to run /fix-bib-in-zotero
  bib_keeper_delegate: <optional second person>  # temporary fallback when bib_keeper is offline; edit CLAUDE.md to reassign before going on leave
  draft_state: drafting      # drafting | shared — flips on first external send (referee, JMP, public PDF)

    type: personal is a user-local override. It declares "for ME, also pull from my personal library." Different users have different personal libraries; the field is not load-bearing for co-authors and is honored only on the machine where the user's MCP is authenticated to that library.

    Group id is load-bearing across all co-authors. Same group → same content.

    bib_keeper designates the one person authorized to run /fix-bib-in-zotero against the project's group library (which writes back to Zotero via MCP). Other co-authors can run /sync-bib (read-only against Zotero) freely; they cannot run the write-back command. Single owner avoids "two laptops, conflicting style edits" race conditions.

    draft_state controls the citekey-reconciliation default (§3.5): - drafting — no public PDF has shipped; default action on key mismatch is rewrite .tex (cheap to change). - shared — at least one public PDF exists (referee version, JMP, working-paper distribution); default flips to rename Zotero (keys in public drafts are immutable, per citation-style.md §2). You flip this manually when first sending the paper out.

    Zotero MCP and multi-library access. A single Zotero API key with read scope (the one configured in install/mcp-add-zotero.md [exists]) works for all libraries the user is a member of. zotero_switch_library selects within that authorized set at runtime — no per-library re-authentication needed. Co-authors who haven't been added to a declared group library will get a "library X not accessible" error on /sync-bib; resolution is for the bib_keeper to add them in Zotero's group settings.

    3.3 File layout per project¶

    Path Role Generated by Hand-edited?
    <discovered>/references.bib (typically next to paper.tex) Canonical bib, consumed by .tex's \bibliography{} /sync-bib regenerates ZOTERO zone; MANUAL zone is hand-edited ZOTERO zone: no. MANUAL zone: yes — see §3.3a.
    working/literature_review.bib Working bib during a lit review; ephemeral; gitignored /lit-review and direct LLM work No — graduates to references.bib once in Zotero
    literature/<citekey>.pdf PDF mirror, one file per citekey, copies only /sync-pdfs from Zotero local storage No — fix in Zotero
    project_management/zotero_todo.md Actionable list of papers awaiting Zotero add / promotion /sync-bib + /lit-review Yes for prose / annotations; structured-entry blocks are auto-managed (§3.6)

    bib_output discovery: bootstrap-project greps every .tex in the project for \bibliography{...} / \addbibresource{...}; uses the path it finds. If no .tex exists yet, bootstrap-project creates a minimal paper.tex skeleton with \bibliography{references} (so a path always exists). If multiple .tex reference different bibs, asks the user.

    3.3a Two-zone references.bib¶

    references.bib is divided by anchor tokens into two zones. The tokens are machine-readable strings that look like code, not decoration — chosen specifically to survive editor reformatting and to be unmistakable when a tool strips them:

    % <<<SYNC-BIB:ZOTERO-START>>>
% Auto-generated. Edits here are overwritten on /sync-bib.
% Source libraries: <list of declared lib IDs>
% Last sync: <ISO date>
% Citekey format: authorYEARkeyword (lowercase, no separators). E.g., gehring2025narrative.
% To add a citation: see docs/co-author-onboarding.md

@article{smith2024corruption, ... }
@techreport{jones2023growth, ... }

% <<<SYNC-BIB:ZOTERO-END>>>

% <<<SYNC-BIB:MANUAL-START>>>
% Hand-edited entries; preserved verbatim across /sync-bib runs.
% Listed in project_management/zotero_todo.md ## Pending with action "promote to Zotero".
% /fix-bib-in-zotero (Phase 6) pushes them up + removes them from this zone.

@techreport{schmidt2024handadded, ... }

% <<<SYNC-BIB:MANUAL-END>>>

    Entries live INSIDE the START/END pair. The error message string the script uses is "anchor tokens corrupted" (we standardize on "anchor tokens" throughout — older drafts also used "zone markers"/"sentinel markers"; deprecated).

    /sync-bib parsing rules: 1. Read existing references.bib; split by anchor tokens (regex on <<<SYNC-BIB:(ZOTERO|MANUAL)-(START|END)>>>, whitespace-tolerant). 2. HALT on incomplete markers. If the parser finds a START without its matching END, or a ZOTERO-START followed by a MANUAL-END (interleaved), STOP and report: "Zone markers corrupted. Likely caused by a .bib formatter or editor reformat. Restore from git log -p references.bib (last known good) or run /sync-bib --rebuild-markers after manual inspection." Never silently re-wrap on partial markers. 3. Regenerate the ZOTERO zone from all declared libraries (sorted by citekey for stable diffs). 4. Preserve the MANUAL zone verbatim — never rewrite, never reformat, never reorder. 5. For each entry in MANUAL: append a "consider promoting" block to project_management/zotero_todo.md ## Pending. 6. If a MANUAL entry's DOI / fuzzy-title matches an entry that just appeared in ZOTERO: surface a merge prompt (delete MANUAL? rename citekey? §3.5 reconciliation flow). 7. Non-destructive bootstrap. If references.bib exists but has no anchor tokens (first run, or pre-migration file): treat the whole file as MANUAL and add tokens around it. See §7 for the migration-step ordering that handles @string macros + top-of-file comments correctly.

    3.4 Cross-library check¶

    Before flagging a candidate as "needs manual add," LLM queries ALL declared Zotero libraries:

    For each candidate paper:
  1. DOI match (with arXiv-vs-published reconciliation) → if present in any library, mark for graduation
  2. Title fuzzy match (algorithm + threshold TBD by empirical tuning during Phase 5) → soft match, surface to user
  3. First-author + year + venue → fallback when DOI missing (working papers, gov reports)

    Papers found in any declared library graduate to references.bib on next /sync-bib only if cited in the .tex — otherwise the bib bloats with auto-imported but unused entries.

    3.5 The promotion rule¶

    An entry graduates from literature_review.bib → references.bib ONLY when both: - It exists in Zotero (added directly or via Connector / MCP), AND - It is cited in the project's .tex (\cite*{key} somewhere)

    Three paths to satisfy "exists in Zotero": - Path A — cross-library check found it in personal/topic library - Path B — user added via Zotero Connector after seeing it on zotero_todo.md - Path C — LLM added via MCP zotero_create_item (during lit review, when the paper is open-access and metadata is high-confidence)

    Citekey reconciliation at promotion (the H1 fix): if the Zotero-generated key differs from a citekey already in the .tex (or in literature_review.bib), /sync-bib presents a diff with three options. The default depends on draft_state (§3.2):

    draft_state Default action Rationale
    drafting Rewrite .tex — sed-style replace to match Zotero's key Keys haven't been shared externally; cheap to change; aligns project to Zotero (canonical going forward)
    shared Rename Zotero — change Zotero entry's citekey to match .tex Keys in shared drafts (referee version, JMP, public WP) are immutable per citation-style.md §2; rewriting .tex would break what's in circulation

    Three options always available regardless of default: 1. Rewrite .tex citations to match Zotero (script does sed-style replace; you review the diff). 2. Rename Zotero entry's citekey to match .tex (manual in Zotero UI; or via /fix-bib-in-zotero --rename if you're the bib_keeper). 3. Skip this entry for now (stays on todo list).

    No silent rename either direction. If draft_state: drafting but the citekey already exists in commits pushed to origin, /sync-bib warns ("this key has been pushed; consider flipping draft_state to shared") before applying the default.

    3.6 The Zotero todo list (project_management/zotero_todo.md)¶

    Generated and maintained by /sync-bib. Has two sections:

    • ## Pending — script-managed. Structured entry blocks. Self-cleaning: when a pending paper appears in Zotero, its block is removed on the next sync.
    • ## Decisions — never touched by the script. User and co-author annotations go here ("Skip Karpman 1972 — superseded", "JW: I'll add #5"). Stays put across syncs.

    The structured-entry template (what the script writes and removes):

    ### orphan: jones2024corruption
- Source:     Overleaf .tex citation (or: LLM lit review, or: cross-check miss)
- Cited in:   paper.tex line 142, context: "...as Jones et al. (2024) showed..."
- DOI:        10.xxxx/xxxxxx (if known)
- Venue:      (if known)
- OA result:  (open-access status if checked)
- Action:     Find paper → add to Zotero with citekey `jones2024corruption`
              (or accept Zotero's Better BibTeX key and rewrite .tex via /sync-bib --reconcile)
- Notes:      <co-author free-text; preserved across syncs even when block resolves>

    The script writes and removes blocks matching this template. Two preservation rules: - Any - Notes: line inside a block is preserved when the block resolves: the script moves the note (with its parent citekey as header) to ## Decisions → Resolved orphans rather than discarding it. - Anything outside structured blocks (free prose, headings, the entire ## Decisions section) is preserved verbatim across syncs.

    3.7 Workflows¶

    Workflow A — bib_keeper adds a known paper¶

    Browser → Zotero Connector → grab paper → Zotero saves PDF + metadata
                                ↓
/sync-bib       (refreshes references.bib from all declared libraries)
/sync-pdfs      (copies PDFs to literature/<citekey>.pdf)
                                ↓
Cite as \citep{citekey} in the paper's .tex

    Typical: 1-2 min per paper end-to-end (browser action + sync). The 30s figure from v1 was optimistic for paywalled papers.

    Workflow B — LLM-driven literature review¶

    User: "Find recent papers on X for the lit review section"
                ↓
LLM runs /lit-review [designed]:
  1. Query OpenAlex / Semantic Scholar for candidates (~20-50)
  2. CrossRef HEAD-check every DOI (drops hallucinations before they enter the file)
  3. For each verified candidate:
       a. Cross-check declared Zotero libraries (DOI → title → author-year)
       b. If in Zotero    → mark for promotion (cited in .tex check happens at /sync-bib time)
       c. Else, attempt OA: arXiv / SSRN / OSF / institutional repos
       d. If OA succeeds → either add to Zotero via MCP + download PDF, OR add to literature/<citekey>.pdf with todo entry
       e. Else            → append to project_management/zotero_todo.md
  4. Output:
       - working/literature_review.bib (all verified candidates)
       - project_management/zotero_todo.md (the manual-add list)
       - Structured summary file (not a one-line summary)
                ↓
User reviews zotero_todo.md, adds the relevant ones via Zotero Connector
                ↓
/sync-bib (graduates new arrivals; flags any citekey mismatches per §3.5)

    Time: variable. A 50-paper review typically needs 10-30 min of user curation in Zotero after the LLM phase.

    Workflow C — New co-author / PhD student onboarding (full setup)¶

    Day 1 checklist for someone who wants to use Zotero + /sync-bib: 1. git clone kai-team-claude 2. bash install/install.sh (or install.ps1 on Windows) 3. /plugin install project-workflow@kai-team-claude 4. Read ~/.claude/principles/bibliography-and-literature.md [designed — Phase 1] 5. Run /bootstrap-project in the new project folder 6. Install Zotero desktop + Zotero Connector browser extension 7. Install Better BibTeX (per install/install-better-bibtex.md [designed — Phase 2.5]) 8. Authenticate Zotero MCP per install/mcp-add-zotero.md [exists]

    Daily work: - Add papers via Zotero Connector to declared libraries - /sync-bib + /sync-pdfs as needed - Cite via \citep{citekey} in the .tex - The ZOTERO zone of references.bib regenerates from your additions; the MANUAL zone is for co-authors who chose Workflow E

    Co-authors who prefer NOT to set up Zotero use Workflow D (citation-only) or Workflow E (hand-edit MANUAL zone) — they skip steps 6-8 entirely. Read docs/co-author-onboarding.md [designed — Phase 1].

    Realistic onboarding: 1 day for full setup; ~15 min for D/E-only paths.

    Workflow D — Overleaf-only co-author adds a citation (citation-only path)¶

    The most common path for senior co-authors. Requires no Zotero, no Claude Code, no bib edit:

    In Overleaf, write \citep{authorYEARkeyword} for new citations. The orphan detection will surface your citation; whoever next runs /sync-bib will source the paper into Zotero.

    Mechanically: 1. Co-author writes \citep{jones2024corruption} in Overleaf. 2. Overleaf's GitHub bridge pushes the .tex change to git. 3. Someone pulls and runs /sync-bib. 4. /sync-bib orphan detection: jones2024corruption is in .tex but not in any declared Zotero library, ZOTERO zone, or MANUAL zone. Warns + appends a todo block to project_management/zotero_todo.md ## Pending. Compile shows [??] — visible, not silently wrong. 5. Someone with Zotero access searches the paper, adds via Connector. 6. Next /sync-bib: graduates the entry. If Better BibTeX assigns a different key, §3.5 reconciliation fires (default: rewrite .tex to match Zotero). 7. /sync-pdfs copies the PDF; co-author who later pulls sees literature/jones2024corruption.pdf available.

    Workflow E — Co-author adds a bib entry manually (manual-bib path)¶

    For LaTeX-fluent co-authors who don't want Zotero but are happy to write a @article{...} block by hand:

    1. Co-author opens references.bib, scrolls to the MANUAL ADDITIONS zone, adds the entry.
    2. Compiles fine immediately (no orphan, no [??]).
    3. Next /sync-bib run: preserves the MANUAL entry verbatim; appends a "consider promoting to Zotero" block to ## Pending.
    4. When someone runs /fix-bib-in-zotero (Phase 6), the MANUAL entry gets pushed to Zotero and migrates to the ZOTERO zone on the following /sync-bib.

    The MANUAL zone is durable. Co-author's contribution survives indefinitely until someone actively promotes it.

    Workflow F — Co-author without Claude Code AND without Zotero¶

    Their default is Workflow D (just type \cite{key}) or Workflow E (hand-edit the bib's MANUAL zone). They never touch the ZOTERO zone. The docs/co-author-onboarding.md one-pager [designed — Phase 1] tells them which two paths are open and how to use each.

    3.7a DOI-collision check (silent-duplicate guard)¶

    Two co-authors on parallel branches independently add the same paper to the MANUAL zone with different citekeys (smith2024corruption vs smith2024growth, both referencing Smith & Lee 2024). After merge, the bib has two entries for the same paper. Neither is an orphan, neither triggers a citekey collision, but the rendered bibliography lists the paper twice.

    /sync-bib runs a DOI-collision pass: for every pair of entries (ZOTERO or MANUAL) with matching DOI but different citekeys, surface a "merge required" prompt with both entries side-by-side. User picks which citekey to keep; the other entry is dropped and any \cite{} references to the dropped key are rewritten in .tex (per §3.5 reconciliation default).

    For entries without DOI (rare), the fallback is title fuzzy match + first-author + year. Same prompt fires on match.

    3.8 Orphan citekey detection — the mechanism¶

    Run as part of /sync-bib. Logic:

    1. Collect every citekey from \cite*{...} in every .tex file under the project root.
   Regex: \\cite[a-z]*\*?\{([^}]+)\} — matches \cite, \citep, \citet, \citealp,
   \citealt, \citeauthor, \citeyear, \citeyearpar, \citetext, \nocite, plus
   starred variants (\citep*, \citet*) and multi-key forms \citep{a,b,c}.
2. Collect every citekey from references.bib (both ZOTERO and MANUAL zones)
   and from Zotero MCP across declared libraries.
3. orphans = .tex keys − (bib keys ∪ Zotero keys)
4. For each orphan:
     - Look up in literature_review.bib (LLM may have a candidate entry with that key)
     - If found: include the candidate metadata in the todo block
     - If not found: write a minimal block with key + .tex context
5. Existing orphan blocks in zotero_todo.md whose keys now resolve are removed
   (preserve any `- Notes:` line — see §3.6)
6. New orphans are appended to ## Pending
7. Anything under ## Decisions is left untouched
8. /sync-bib WARNS but does NOT halt — compile continues, [??] visible in PDF, todo updated

    Paste-bomb cap. If a single /sync-bib run would append more than 10 new orphan blocks, the script pauses and asks: "(a) add all N, (b) add the first 10 and surface the rest for review, (c) abort — let me look at the .tex diff." This catches the case where a co-author pastes a related-work paragraph from another paper with 30+ citations attached.

    This is what catches every citation a co-author types (Overleaf, hand-typed, LLM-suggested) and turns it into a tracked todo item, without requiring the co-author to know anything beyond the citation key.

    Intentional placeholders. Two ways to silence them: - Convention: use the prefix \cite{TODO_...} or \cite{ph_...} for any placeholder. /sync-bib skips orphan blocks for citekeys matching these prefixes. - Per-key opt-out: move the auto-generated todo block to ## Decisions and add a - Notes: line — future syncs leave it alone.

    Phase 3 (later session): Build /sync-bib¶

    • New slash command in project-workflow plugin.
    • Reads zotero: block from CLAUDE.md.
    • Queries declared libraries via Zotero MCP (loops over libraries using zotero_switch_library).
    • Parses existing references.bib into ZOTERO zone + MANUAL zone (§3.3a). HALTs on incomplete markers.
    • Regenerates ZOTERO zone only; preserves MANUAL zone verbatim.
    • Runs orphan-key detection (§3.8) — warns + auto-appends to todo, does not halt. Paste-bomb cap fires if >10 new orphans in one run.
    • Citekey reconciliation flow (§3.5) on mismatches; default depends on draft_state.
    • For each MANUAL entry: append a "promote-to-Zotero" block to ## Pending.
    • Atomic write (tmp file + rename), lock file with stale-lock detection.
    • Stable canonical formatting in the ZOTERO zone (sort by citekey, normalized whitespace) so re-runs are no-op when nothing changed — preserves git blame for ZOTERO zone. (MANUAL zone preserves user formatting, so re-runs after MANUAL edits do change the file — this is intended, not a violation of idempotence.)
    • Library priority: declared order in the YAML block (first listed wins on conflict), not by dateModified.
    • Refuses to write an empty bib over a non-empty one without --force.

    Phase 6 (later session): Build /fix-bib-in-zotero¶

    The bidirectional sync + style hygiene command. Single command name throughout (NOT /bib-hygiene — earlier drafts used both names interchangeably; consolidated here). - Detection: wraps the existing bibliography-auditor agent [exists] for reporting; adds the write-back leg. - Three uses, one command: - Promote MANUAL-zone entries to Zotero (one entry at a time, with diff approval). - Fix style violations in ZOTERO-zone entries per citation-style.md (capitalization, missing DOI via CrossRef HEAD-lookup, author name formatting, page-range normalization). - Detect WP→published transitions: for any @techreport whose CrossRef title+author match a non-WP DOI, surface a "promote to @article" diff (entry-type change + field shuffle). - Authorization: only the project's bib_keeper (declared in CLAUDE.md, §3.2) can run this command against a shared group library. Other users get "you are not bib_keeper for this project; ask ." Avoids the multi-laptop-conflicting-style-edits race condition. - Transactional writes: build full diff → user approves the batch → MCP dry-run validates every update payload (resolves item IDs, checks field schemas) → only if all dry-runs succeed do the actual writes fire. Any failure mid-batch → abort, present a list of what was written vs. what remains. - Logs every Zotero write to working/zotero_writes.log (timestamped, before/after diff). Audit trail across runs. - Dry-run-by-default (/fix-bib-in-zotero --apply to actually write). - After successful writes, next /sync-bib regenerates the ZOTERO zone from the (now-clean) Zotero state. Local and remote aligned.

    5. Open questions / decisions¶

    1. Citation key convention. CLAUDE.md says authorYEARkeyword. Decision (REVISED 2026-05-26): the citekey-format question is real but cannot be solved by mandating "everyone uses formula X" — BBT formula is global per Zotero install, so multi-project users would have to flip the global formula every time they switch projects, which breaks every other project that pulls from the same Zotero. Resolved via the three-mode architecture in §3.0a: each project records formula_mode in CLAUDE.md and behaves accordingly. The original "configure BBT to produce authorYEARkeyword" guidance still applies for single-project users (Mode A); multi-project users default to Mode B (bib-canonical) and the bib's existing convention wins regardless of BBT's formula.

    2. Where does references.bib live? Decision: next to the .tex (paper.tex → references.bib in the same folder). bootstrap-project discovers via grep; if no .tex exists, bootstrap-project creates a paper.tex skeleton first (paper.tex always exists post-bootstrap). NOT github-sync/ — that was a v1 mistake.

    3. PDFs in git? Decision: .gitignore literature/ by default; PDFs reconstructed via /sync-pdfs from local Zotero. Dropbox sharing is fine (per project setup); shared with co-authors on the project is acceptable.

    4. literature_review.bib lifecycle. Decision: lives in working/ (gitignored, Dropbox-only); archive to working/_old/literature_review_<date>.bib if the user wants. Cheap insurance.

    5. Conflict: paper exists in multiple declared libraries. Decision: declared library order in the YAML wins (not dateModified). Predictable. If user wants to change winner, reorder libraries in the YAML.

    6. What if a co-author doesn't have access to a declared library? Decision: /sync-bib fails loudly with "library X not accessible — confirm with project owner you've been added." Does not silently produce a partial bib.

    7. Bidirectional sync — DECIDED, option (c). Local-bib fixes (capitalization, missing DOI) flow back to Zotero via /fix-bib-in-zotero (Phase 6): LLM edits local bib per citation-style.md, presents diff, user approves, MCP zotero_update_item writes back. Dry-run by default. Same command also promotes MANUAL-zone entries to Zotero. One command, two uses. (Options (a) strict one-way and (b) silent bidirectional are rejected — (a) makes Zotero UI editing too painful, (b) is too risky without user-in-the-loop diffs.)

    8. Citation-style spec doc — RESOLVED. principles/citation-style.md written (2026-05-21). Captures all 9 decisions: Chicago title case with {} protection; Last, First Middle author format with all authors listed; maxcitenames=2 in preamble; DOI required when available; full journal names; full page ranges; entry type matches publication state (@article for published, @techreport for working papers including NBER/CEPR/IZA/SSRN/arXiv); year-disambiguation by different keyword first, letter suffix as fallback; post-publication-history and secondary identifiers in note. Empirical bst rendering test in docs/plans/bibstyle-test/ confirmed @article-everywhere produces misleading output under biblatex authoryear (Kai's default); switched to @techreport for WPs. See the file for the rules in detail.

    7. Migration path for existing projects¶

    For projects with an existing references.bib not generated by /sync-bib:

    1. Run /bootstrap-project (or hand-edit CLAUDE.md) to add the zotero: block (including bib_keeper and draft_state).
    2. Discover bib_output: grep existing .tex for \bibliography{...}. Preserve that path.
    3. Backup existing references.bib to working/_old/references_pre-sync.bib.
    4. Idempotent zone migration. Check for existing anchor tokens — if already present, skip this step entirely (don't double-wrap). Otherwise:
    5. Identify and hoist top-of-file material above the ZOTERO marker: @string{...} macros, @preamble{...} blocks, top comments (anything before the first @type{citekey,...} entry).
    6. Place the ZOTERO-START / ZOTERO-END anchors as an empty pair (no entries yet).
    7. Wrap the rest of the file (the actual entries) between MANUAL-START / MANUAL-END anchors. Every existing entry survives as a MANUAL entry by default.
    8. Pre-promotion dedup. For each MANUAL entry: check if Zotero already has a matching DOI (exact match). If yes, tentatively mark for "ZOTERO-origin" routing rather than leaving in MANUAL — avoids the "every entry duplicated after first sync" scenario when the legacy bib was originally exported from Zotero.
    9. Build a citekey-rename map: for each remaining MANUAL entry, find the matching Zotero entry (title + first-author + year fuzzy). Surface mismatches between existing key and Zotero's key.
    10. User decides per entry: rename in Zotero (entry moves to ZOTERO zone next sync), rewrite in .tex (default depends on draft_state per §3.5), or leave in MANUAL (entry stays in MANUAL zone; promote later via /fix-bib-in-zotero).
    11. Run /sync-bib first time. Diff the generated bib against the backup — surface any drift.
    12. Going forward: discipline as in §3. Entries in MANUAL zone gradually drain to ZOTERO via /fix-bib-in-zotero (Phase 6).

    8. Success criteria¶

    The workflow is successful if: - A new PhD student can read bibliography-and-literature.md + co-author-onboarding.md, follow the day-1 checklist, and add their first citation correctly within 1 day. - A senior co-author working only in Overleaf can add a citation by writing \citep{authorYEARkeyword} with no other steps required. - A literature review of 50 candidate papers takes ~30 min of user curation in Zotero after a 5-min LLM phase. (Pending Phase 5.) - /sync-bib is idempotent on the ZOTERO zone: re-running immediately after a successful sync (no .tex changes, no Zotero changes, no MANUAL edits) produces only a header-timestamp diff. ZOTERO entry content + sort order is byte-stable. (The MANUAL zone changes whenever a user edits it — that's intended.) VERIFIED for bib-canonical mode on mining-narratives. - Cross-library check catches ≥80% of papers Kai already has but the LLM treats as "new" (measurement: manual audit on the next two lit-review runs after Phase 5 ships). - The principle docs + commands run on Windows + Mac + Linux with platform-specific gotchas documented (not absent).

    9. Implementation arc (v1.3.x) — what shipped and what we learned¶

    Five distinct architectural attempts on /sync-bib Phase 2 before convergence:

    Version Approach Outcome
    1.3.0 Zotero MCP per-item fetch HALT — MCP returns ad-hoc citekey scheme ({LastName}{Year}_{ItemKey}), not BBT format
    1.3.4 BBT JSON-RPC connectivity probe OK — endpoint reachable; method shapes unknown
    1.3.5 BBT extended probe + per-library probe mode Discovered: user.groups returns BBT-internal IDs, no Zotero web ID; name-based mapping required
    1.3.6 BBT enumerate-all + client-side library route HALT — item.search("") times out on 5000+ items
    1.3.7 BBT cited-only fetch (input = Phase 1 cited keys) Architecturally clean; per-key item.export works in 0.5s
    1.3.8 Cited-only + --diagnose-keys/--build-rekey-map Surfaced: 0/70 keys found because the project's bib uses a different BBT formula than the current install
    1.3.9 Three-mode architecture Shipped. bib-canonical validated on mining-narratives.

    The load-bearing insight from this arc: BBT's citekey-generation formula is a global setting per Zotero install, not a per-project or per-library setting. The original design assumed citekeys were stable canonical IDs across the team, which fails as soon as one user works on multiple projects with different conventions. The three-mode architecture sidesteps this by letting each project declare how it wants to relate to BBT.

    Other lessons captured for future maintenance: - BBT JSON-RPC at http://localhost:23119/better-bibtex/json-rpc (no trailing slash). Confirmed via path-variant probe. - item.search is phrase-match on title text, not token-match. Stopword-stripped queries return 0; literal first-6-words-of-title works. - item.search("library:N") is NOT a library filter — it's a plain-text search for the literal string. Use the CSL id URL (http://zotero.org/groups/<zotero-web-id>/items/...) to route items client-side instead. - item.export([citekeys], "biblatex") errors out (code -32602) when any requested key is missing. Implementation falls back to one-at-a-time after a chunk failure. - The mining-narratives bib used the formula auth.replace(" ", "_").lower + "_" + shorttitle(1, 0).lower + "_" + year. Reverse-engineered via iterative BBT preview testing.
