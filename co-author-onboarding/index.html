    First week: the essentials¶

    New to git/GitHub entirely? Read the 10-minute primer first — it defines every term this page uses (commit, push, branch, markdown, repo).

    Audience: anyone joining a kai-team-claude project as a co-author or PhD student. Read this once. ~15 minutes. Last substantive revision: 2026-05-21.

    Why this page. Citations are the single highest-friction shared resource on a paper — two people adding the same reference under different keys is how bibliographies break for everyone. Getting the citekey rule and the bib flow right in week one prevents that, which is why this page leads with them.

    This doc covers what you need to know in the first week. No Claude Code, no Zotero, no Python required — all of those are optional. The only pieces everything else depends on are GitHub, Dropbox, Overleaf (where applicable), and a shared citekey format — get these consistent and the rest is flexible.

    Manual or with Claude — your choice, per task. Every git step on this page can be done by hand (see the manual workflow) or by asking Claude Code in plain language. Pick whichever you prefer for each task; the rules are the same either way.

    What you need to know on day one¶

    The repo lives in Dropbox (and usually GitHub)¶

    Each paper has two homes: - Dropbox folder — always present. Holds data, large files (PDFs, figures), working notes, and the project's CLAUDE.md. Every project co-author needs to be on Dropbox — project_management/zotero_todo.md and the PDF mirror flow through it. Ask whoever manages the project for access. - GitHub repo — present for most projects. What is canonical (paper text in git vs in Overleaf) depends on the project's mode (declared in the project's CLAUDE.md under ## Project mode). The four modes are defined in principles/project-structure-canonical.md — read that first to understand what you can commit/push from your sessions.

    Quick mode summary: - Overleaf-mastered (e.g., Virality): Overleaf is canonical. Paper drafts live as date-stamped PDFs in the Dropbox folder under paper/. The Overleaf admin applies final changes manually in Overleaf. - Git-mastered (e.g., Sor4d): GitHub is canonical. paper/paper.tex and paper/references.bib are the editable source. Drafting happens there directly.

    See principles/project-structure-canonical.md for the full layout (every project, every mode).

    How citations work¶

    The paper's references.bib is split into two zones by anchor tokens. Entries live inside the START/END pair:

    % <<<SYNC-BIB:ZOTERO-START>>>
% Auto-generated from Zotero. Do not edit here — overwritten on /sync-bib.

@article{smith2024corruption, ... }
@techreport{jones2024growth, ... }

% <<<SYNC-BIB:ZOTERO-END>>>

% <<<SYNC-BIB:MANUAL-START>>>
% Hand-edited entries. Preserved across /sync-bib runs.

@unpublished{schmidt2024draft, ... }

% <<<SYNC-BIB:MANUAL-END>>>

    You have three ways to add a citation. Pick whichever fits how you work.

    Default to Path 1. Use Path 2 only when you have full metadata in front of you and want the citation to resolve immediately (e.g., before a deadline). Use Path 3 only if you're already a Zotero user or want to invest the setup time.

    Path 1 — You just type the citation in .tex (citation-only)¶

    Easiest. No setup needed.

    1. In your .tex file, write \citep{authorYEARkeyword} — e.g., \citep{jones2024corruption}.
    2. Don't touch references.bib.
    3. Record and share the change:
    4. Overleaf-mastered project: nothing more to do — Overleaf saves it.
    5. Git-mastered project, no terminal: open GitHub Desktop (free, https://desktop.github.com), which lists your changed .tex; type a one-line summary, click Commit, then Push origin. (Commit = record a snapshot; push = upload it so co-authors see it.)
    6. Terminal users: git add / git commit / git push per the handbook §2.3.

    Whoever next runs /sync-bib will see your new citation surface as a "pending orphan" in project_management/zotero_todo.md. They'll source the paper into Zotero. Your \citep{...} will resolve in the next compile.

    In the meantime, your compiled PDF will show [??] for the unresolved citation. That's expected — it'll resolve when the bib gets updated. Don't try to "fix" it yourself unless you're under a deadline (then use Path 2 below).

    Before inventing a new citekey, search (Ctrl-F) references.bib AND project_management/zotero_todo.md for the first-author surname. Avoids the case where the paper is already pending under a slightly different key.

    Disambiguation when Overleaf autocomplete suggests an existing key: pick a more specific keyword (gehring2025narrative already taken → use gehring2025refugees, gehring2025wartime, whatever the new paper is about). If you genuinely can't distinguish: letter suffix (smith2024a, smith2024b) is the fallback.

    In long-form workflow doc, this is Workflow D.

    Path 2 — You write a bib entry by hand (manual bib edit)¶

    For LaTeX-fluent people who'd rather add an entry directly:

    1. Open references.bib. Scroll to the MANUAL zone — do not edit the ZOTERO zone, those entries are auto-generated and your edits will be erased.
    2. Inside the MANUAL zone (between % <<<SYNC-BIB:MANUAL-START>>> and % <<<SYNC-BIB:MANUAL-END>>>), add your entry. Use the format described in principles/citation-style.md:
    3. @article for papers published in a journal
    4. @techreport for working papers (NBER, CEPR, IZA, SSRN, arXiv)
    5. @unpublished for circulated drafts / mimeo / unpublished manuscripts
    6. Before adding, search (Ctrl-F) the MANUAL zone for the first-author surname to avoid silent duplicates (the case where another co-author already added the same paper under a different citekey on a parallel branch).
    7. Get the core fields right (author, title, year, journal/institution + DOI if known). Style polish (Chicago title case, full author names, exact page-range format) gets normalized later by /fix-bib-in-zotero. Follow citation-style.md from the start if you can — it saves the bib_keeper time later.
    8. Commit and push.

    Your entry survives indefinitely. Someone will eventually promote it to Zotero via /fix-bib-in-zotero. Until then, your bib entry is the source of truth.

    In long-form workflow doc, this is Workflow E.

    Path 3 — You use Zotero¶

    If you already have Zotero installed and use the browser Connector:

    1. In your browser, click the Zotero Connector button on the paper's page. Zotero saves the metadata + PDF.
    2. Ask whoever manages the Zotero library which group the project uses — they'll add you.
    3. After adding a few papers, run /sync-bib (if you have Claude Code) or wait for someone else to run it. New entries appear in the ZOTERO zone of references.bib.

    If you want to run /sync-bib yourself, you'll need: - Zotero desktop running - Zotero Connector browser extension - Better BibTeX installed and configured (see install/install-better-bibtex.md) - Zotero MCP authenticated (see install/mcp-add-zotero.md)

    This is optional. Path 1 or Path 2 work fine without any of this.

    In long-form workflow doc, this is Workflow A.

    Choosing a citekey strategy (Path 3 users only)¶

    Important constraint: Better BibTeX's citekey-generation formula is global per Zotero install — not per project, not per library. If you work on multiple papers with different citekey conventions (very common for active academics), you cannot satisfy all of them at once by changing the BBT formula.

    The project's CLAUDE.md records a formula_mode to handle this:

    Mode What it means Who picks this
    bib-canonical (recommended default) Treat the bib as source of truth. /sync-bib runs hygiene checks (orphans, collisions) but does NOT fetch new entries from BBT. To add a citation: hand-edit MANUAL zone of references.bib, or use a future /add-cite-from-zotero helper. Multi-project academics — the typical case
    formula-aligned Change your global BBT formula to match the project's. /sync-bib then fetches new entries from BBT and regenerates the ZOTERO zone. WARNING: affects every other project you cite from this Zotero install. Single-project users, or users whose projects all share one convention
    per-project-export Advanced. Configure BBT to auto-export a project-specific .bib with the project's formula. /sync-bib reads that file instead of querying BBT. Power users who set up per-project BBT auto-export

    Check the project's CLAUDE.md zotero.formula_mode to see which mode is recorded. If you're not the bib_keeper, you don't need to change anything — just follow Path 1 (citation-only) or Path 2 (manual bib edit) and the bib_keeper handles the rest.

    Switching modes mid-project: edit formula_mode in CLAUDE.md, commit, ask co-authors to do the same. Don't toggle frequently — pick a stable mode once and stick.

    The one convention worth keeping consistent¶

    Citekey format: authorYEARkeyword — lowercase, no separators.

    • gehring2025narrative ✓
    • acemoglu2001colonial ✓
    • vanderberg2022growth ✓ (particles like "van der" join the surname; no spaces)
    • smith2024a / smith2024b ✓ (letter-suffix disambiguation as fallback)
    • Gehring_2025_Narrative ✗ (no underscores, no capitals)
    • Gehring2025 ✗ (missing keyword)

    If you make up a citekey when adding a citation in Path 1, follow this format. The person who sources the paper into Zotero will use the same format, so your \citep{jones2024corruption} will resolve cleanly.

    Year unknown at first citation? Use \cite{TODO_smith_corruption} — the TODO_ prefix tells /sync-bib to skip orphan detection for this key. Resolve later.

    Special cases (single-name authors like Aristotle, institutional authors like World Bank, Asian names, Spanish double surnames, joint first authors): see citation-style.md §2.

    Once a citekey appears in a shared PDF (referee version, JMP, working-paper distribution), it doesn't change. The bib_keeper sets draft_state: shared in CLAUDE.md when first sending the paper out — this mechanically protects all keys from being rewritten by /sync-bib.

    Habits that quietly break the bib for everyone¶

    • Don't edit the ZOTERO zone of references.bib. It's regenerated on every /sync-bib. Edits are lost.
    • Don't delete the anchor tokens (% <<<SYNC-BIB:...-START>>> / -END>>>). They tell the script which zone is which. If they vanish, the script HALTs and points you at git history.
    • Don't open references.bib in any tool that auto-formats .bib files — JabRef, BibDesk, TeXstudio's .bib mode, VSCode with bibtex-tidy or LaTeX Workshop format-on-save enabled, vim/emacs with auto-format bibtex-mode hooks. They reorder or reformat entries and scramble the zones. Use a plain-text editor or Overleaf's editor.
    • Don't rename citekeys that have appeared in shared drafts. Once a paper has been circulated, its keys are frozen.
    • Don't hand-edit Zotero entries to fix typos in the rendered bib (Path 3 users). Run /fix-bib-in-zotero if you're the bib_keeper, or ask the bib_keeper to run it.

    Merge conflicts on references.bib¶

    If git flags a conflict in references.bib, look at the markers:

    • Conflict in the ZOTERO zone — accept either side; the bib_keeper will re-run /sync-bib to regenerate. The ZOTERO zone is regenerated from Zotero, so the file content will resolve. If you don't have Claude Code, accept either side and commit.
    • Conflict in the MANUAL zone — both sets of new entries are real work; keep both. Don't blindly pick one side. Merge the entries manually: include all the @article{...} / @techreport{...} / @unpublished{...} blocks from both sides. If the conflict is intricate, /sync-bib --resolve-conflicts parses the markers and offers to merge both sides automatically.

    What to do when something goes wrong¶

    Symptom Likely cause What to do
    [??] in compiled PDF for a citation Orphan citekey — your .tex cites a key not yet in the bib Wait for next /sync-bib, or add the entry yourself via Path 2 (immediate resolution)
    Compile fails entirely (won't produce a PDF) BibTeX strict mode rejects undefined citations Path 2: add a real entry to MANUAL right now. Don't wait for the next sync.
    /sync-bib HALTs: "anchor tokens corrupted" A .bib formatter ate the markers git log -p references.bib → find last good version; revert or restore the markers manually. Then /sync-bib again.
    /sync-bib fails: "library X not accessible" You haven't been added to a declared Zotero group Ask whoever manages the Zotero group to add you in its group settings
    /sync-bib fails: "your BBT formula doesn't match the project's" Your Better BibTeX is generating different citekeys than the canonical ones Re-check install/install-better-bibtex.md formula; reinstall BBT with the pinned config
    Your .tex rename of a citekey doesn't take effect draft_state: shared flipped — keys are now frozen If paper has been shared, citekeys can't be rewritten silently — see "What NOT to do"
    Same paper appears twice in the rendered bib Two co-authors added it to MANUAL with different citekeys /sync-bib's DOI-collision check should catch this; if it didn't, surface to bib_keeper

    Per-project quirks¶

    Read each project's CLAUDE.md once when you join. It's just a markdown file in the repo root — open it like any other doc. The zotero: block tells you: - Which Zotero libraries the project uses - Who the bib_keeper is — the one person authorized to run /fix-bib-in-zotero (the command that writes changes back to Zotero). Whoever the team designates. Anyone else can run /sync-bib (read-only) freely. - Whether the project is in drafting or shared state — controls whether /sync-bib rewrites your .tex keys (drafting) or renames Zotero entries (shared) on key mismatch.

    If you're not the bib_keeper, don't run /fix-bib-in-zotero against the project — it writes to Zotero, and conflicts arise if two people run it on the same library. The bib_keeper field is also visible as a comment at the top of references.bib once /sync-bib has run.

    If you have Claude Code but no Zotero¶

    You can still run /sync-bib --read-only — it skips Zotero entirely and just runs orphan detection against your local bib, updating project_management/zotero_todo.md. Useful for seeing what's pending without needing Zotero auth. The flag auto-engages when no Zotero MCP is configured on your machine.
