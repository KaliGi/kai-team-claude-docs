    Notes and feedback¶

    The team's institutional memory accumulates in project_management/notes_and_feedback/ — a folder that stays local-only and is never committed (see project-structure). Meeting notes, call transcripts, co-author comments, internal discussion transcripts: anywhere a real decision happens without a formal channel. The format is uniform: one file per meeting or topic, prefixed with the date. In eighteen months, when a revision lands or a new co-author joins, this folder lets you answer "what did we actually decide about X?" without re-reading every email thread.

    What goes here¶

    Inside project_management/notes_and_feedback/:

    • Meeting notes — your notes from any call, your notes from someone else's meeting, voice-memo transcriptions cleaned up to text.
    • Call transcripts — full Teams or Zoom transcripts, optionally with a short summary at the top.
    • Co-author feedback — emailed comments pulled to text, Word track-changes notes flattened to markdown, voice-message transcriptions.
    • Internal discussion transcripts — Slack threads, email threads, anywhere a real decision happens without a formal meeting.
    • Strategic-positioning decisions: "we decided to position this as X because Y". The kind of choice you make once but need to remember.

    Reviewer reports do NOT go here. The journal's PDF goes in project_management/submissions/<NN_journal>/ (the submission archive); the agent-formatted TeX version goes in paper/revisions/<JOURNAL>/. See the submissions page for that workflow.

    Naming convention¶

    YYYY-MM-DD_<kind>_<identifier>.md is the format. The date prefix is the one part I treat as non-negotiable, because the folder accumulates over years; without dates, sorting by date stops working the moment co-authors save files with their own conventions. The <kind> slot tells you the type at a glance: meeting, call, feedback, decision, transcript. The <identifier> slot tells you which one: Arne, Esther, AEA, intro_framing.

    Examples:

    • 2026-03-15_meeting_with_Arne.md
    • 2026-03-22_call_AEA_revisions.md
    • 2026-04-01_feedback_from_Esther.md
    • 2026-04-10_decision_framing_for_intro.md

    Pick the identifier so a glance tells you what is in the file. meeting_with_Arne beats meeting_3 because the latter forces you to open every file to find the right one. Same logic everywhere else: feedback_from_Esther beats feedback_2, decision_framing_for_intro beats decision_5.

    Why a fixed structure matters¶

    The case for the convention is simple: a folder with eighty undated free-form notes is unsearchable; eighty files with the same template are scannable. When a revision lands and you need "what did Esther say about the framing?", a structured note answers in five seconds. A free-form one answers in twenty minutes.

    The other half of the case is that Claude (and the upcoming meeting-notes assistant; see below) can parse a structured file. A note with Decisions: and Action items: headers is queryable; a stream-of-consciousness file is not. There is also a less obvious benefit: a uniform structure prevents the failure mode where a note records the discussion but not the decision. If the template has a Decisions section, you fill it in even when the meeting felt inconclusive. That habit is how institutional memory survives.

    File template (recommended)¶

    # 2026-03-15 — Meeting with Arne

**Attendees:** Kai, Arne
**Agenda:** R&R strategy for QJE; division of labour for the response.

## Decisions

- Send the revision to QJE rather than RESTAT (Arne's argument: stronger
  fit with the policy framing).
- Arne drafts the response to Referee 1; Kai drafts response to Referee 2;
  both review each other.

## Action items

- [ ] Kai: draft response to R2 by 2026-03-22
- [ ] Arne: draft response to R1 by 2026-03-22
- [ ] Joint review session 2026-03-25

## Open questions

- Do we need a new robustness check on cluster level? Arne to think about
  it before next call.

## Notes

- Arne mentioned a Blattman paper relevant to the framing — send him the
  citation if I find it.
- Discussion of alternative venues if QJE rejects: RESTAT, JEEA, EJ.

    The point is not the exact template (pick the one that fits the team), but that there IS one and the team uses it consistently. Switching template every meeting defeats the searchability the convention was supposed to buy.

    Anti-patterns¶

    • Free-form notes with no date in the filename. A folder of meeting_notes.md, discussion.md, call_notes_FINAL.md is unsearchable within a month.
    • Notes scattered across multiple folders. A meeting note in working/, a co-author comment in your email folder, a reviewer report in paper/. When you need to reconstruct a decision, you check three places and miss something.
    • Notes that record discussion without recording decisions. "We talked about the framing" is not useful in eighteen months. Force the decision into a heading the template makes you fill in.
    • Voice notes kept as .m4a. Transcribe to text. Audio is not searchable; text is.

    The meeting-notes assistant¶

    The /meeting-notes skill (project-workflow plugin, shipped 2026-06-23) does this for you: paste a Teams or Zoom transcript (or your raw written notes) and ask, and it produces (i) a date-prefixed note file in this folder using the template above, and (ii) extracted TODOs for project_management/TODO.md, with a confidentiality blocklist applied. The fixed template here is what makes that automation possible: a transcript can be reformatted into a structured note because the structure is known.

    Prefer the manual route? Paste the transcript at the bottom of a date-prefixed file, write the Decisions / Action items / Open questions sections at the top by hand, and save it there. Either way, remember: project_management/ is local-only — it is never committed (it is gitignored by the canonical structure, precisely because these notes can contain sensitive discussion).
