    Daily workflow (handbook)¶

    Audience: anyone working on a kai-team-claude project — from co-authors who never touch the command line to those writing every line of code.

    This handbook is your day-to-day reference once you're set up. If you're brand new, start with why collaboration is hard and the quickstart, then come back here. Read Part 1 once (10 minutes); reference the rest as you encounter situations.

    Works for three workflow styles: pure terminal (no AI), Claude Code, Codex. Tool-specific bits are flagged.

    Term you don't know? The primer defines them all in economist language; the concepts page explains why the system is built this way.

    Part 1 — Get started¶

    10 minutes to a first commit. After this part you can do useful work; the rest of the handbook is reference.

    Who reads this and what they care about¶

    The table below maps what you spend time on to the sections you most need. You don't have to know git deeply; you do have to follow a small set of rules that prevent failure modes git's flexibility allows. Every rule has a reason — we explain each.

    If you mostly… …you most need Read first
    Edit the paper text (writing, conceptual contributions, lit review) Compile the paper, leave notes and edits, never break anything §1.2 setup, §2.7 paper workflow, §3.1 Claude Code, §6 cheat sheet
    Write code or generate exhibits Run scripts, produce figures/tables, share them with the team All of §2, §3.2 or §3.3 (your tool), §4 when it goes wrong
    Are new to git Survive the Save-vs-Commit confusion and never lose work §1.2 setup, §2.2 two-layer model, §2.3 Save ≠ Commit, §4 recovery
    Are new to AI assistants Decide whether to use Claude Code or Codex; learn the safe paths §1.2, §3 (all three)

    These are roles in a workflow, not levels in a hierarchy. You may switch between rows on different projects, or within the same project across weeks.

    1.1 The 30-second mental model¶

    A project has two places where files live: Dropbox (instant sync across your machines and any co-authors looking at the same folder) and GitHub (deliberate snapshots that record what changed, who changed it, when). Use both at once: Dropbox prevents "I lost what I typed"; GitHub records "this is the version that produced the paper."

    The single sentence to remember: saving a file is not the same as sharing it with your co-authors. Save lives in Dropbox. Share happens via git commit + git push.

    Three more sentences that prevent most confusion later:

    • There is exactly ONE git repository per project. The project root, every clone_<XX>/ folder, and any copy on GitHub are all clones of that one repo — copies of the same history that exchange commits. You never "create another repo" for a co-author; you create another clone.
    • A branch is a parallel line of commits inside that one repo. Your work lives on your branch; main is the agreed-upon version.
    • Merge is the step that brings branches together: it combines two branches' commits into one history. Git does it automatically unless both branches changed the same lines — then it asks a human to choose.

    1.2 Setup walkthrough — once per machine¶

    These are the one-time steps for each computer you use. Allow 30 minutes.

    Step 1: Dropbox¶

    You almost certainly already have it. If not: install from dropbox.com. Sign in with the account the project was shared with. Wait until the Dropbox tray icon shows a green tick — that means everything is downloaded.

    If you have hundreds of GB free disk: choose "Online Only" for big folders you won't open daily (literature/, large data). The project's code/, paper/, and output/ folders should be set to "Available Offline" so they're always on your laptop.

    Step 2: GitHub access¶

    Whoever set up the repository invites you to it. You receive an email. Click the link, accept.

    You need either an SSH key or a Personal Access Token to push from your laptop. The easiest path: install GitHub Desktop (desktop.github.com) on Windows or macOS. It handles authentication invisibly. You can run all git commands from a terminal AND have GitHub Desktop sign you in.

    Step 3: Git¶

    If you're on macOS: git is usually already installed. Test by opening Terminal and typing git --version. If you see a version number, you're done.

    If you're on Windows: install Git for Windows from git-scm.com. This gives you "Git Bash" — a terminal where git commands work the way the rest of this handbook assumes.

    Then, one-time identification (your name and email show up in commit history):

    git config --global user.name "Your Full Name"
git config --global user.email "your.email@university.edu"

    Use your university email if the repo is institutional; otherwise your personal one.

    Step 4: Choose your AI assistant (optional)¶

    You can do everything in this handbook with just a terminal. Adding an AI assistant makes some operations smoother. Two options:

    • Claude Code (desktop or CLI from claude.com). Reads the project's CLAUDE.md and follows the project rules automatically. Won't push without your explicit OK. Refuses to touch data/raw/. Either tool works; Claude Code is the lower-friction option because it reads the project rules for you.
    • Codex (CLI or VS Code extension). Faster code autocomplete but does not automatically read CLAUDE.md. You own the rules — read every diff it suggests, stage and commit yourself, never let it push.
    • Neither. Just use your editor + terminal. The handbook covers this in §3.3.

    If you're new to AI assistants, start with neither for the first week. Get comfortable with the rhythm first. Add Claude Code in week 2.

    Step 5: Find the project on your machine¶

    The project lives at ~/Dropbox/<project-name>/. (Where ~ is your home directory: /Users/<you> on macOS, C:\Users\<you> on Windows, with Dropbox under it.)

    Open a terminal there:

    # macOS / Linux
cd ~/Dropbox/<project-name>

# Windows (Git Bash)
cd /c/Users/<you>/Dropbox/<project-name>

    If it's a multi-clone project (you'll see per-author folders like clone_AW/, clone_CD/), cd into the clone named with your two-letter initials. If yours doesn't exist yet, the setup runbook in docs/per-project-onboarding.md ("Set up your own working clone") creates it in ~6 commands. Only edit inside your own clone_<XX>/ — never in the project root (it's the shared container, not a repo).

    If it's a single-clone project (you'll see one code/ folder), cd into code/. Everyone shares it.

    Step 6: Pull latest¶

    Before your first edit:

    git pull

    If this is a multi-clone project, run git pull inside each clone_*/ folder you'll touch. For most co-authors, that's only your own clone_<XX>/.

    You're set up. The rest is workflow.

    1.3 A first end-to-end exercise (recommended)¶

    To make sure setup actually works, do this small test before any real work. (This one test commits straight to main and pushes immediately — the single sanctioned exception, because TODO.md is harmless by design. All real work follows §2.5: branch first. If the project has no TODO.md, ask a co-author for an equally harmless target file.)

    1. Open TODO.md in the project root.
    2. Add a line under "High priority": - [ ] [XX] Test commit by [your name]. Use your two-letter initials.
    3. Save the file (Ctrl-S).
    4. Run: 
      git status                               # should show TODO.md as modified
git add TODO.md                          # stage the change
git commit -m "Test commit by [your name]"
git push
    5. Open the project on GitHub in your browser. Find your test commit in the history.

    If all five steps worked, you're properly set up. If step 4's git push asks for credentials or fails, your GitHub auth needs fixing — see GitHub Desktop in §1.2 step 2.

    Now delete the test line in TODO.md and commit again to clean up. Or leave it as a memento.

    Part 2 — Daily workflow¶

    2.1 What this project looks like¶

    Your project folder is on Dropbox at ~/Dropbox/<project>/. The layout is the same across every kai-team project (formal spec in principles/project-structure-canonical.md):

    <project>/
├── CLAUDE.md                 project rules; read first every session
├── README.md                 what the project is
├── data/
│   ├── raw/                  READ-ONLY. Never edit. Copy to processed/ before transforming.
│   ├── processed/            cleaned outputs from your scripts
│   └── documentation/        codebooks, dictionaries
├── code/  (+ clone_<XX>/ per-author clones on multi-clone projects — see §2.4)
├── output/
│   ├── figures/              FLAT. <theme>_<descriptor>_v<N>.pdf naming.
│   ├── tables/               FLAT.
│   └── _exploratory/<branch>/  auto-redirected outputs from feature branches
├── paper/                    paper.tex, references.bib, compiled PDFs
├── literature/               PDFs of cited papers. LOCAL ONLY. Never commit.
├── project_management/       reviewer notes, deadlines, decisions. LOCAL ONLY. Never commit.
└── temp_claude/              Claude session scratch. Local only.

    Two ideas are doing all the work here:

    • Sensitive things are local-only. literature/ has copyrighted PDFs. project_management/ has reviewer feedback, panel critiques, strategic decisions. These never go to GitHub.
    • Raw data is read-only. data/raw/ is the original truth. Every script reads from it but writes elsewhere. If raw data ever changes accidentally, your analyses become irreproducible.

    2.2 The two-layer model: Dropbox + GitHub¶

    You have two systems that look like they do the same thing. They don't.

    Dropbox GitHub
    What it stores The current file contents Snapshots ("commits") of what files looked like at specific moments
    When it syncs Instantly when you save When you deliberately run git commit and git push
    Who sees changes Anyone with access to the folder, immediately Anyone who runs git pull after you git push
    Reverting "Show deleted files" — last ~30 days Any commit ever made, forever
    Conflict resolution Creates "('s conflicted copy)" files Asks you to merge
    What it's for Backup + cross-machine sync for one person Collaboration + history + reproducibility

    Use both at once. When you save, Dropbox handles the "don't lose what I just typed" problem instantly. When you commit and push, GitHub handles the "everyone needs to see this version" problem.

    The most common failure mode by far is treating these as interchangeable. They're not. The next two sections explain why, in practice.

    2.3 The rule: Save ≠ Commit¶

    Saving a file via Ctrl-S in your editor does NOT create a git commit.

    You did this Result
    Ctrl-S in your editor File is on disk. Dropbox syncs to your other machines. Git has no idea anything changed.
    git add <file> You tell git "I want to include this file in my next commit." Still no commit.
    git commit -m "message" Git creates a snapshot you can later go back to. Lives only on your computer.
    git push Git uploads your commit to GitHub. Your co-authors can now git pull and see it.

    So a typical change has FOUR steps to be fully shared: Save → git add → git commit → git push.

    Why does this matter, in concrete terms?

    • You spent the afternoon improving a regression. You saved everything. You closed your laptop. You did NOT commit. Tomorrow your co-author opens the project (in single-clone mode) and her code/ folder has YOUR uncommitted edits in it because Dropbox synced them. She thinks they're from main, edits on top of them, commits her work. Now both of your changes are tangled and there's no clean way back to "what was on main yesterday."
    • You spent the afternoon improving a regression. You committed. You closed your laptop. You did NOT push. Tomorrow your co-author runs git pull and sees nothing new. She doesn't have your improvement. She redoes work you already did.

    The fix is to make commit + push a habit, not an afterthought. Commit at every clean checkpoint (every ~30 minutes if actively coding). Push at the end of every session. The next section gives you a concrete rhythm.

    If you only edit paper text (not code): the same rule applies to paper/paper.tex. Saving in your editor doesn't make your co-authors see your edits. You still need git add paper/paper.tex && git commit && git push (or your editor's git interface), or — if the project is Overleaf-mastered — to apply the edits in Overleaf where they get committed by Overleaf's git bridge.

    2.4 Single-clone vs multi-clone — and which one you're on¶

    Whoever set the project up chose one of two layouts when it was bootstrapped. You don't choose; you adapt. Neither makes anyone "the lead" — all co-authors are equal.

    How to tell which¶

    Look at the project root (or the project CLAUDE.md, which declares it in a ## Multi-clone layout block).

    • Single-clone: one folder named code/, no clone_<XX>/ siblings. Everyone shares it (for 1–2 people editing code, rarely in parallel).
    • Multi-clone: per-author folders named clone_AW/, clone_CD/, etc. Each is its own full git clone, on that author's branch.

    Single-clone (default for 1-2 active code editors)¶

    Simpler. One git clone — the project root itself. You switch branches inside it. Dropbox keeps everyone in sync on whatever branch is currently checked out.

    The trap: that last sentence is also the failure mode. If you switch to your branch and forget to switch back to main, your colleagues see your branch's files next morning. The rule "switch back to main before stopping" exists exactly to prevent this.

    Multi-clone (when 3+ co-authors edit code in parallel)¶

    No one owns the project. The Dropbox project folder is a shared container — it holds the single data copy and everyone's personal clones, but it is not itself a git repo. There is one GitHub repo; main is canonical and owned by no one locally. Each co-author has their own equal clone (clone_<XX>/), on their own branch, and works only in it.

    Folder What it is Who runs git in it
    project root shared container (data + everyone's clones) — no .git nobody — it's not a repo
    clone_AW/ Arne's full-project clone, on his branch only Arne
    clone_CD/ Charlie's clone, on his branch only Charlie
    clone_KG/ Kai's clone — same as everyone else only Kai

    The folder name tells you whose work (and which branch) you're looking at — Dropbox doesn't show branch info; folder names do.

    flowchart TB
    GH["GitHub: main (canonical, owned by no one)"]
    subgraph P["~/Dropbox/&lt;project&gt;/ — shared CONTAINER (no .git)"]
        DATA["data/ — THE single copy<br/>(gitignored)"]
        subgraph KG["clone_KG/ — Kai's clone"]
            KC["code/ paper/ output/"]
        end
        subgraph AW["clone_AW/ — Arne's clone"]
            AC["code/ paper/ output/"]
            M[".data-in-parent marker"]
        end
    end
    M -->|"re-anchors rawdata/processed"| DATA
    KG -->|"push &#8594; PR &#8594; merge (anyone)"| GH
    AW -->|"push &#8594; PR &#8594; merge (anyone)"| GH
    GH -->|"git pull (into your own clone)"| AW

    Two things to know about your nested clone:

    1. It does NOT contain the data. data/ is gitignored — listed in a file called .gitignore that tells git to act as if those files don't exist, so they can never be committed or pushed by accident; the one real copy lives in the parent container folder. An empty .data-in-parent marker file in your clone root makes the 00_setup scripts find it — the setup runbook in docs/per-project-onboarding.md ("Set up your own working clone") walks you through this.
    2. Your code/, paper/, and output/ are clone-local on purpose. They reach the team through git push + pull request — that's the collaboration mechanism.

    The rule: clones are single-writer, and everyone is equal. Only you touch your clone_<XX>/; nobody runs git at the container root (it isn't a repo).

    What's actually inside your clone (it LOOKS like duplication, it isn't)¶

    Open your clone_<XX>/ in a file browser and you'll see data/ and literature/ folders and panic that the whole dataset got copied. It didn't. Those folder names are misleading — what's actually inside is tiny, because the heavy content is gitignored and lives only once, at the parent. Measured on a real project:

    Folder in your clone What's really in it Typical size
    data/ the codebooks (data/documentation/, tracked + versioned). raw/ and processed/ are gitignored — re-anchored to the parent via .data-in-parent ~1 MB
    literature/ the .bib files (tracked). The PDFs are gitignored — repopulate from Zotero via /sync-pdfs ~2 MB
    code/, paper/ your actual scripts and paper source small, unless legacy binaries linger in paper/
    output/ tracked exhibits (figures/tables) — clone-local, merged via PR can be large by design

    So data/ + literature/ + code/ together are a few MB — the design working exactly as intended, not a copy of the data. If a clone is genuinely heavy, the cause is almost always tracked binary bloat in paper/ or .git/ history (see the migration note in principles/project-structure-canonical.md), never the data/literature skeletons.

    "Sandbox" does NOT mean invisible — seeing vs. interfering¶

    Because the clones sit inside the Dropbox-synced project folder, everyone can SEE everyone's sandbox. That is intended: Dropbox backs your clone up, and teammates can peek at your in-progress work. The isolation is about WRITING, not seeing:

    Allowed? Why
    Looking at files in someone else's clone_<XX>/ Yes Dropbox shows them to you; that's the design
    Editing files or running git in someone else's clone_<XX>/ Never You'd race their Dropbox sync and corrupt their .git/
    Others seeing your half-finished work in your sandbox Yes, normal Visibility ≠ shared; it enters the team's history only when YOU push

    And inside your own sandbox: you edit the SAME canonical files as everyone else (code/02_analysis.do, not a parallel structure) — the clone is a full copy of the repo, so the file layout is identical by construction. Only your outputs are routed somewhere special (output/_exploratory/<branch>/, automatically, by the setup scripts).

    Mental-model FAQ (field-collected — real questions from the first deployment)¶

    • "So we need an extra git repo for each project / each co-author?" No. ONE repo per project. Root, clone_<XX>/ folders, GitHub — all clones of it.
    • "When do I push?" Daily, even unfinished work. Pushing your branch is always safe: it never touches main, and it's your only off-machine backup besides Dropbox. Push and merge are SEPARATE steps — possibly weeks apart.
    • "Who writes to main?" Nobody, directly. main changes only through a merge any co-author (or a reviewed PR) performs.
    • "Does merge check our conventions?" No — git merges text, blindly. The PR review is the convention gate: that's where one-canonical-file-per- language, the exhibits note, and exhibit promotion get checked by a human.
    • "Do I write code differently in my sandbox so it can merge later?" No. Same files, same conventions, same structure. Merging works precisely because everyone edits the same canonical files on different branches.

    2.5 Daily rhythm¶

    A workday has a beginning, middles, and an end. Here's the rhythm:

    Starting a session¶

    1. Open the project folder.
    2. Pull latest: git pull. (In multi-clone, do this inside your own clone_<XX>/.) Multi-clone caution: in your nested clone, git pull only updates your own branch — it says "up to date" even when main moved on weeks ago. Every few days, and always before opening a PR, also pull main into your branch: git fetch origin && git merge origin/main.
    3. Confirm what branch you're on: git status --short --branch. (Multi-clone: it should match the folder name.)
    4. Single-clone only: switch to a feature branch if you're about to edit. Never edit main directly. 
      git checkout -b XX/short-description-of-change
      (Example: git checkout -b KG/cluster-se-fix.)

    Middle of the day — making changes¶

    1. Edit your script, exhibit, or paper.tex.
    2. Run scripts; check outputs land in output/_exploratory/<your-branch>/ (not canonical output/).
    3. Commit at every clean checkpoint: 
      git status                                    # see what changed
git add <specific file paths>                 # never `git add .`
git commit -m "Short imperative summary"
    4. Keep going. Each commit is a save-point you can return to.

    Ending a session¶

    1. Final commits: stage and commit anything not yet committed.
    2. Push: git push.
    3. Single-clone only: switch back to main and pull, so the folder is in a clean state when your co-author opens it. 
      git checkout main
git pull
    4. Multi-clone: nothing special. Each clone stays on its own branch.

    That's the whole rhythm. It feels like overhead at first; after a week it's automatic.

    2.6 Adding a new exhibit, end-to-end¶

    This is the most common workflow. Suppose you want a new figure: outcomes_event_study_v1.pdf.

    1. Branch first¶

    git checkout -b KG/add-eventstudy-fig

    2. Write the script¶

    Add it to the right numbered slot in your code folder. For example, code/04_plots_eventstudy.R (R) or code/04_plots_eventstudy.do (Stata) or code/04_plots_eventstudy.py (Python).

    The first line of the script (or near the top) should source the setup file:

    # R
source(here::here("code", "00_setup.R"))

    * Stata
do "../code/00_setup.do"

    # Python
from pathlib import Path
exec(open(Path(__file__).resolve().parents[1] / "code/00_setup.py").read())

    The setup file sets paths, installs dependencies if needed, and prints a banner showing the active git branch. The branch banner is your first chance to catch "wait, I'm on the wrong branch."

    3. Run it¶

    The setup file redirects outputs to output/_exploratory/<sanitised-branch>/figures/ automatically — branch names are lowercased and non-alphanumerics become underscores. So on branch KG/add-eventstudy-fig, your figure lands at output/_exploratory/kg_add_eventstudy_fig/figures/outcomes_event_study_v1.pdf, not in canonical output/figures/.

    This is deliberate: your work-in-progress doesn't contaminate the canonical exhibits the paper compiles against. _exploratory/ is gitignored scratch — it never enters a commit. Promotion to canonical is an explicit copy you make in step 7.

    4. Reference it in the paper, also on the branch¶

    In paper/paper.tex:

    \includegraphics[width=\textwidth]{\outdir/figures/outcomes_event_study_v1.pdf}

    The \outdir macro is set automatically by 00_setup.{do,R,py} via paper/_output_path.tex — points at output/_exploratory/<branch>/ on a feature branch, at canonical output/ on main. So the same \includegraphics line in your .tex resolves to the right place on your branch and the right place after PR merge to main.

    5. Compile¶

    cd paper
latexmk -pdf paper.tex          # or your usual compile command

    If the paper builds and the figure looks right, you're ready to share.

    6. Show it: the exhibits note¶

    Before anyone reviews your work, it goes into your branch's exhibits note — one exhibits-note.tex at your clone root, copied once from kai-team-claude/templates/exhibits-note.tex. This is THE surface where new experimental work is shown; not screenshots in email, not pasted console output. A teammate opens one PDF and sees what the branch produced and what it means.

    The note contains only exhibits plus interpretation, under five hard rules (all scaffolded in the template):

    1. One section per exhibit, title states the finding, not the method.
    2. Every exhibit gets a 2–4 sentence Interpretation: what to see, the key magnitude with units, the main caveat.
    3. Consistent wording across exhibits and with paper.tex — same treatment name, outcome name, sample label, units everywhere.
    4. One transition sentence opens each section, linking it to the previous exhibit.
    5. \FloatBarrier closes every section (already in the skeleton), so floats stay with their exhibit instead of drifting.

    Compile from the clone root (latexmk -pdf exhibits-note.tex); the template's \exhibitdir macro points into your branch's output/_exploratory/<branch>/ folder. A small checker script (check-exhibits-note.py, copied from the same templates folder) mechanically verifies coverage and structure — every exhibit in the note, an interpretation per section, FloatBarrier in place — so the five rules are enforced, not just suggested. Commit the note with your code — it travels with the branch, so your PR carries its own explanation.

    If you work with Claude Code or another LLM: tell it to add every new exhibit to the note as it creates it, and require it to visually check the compiled PDF (it can read PDFs) before showing it to you — broken references, overflowing figures, and legends covering data all compile "successfully". The interpretation paragraph is yours to verify — the numbers in it must match the exhibit exactly.

    7. Promote the final exhibit, then commit¶

    output/_exploratory/ is gitignored — it cannot be committed, and git will refuse to add it. Promotion is YOUR explicit copy: when the figure is final, copy it from your exploratory folder to the canonical (tracked) path, on your branch:

    cd ..                            # back to project/clone root
cp output/_exploratory/kg_add_eventstudy_fig/figures/outcomes_event_study_v1.pdf \
   output/figures/outcomes_event_study_v1.pdf

git status                       # see what changed
git add code/04_plots_eventstudy.R \
        output/figures/outcomes_event_study_v1.pdf \
        paper/paper.tex
git commit -m "Add event-study figure"

    The PR therefore carries three things: the producing script, the final exhibit at its canonical path, and the paper reference. Nothing "promotes automatically" — the copy above IS the promotion, and it's the PR author's job.

    (Use explicit paths. git add . is blocked by project rules — too easy to stage sensitive files by accident.)

    8. Push¶

    git push                         # first push on a new branch: git push -u origin <branch>

    (Per project rule, Claude Code asks for your explicit confirmation before pushing. If you're using terminal directly, you're already explicit.)

    9. Open a pull request¶

    In your browser, go to the project's GitHub page. There's a banner suggesting you open a PR from your branch. Or via terminal:

    gh pr create --base main

    10. Review and merge¶

    A co-author reviews. The merge brings your committed canonical exhibit (output/figures/...) and the paper reference to main together — the paper on main compiles immediately because the file travelled inside the PR (you copied it there in step 7).

    That's the end-to-end. Every figure or table goes through this loop. It feels like more steps than "save the file" but each step has a clear purpose: branch protects main, _exploratory/ separates work-in-progress, the step-6 copy is the deliberate promotion, PR review catches mistakes.

    2.7 Modifying the paper, end-to-end¶

    Same rhythm. Treat the paper like code.

    1. Branch first. git checkout -b KG/edit-intro-pars-3-5.
    2. Edit paper/paper.tex. Save as you go.
    3. Compile locally to confirm nothing broke.
    4. Commit + push: git add paper/paper.tex && git commit -m "Tighten intro pars 3-5" && git push.
    5. PR + review + merge.

    Never edit paper.tex on main directly. Main is the submitted version of the paper. All changes go through branches + PR.

    For Overleaf-mastered projects (declared in CLAUDE.md ## Project mode): the canonical .tex lives in Overleaf, NOT in paper/. Your edits happen in Overleaf via your browser. Syncing Overleaf to git is a manual step (done by the Overleaf admin via Overleaf's git access), not automatic. You don't git add paper/paper.tex because there's no local paper.tex to add. The Overleaf admin (one person sets up the sync) coordinates what's in Overleaf.

    2.8 Pushing and sharing — the rules¶

    First, the distinction the rules build on: pushing is backup + visibility; merging is integration. Pushing your branch to GitHub copies your commits off your machine — safe anytime, touches nothing canonical, recommended daily. Merging (later, via PR) is the separate, deliberate step that brings your branch into main. A co-author who thinks "GitHub only gets my work at merge time" has no off-Dropbox backup until the work is finished — push early, push often.

    Operation Allowed without per-push approval?
    git push of your own feature branch (XX/...) YES — anytime. That's how your work gets backed up and reviewed; §2.3's "push at the end of every session" means exactly this.
    Anything that lands where others build on it: merging a PR to main, pushing directly to main A co-author's review is the team convention, not a technical gate — you may merge your own (see below).
    (Note: the "pushes require explicit approval" rule in CLAUDE.md governs Claude — your AI session asks YOU before it pushes. It is not a restriction on you pushing your own branch.) —
    git push of .bib-only commit (single file, you are the declared bib_keeper) YES — co-authors need the updated bib to compile.
    git push --force NEVER without explicit approval. Rewrites shared history.
    git push --tags Counts as a push. Ask.
    gh pr create, gh pr merge Counts as an implicit push. Ask.

    Why this rule exists. Pushed commits are visible to everyone with read access — co-authors, but also anyone the repo is shared with later. A commit message containing "fixed JPE reviewer 2's point about Table 3" leaks the target journal AND the existence of a critical review. Per the external-communications-hygiene rule, this kind of information doesn't go in git history. Asking a co-author before pushing catches these accidents.

    For routine code changes with neutral commit messages ("Tighten cluster SE in main regression"), approval is fast — usually a one-line "go ahead" in chat.

    2.9 Working with the shared data¶

    Here is the one place where "work in your own clone" does not isolate you, so it's worth understanding. Your code, paper, and exhibits stay in your clone until you merge a PR — but the data is shared the instant you write it. Each clone's scripts read and write the one data/ folder in the parent (that's the .data-in-parent setup), so when you run the cleaning code, the shared data/processed/ changes for everyone immediately — no merge involved. That's why data needs a little human coordination where code does not.

    The mental flip for a Dropbox veteran: git reconciles parallel work on code; humans reconcile parallel work on data.

    • Reading is free and parallel. Normally the dataset is fixed and everyone analyses the same processed/. No coordination needed — this is 99% of the time.
    • Data lives in Dropbox, not git (it's too big and not text-mergeable). So a bad change is recoverable from Dropbox version history — the data equivalent of re-cloning a broken repo.
    • Never overwrite the raw data. data/raw/ is read-only and append-only: new raw arrives as new files, never edits to existing ones. It's the one thing you can't regenerate. (Claude will ask you to confirm before running any code that writes to or deletes raw — that's the guard_raw_data hook. The same goes for a frozen replication package.)
    • processed/ is a cache, not the truth. It's rebuilt from raw/ + the cleaning code (which is in git). If it ever gets clobbered, just re-run cleaning.

    When you change the dataset, which kind of change is it?

    • Adding a variable — you add a column in the cleaning code. It merges through git like any code change and doesn't move anyone's existing results. Just merge it; a heads-up is polite but nothing breaks.
    • A breaking change — recoding, fixing, dropping observations, changing the sample: this moves everyone's results. So:
    • Announce before you rebuild ("rebuilding the analysis dataset, hold off re-running cleaning") — two people rebuilding at once clobber each other, and there's no merge for data.
    • Rebuild from the merged cleaning code, wait for Dropbox to sync (green tick), and tell the team to re-run their analyses.
    • Log it in data/documentation/data_changelog.md — one dated line, e.g. 2026-06-20 Added 2024 wave. N 1,200 -> 1,540. All time-series regs change. (Breaking changes only — not new variables, and not the messy initial build before anyone depends on the data.)

    Full version, including the data_keeper option for data-heavy projects: the "Working with the shared data" section of principles/project-structure-canonical.md.

    Part 4 — When things go wrong, and why they usually don't¶

    This section covers the failure modes the design tries to prevent, what to do if they happen anyway, and why they're rarer in practice than they look on paper.

    4.1 "I edited the wrong file"¶

    If you saved but haven't committed:

    git checkout -- <file>             # revert to last committed state

    Or via Dropbox web UI: "Show deleted files" → restore. Dropbox keeps versions for ~30 days.

    If you committed but haven't pushed:

    git reset --soft HEAD~1            # undo last commit, keep changes staged
# (per global rule, --hard requires explicit approval — soft is fine)

    If you committed AND pushed:

    git revert <commit-hash>           # creates a new commit that undoes the bad one
git push

    Revert is preferred over reset for pushed commits — it preserves history (useful for blame and reproducibility) and is always safe per the global rules.

    4.2 "I'm on the wrong branch"¶

    git status --short --branch        # confirm what branch you're on
git stash                          # save your in-progress changes
git checkout <right-branch>        # switch
git stash pop                      # restore your changes on the right branch

    If you'd already committed on the wrong branch:

    git log --oneline -3               # see the recent commit(s) on this branch
git checkout <right-branch>        # switch
git cherry-pick <commit-hash>      # bring the commit over
git checkout <wrong-branch>        # back to where you were
git reset --soft HEAD~1            # remove the commit from the wrong branch

    4.3 "Dropbox shows a conflicted copy"¶

    Two devices saved the same file at almost the same time. Dropbox keeps both: the canonical one with the original name, and a copy named <file> (<Name>'s conflicted copy 2026-06-09).<ext>.

    1. Open both. Decide which content wins (or merge manually).
    2. Save the merged result as the canonical name.
    3. Delete the conflicted copy.

    Never git add a conflicted copy. Project rules block staging files matching *conflicted copy* precisely to prevent these from polluting history.

    If the conflict happened in a code file, this is the most painful failure mode — you have to read both versions and decide. Prevention: commit + push frequently. The shorter the window between save and push, the smaller the surface for two devices to disagree.

    Binary files (.dta, .xlsx, .pdf, images) can't be merged at all — there is no line-by-line comparison to do. Decide by provenance instead of by eyeballing:

    1. If the file is produced by a script (most .dta and figure PDFs are): delete BOTH copies and re-run the producing script. The code is the truth; the conflicted pair is just two stale snapshots.
    2. If it's hand-made (a manually built spreadsheet, an external figure): keep the copy with the later modification time, open it to confirm it contains the recent work, then delete the other.
    3. If both copies contain different recent work (rare, but happens with shared spreadsheets): keep both temporarily, rename the loser to <file>_recovered_<date>.<ext>, and reconcile by hand — then delete the recovered copy.

    4.4 "I think .git/ is corrupted"¶

    (Multi-clone projects, after a parallel-write race or sync mishap inside .git/.) The recovery is fast — push anything pushable first if git still responds, then re-clone your own folder:

    cd ~/Dropbox/<project>/
rm -rf clone_AW/                    # your corrupted clone (use YOUR initials)
git clone <repo-url> clone_AW/
cd clone_AW && git checkout AW/exp-sandbox
touch .data-in-parent              # re-create the data marker

    Real history lives on GitHub. The local clone is reproducible from there. ~30 seconds; you lose only commits that were never pushed.

    Why this is rare in practice. Three reasons the design makes corruption unlikely:

    1. Clones are single-writer. Only you touch your clone_<XX>/. Simultaneous-write conflicts on .git/ require multiple processes editing the same .git/. With a one-writer rule, that almost never happens.
    2. The container root is not a git repo. No one runs git there; routine work happens only in your own clone.
    3. Economist commit cadence is low. A few commits per day per researcher. The window for two operations to race is tiny.

    Matray's original framing: the corruption risk is "barely there" for economist workflows. If it ever happens, the cost is ~30 seconds. That's the deliberate trade-off the multi-clone design makes — we accept a small theoretical risk because the recovery is trivial.

    4.5 "I have no idea what happened"¶

    A few places to look:

    • project_management/decisions.md and log.md — recent project decisions, in chronological order.
    • git log --oneline -20 — last 20 commits with short messages. Helps reconstruct "who changed what when."
    • git reflog — your local git history INCLUDING resets and aborted operations. The "did I really delete that branch?" command.
    • Dropbox web UI → file history → see all versions.
    • Ask a co-author. Some failure modes (especially multi-clone confusion) are hard to diagnose remotely.

    4.6 "I forgot to switch back to main" (single-clone only)¶

    You left a feature branch checked out at end of day. Tomorrow morning your co-author opens the folder and sees your in-progress files.

    Recovery on your end: push your branch, then switch back to main:

    git push -u origin <your-branch>   # send your work to GitHub
git checkout main
git pull

    Mitigation on your co-author's end: when she opens the project, the first thing she should do is check git status --short --branch. If she sees an unfamiliar branch name, she switches back to main:

    git status --short --branch        # tells her she's on KG/whatever
git checkout main
git pull

    No data was lost — both versions exist (yours on your branch, hers on main once she switches). The cost is a few seconds of confusion. Prevention: end every single-clone session on main.

    In multi-clone this problem doesn't exist. Your sandbox stays on your branch; her sandbox stays on hers. The folder-name-encodes-branch rule eliminates the failure mode.

    Part 5 — For the curious — why this design¶

    You can skip this part if you just want to get work done. Read it if you want to understand the rationale, anticipate why things are the way they are, and explain it to a future co-author yourself.

    5.1 Why GitHub + Dropbox at all?¶

    Why not just GitHub? Or just Dropbox? Each one alone fails for academic research workflows:

    GitHub alone fails on data. Datasets in economics are routinely 100 MB to many GB. Confidential or proprietary data can't be in a public-facing service. Git is built for text, not binary, and tracks every change to large files in a way that bloats the repo permanently. The standard workaround is .gitignore for data — which means data lives somewhere else and you need a second system for that "somewhere else."

    Dropbox alone fails on collaboration discipline. Dropbox shows you the current contents of a file. It does not record who changed what, why, in what order. You can't review changes before they're applied. You can't tell if Alice agrees with the version of the code that produced Figure 3. You can recover the past 30 days, but not the past three years. Reproducing a paper from two years ago is impossible.

    The two together cover each other. Dropbox handles the "we all have the data, instantly" problem; GitHub handles the "we have an auditable history of code and paper text" problem. Each system has guardrails to keep it in its lane: large data is in data/ (Dropbox-only, gitignored), code and paper text are in git, exhibits sit in output/ (Dropbox sees them for instant access; git tracks the canonical versions for reproducibility).

    This is also Matray's framing: Dropbox is the storage layer, GitHub is the collaboration layer.

    5.2 Why this folder layout?¶

    The layout in §2.1 is the result of working backward from two constraints:

    1. AEA Data Editor expectations. Published economics papers in many journals require a replication package whose structure follows the AEA's data editor guidance. The canonical layout's code/, data/raw/, data/processed/, output/figures/, output/tables/, and the run_all.sh orchestrator map directly onto what the AEA expects in a replication archive. You finish the paper and the replication package is 90% already structured.
    2. Sensitive content must never leak. literature/, project_management/, and temp_claude/ are local-only. data/raw/ is read-only. These rules exist because the failure modes — a copyrighted PDF in the repo, a reviewer's name in the commit history, raw data modified in a way that breaks reproducibility — are bad enough to justify a hard rule rather than a soft convention.

    Numbered scripts (00_setup, 01_clean, 02_analysis, 03_visualization) give a clear run order. A replicator (the AEA, a referee, a future you) can see the pipeline at a glance.

    5.3 Why per-author folders (multi-clone)?¶

    This applies to multi-clone projects. The short version: with 3+ active editors, single-clone causes more confusion than it saves.

    In single-clone, the code/ folder always shows whatever branch is currently checked out. There's no way for Dropbox to distinguish "Alice's experimental branch" from "production code we should run." Whoever switched branches last wins. The "Save ≠ Commit" rule and "switch back to main at end of day" rule exist precisely to mitigate this — but they're easy to forget.

    In multi-clone, each folder is pinned to one branch. Folder name encodes branch. You can't accidentally see someone else's experimental code in your folder — it's not there. You can't switch branches and forget — there's nothing to switch.

    The cost is disk space (N copies of .git/, which is small) and complexity (N folders instead of 1). The benefit is that two of the most common multi-author failure modes (code-file overwrite, branch-state confusion) become impossible by construction.

    The break-even is roughly 3 active code editors. With 2, single-clone is usually fine. With 4+, multi-clone is unambiguously better.

    5.4 Why _exploratory/<branch>/ for outputs?¶

    The setup files redirect exhibit outputs to output/_exploratory/<branch>/ whenever you're not on main. Why?

    Without this, two co-authors on different branches both write to output/figures/main_did_v1.pdf. The second writer wins. The first writer's exhibit is destroyed, and worse, the paper might compile against the second writer's exhibit while the script that produced it lives on the first writer's branch — creating a code-vs-figure mismatch nobody notices.

    With _exploratory/<branch>/, each branch has its own output directory. No collisions. After PR review, the merge to main promotes the exhibit to canonical output/figures/. The paper text on main automatically points there because \outdir is set to canonical output/ on main and to _exploratory/<branch>/ on feature branches.

    This is the kai-team-claude adaptation of Matray's pattern. He solved it via multi-clone (each branch has its own output/); we solve it via path redirect (one output/ directory with branch-aware subfolders). Both work; the redirect is simpler for single-clone projects.

    5.5 Why "experimental first, canonical only via PR"?¶

    Every change — to code, to exhibits, to the paper — lives on a branch first. Only after PR review does it land on main. This rule has two motivations:

    1. A reviewer catches mistakes. A second pair of eyes between "I wrote this" and "this is in the production paper" catches typos, methodology questions, and outright errors before they propagate. The PR is the natural review point.
    2. Main is always coherent. If anyone clones the repo at any moment and runs code/run_all.sh, they get the current paper with all the current figures. Main is the only branch that has this guarantee. Feature branches are explicitly NOT guaranteed to be coherent — they're work-in-progress.

    The cost is the PR step. The benefit is that "is the paper currently broken?" always has the same answer: no, because main is always coherent by construction.

    5.6 Why "never git push --force"?¶

    Force-push lets you rewrite history that's already been shared. You make a commit, push it, then realize you wanted it differently — you can force-push a new version, and git treats it as if the original never existed.

    The cost in a collaborative repo: your co-authors already pulled the original. Their local clone has the original commit. When they git pull next, git can't reconcile and either refuses or silently overwrites. Either way, the co-author who pulled before your force-push is now in trouble.

    Force-push is occasionally legitimate (rewriting commit messages on an unshared branch before opening a PR). It's never safe on shared branches. The global rule "no force-push without explicit approval" exists because the cost of getting it wrong is "your co-author silently loses work."

    5.7 Why the data/raw read-only rule?¶

    Two reasons:

    1. Reproducibility. Every script reads from data/raw/. If data/raw/ ever changes, every result built on it could be different. Reproducing the paper from a snapshot of the project requires data/raw/ to be identical. Editing it in place breaks this guarantee silently.
    2. Provenance. Whoever first downloaded the data got it from some source on some date. That source data is the ground truth. Any transformation (cleaning, recoding, merging) belongs in scripts that read from data/raw/ and write to data/processed/. Then the transformation is reproducible, reviewable, and (importantly) reversible — if the cleaning logic was wrong, you re-run from raw.

    The rule is enforced two ways: by convention (everyone knows), and mechanically (Claude Code refuses to write to data/raw/). If you find yourself wanting to edit a file in data/raw/, the answer is always "no, copy to data/processed/ first, then transform."

    Part 6 — Quick reference¶

    6.1 Cheat sheet¶

    WHO AM I?
  git config user.email                   # check the email git uses to commit
  git status --short --branch             # what's changed, what branch

START WORK
  git pull                                # bring in others' work
  git checkout -b XX/short-name           # new feature branch (single-clone)
  cd ~/Dropbox/<project>/clone_XX/         # cd into your sandbox (multi-clone)

EDIT
  # Save in your editor.
  # Run scripts: outputs go to output/_exploratory/<your-branch>/

COMMIT
  git add <explicit paths>                # NEVER `git add .` or `git add -A`
  git commit -m "Short imperative summary"

PUSH
  git push                                # ask a co-author first per global rule

PR
  gh pr create --base main                # or open via GitHub web UI

END SESSION
  # Single-clone: git checkout main && git pull
  # Multi-clone: nothing — each clone stays on its branch

RECOVER
  git checkout -- <file>                  # revert uncommitted change
  git revert <hash>                       # undo a pushed commit (safe)
  git reflog                              # your local git history including resets
  # Dropbox web UI -> Show deleted files -> last 30 days

    6.2 Seven habits worth avoiding¶

    1. Edit files in data/raw/. Copy to data/processed/ first, then transform.
    2. Commit literature/. Copyright + size. PDFs come from Zotero.
    3. Commit project_management/. Local-only operational notes (reviewer feedback, decisions).
    4. git add . or git add -A. Always explicit paths.
    5. git push --force without explicit approval. Rewrites shared history.
    6. Edit someone else's sandbox (multi-clone). clone_<XX>/ belongs to one person.
    7. Commit large files (>5 MB) without asking. Especially old exhibit PDFs in _archive/.
