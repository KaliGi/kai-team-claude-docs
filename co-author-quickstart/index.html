    Co-author quickstart (start here)¶

    For co-authors and RAs on a team already using this setup. Sizing it up for your own team instead? Start with why collaboration is hard.

    This is the fast path: a one-time GitHub setup (~10 min, below), then day-to-day work by asking Claude Code in plain language — no terminal or git commands to memorize. You don't have to learn git to use it; you can pick up as much or as little as you like over time. Prefer to click or type yourself? The same workflow, entirely by hand, is in the handbook and the manual workflow. Everything here is the shortcut.

    The one idea that makes everything click¶

    There is ONE repository, and it lives on GitHub. Your project folder on your laptop — and every clone_XX/ folder on a multi-author project — is just a local mirror of that one repository. They all sync to the same GitHub.

    • Dropbox keeps your mirror backed up and shares the heavy data files (which never go into git).
    • GitHub is where everyone's work actually meets.
    • Overleaf reads only GitHub's main branch.

    Nobody "owns" the project. The top project folder is a shared container — it isn't a git repo at all; it just holds the data everyone shares and one personal clone per person (clone_XX/). You run git only inside your own clone, so two people can never collide on the same git. Everyone can push, and everyone can merge their own work. There is no gatekeeper, and no lead.

    Hold onto that picture; every step below is just a consequence of it.

    What you do ONCE (the only real setup, ~10 minutes)¶

    1. Install Claude Code — the desktop app from claude.com (or the CLI) — and sign in with your Claude subscription.
    2. Get GitHub access, once. Accept the repository invitation (it arrives by email). Then open Claude Code in any folder and say:

      "Help me sign in to GitHub so I can push and pull." Claude walks you through it (usually: install GitHub Desktop, sign in once — that quietly handles authentication forever). You do this one time per computer.

    3. Tell Claude who you are, once — so your name is stamped on your work:

      "Set my git name to 'Your Name' and email to you@university.edu."

    That's the entire setup. You never repeat it on this machine.

    Then: everything is a sentence to Claude Code¶

    Open Claude Code inside your project folder — the one Dropbox already synced to C:\Users\<you>\Dropbox\<project>\. (To do that: in the Claude Code desktop app use Open folder and pick it; or, in the terminal, cd into the folder and run claude. Your project arrived via Dropbox — you do not download it from GitHub.)

    Multi-clone projects: if your project folder contains clone_<XX>/ sub-folders (or its CLAUDE.md has a "Multi-clone layout" block), open Claude Code in your own clone_<XX>/ instead of the top folder — everywhere below, "your project folder" means your clone. Not sure which kind you're on? Ask a co-author, or see why. Single-clone projects: the top folder is correct, read on. Claude reads the project's rules on the way in, so it knows the safety conventions. Then just say what you want — in plain words; you don't need the exact phrasing below:

    You want to… Say to Claude Code… What actually happens
    Get set up to work here "Help me set up my own copy to work on this project." Claude walks you through the short one-time setup of your personal copy (or tells you it's already set up). A few steps, once.
    Save your work "Commit my work." Claude records a snapshot of your changes, with a short note.
    Share it / back it up "Push my branch to GitHub." Your snapshots go up to GitHub — your off-machine backup, and how the team can get your work. Touches nothing in the shared paper.
    Propose it for the paper "Open a pull request for my work." Claude opens a pull request on GitHub — a tidy "here's what I changed, please pull it in."
    Actually put it in the paper (on GitHub, click Merge — or "merge my pull request") Merging the PR into main is the step that reaches the paper. This is a GitHub action, not something Claude does silently — see "two things" below.
    Get the team's latest "Bring in the latest changes from the team." Claude pulls everyone's merged work into your copy.
    Check you're working safely "Am I in the right folder to run git here?" Claude runs a quick check and tells you.

    Why this path is recommended: when the project is set up for it (its CLAUDE.md carries the team conventions), Claude reads those rules and keeps you on the rails — it won't run git in the shared container folder, won't stage data or secrets, and checks you're in your own copy first. Raw git by hand has none of that. It's not magic, though: if something looks off, Claude tells you and you decide — so the conversational path is easier and safer, not hands-off.

    Everything above you can also do by hand — Claude just saves the typing and remembers the rules. Here's the core save-and-share loop both ways:

    "Commit my work, push my branch, and open a pull request."

    Claude stages your changed files (explicit paths, never git add -A), commits with a sensible message, pushes, and opens the PR — pausing for your OK before the push.

    git add <file>                 # explicit paths, never `git add -A`
git commit -m "what changed"
git push                       # then open the PR on GitHub

    The full by-hand reference is the manual workflow.

    Two things every co-author gets wrong (now you won't)¶

    1. Pushing is not the same as putting it in the paper. The full chain is:

      your branch → push to GitHub → merge into main → Overleaf "pull from GitHub"

    Until the merge into main step, the paper (and Overleaf, if the paper uses it) don't see your work. So "I pushed it" is not "it's in the paper" — the merge is the missing link. (On an Overleaf-mastered project the paper text lives in Overleaf, not the repo, so this chain applies to your code and figures, not the .tex — ask a co-author if unsure.)

    1. You're allowed to merge your own work — but check what your team expects. On a standard private repo GitHub doesn't force a reviewer, so technically you can merge your own pull request. Whether you should is a team norm: a co-author often just merges; a research assistant usually wants the PI to look first. When in doubt, open the PR and say "ask a co-author to review" rather than self-merging. "Allowed" and "expected" are different things — this guide tells you what's allowed; your team tells you what's expected.

    If you use Codex instead of Claude Code¶

    Codex does not automatically read the project's rules, so the safety guardrails don't apply on their own. Two options: prefer Claude Code for anything touching git, or — if you stay in Codex — open the project's CLAUDE.md, read its "Multi-clone layout" section yourself, and be deliberate. The one rule that matters most: never run git in the project root (the top folder); only in your own clone_XX/.
