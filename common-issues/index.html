    Something broke — fixes & recovery¶

    Why this page exists. Almost every problem a newcomer hits on this setup is one of a small, known set — and each has a calm, specific fix. This is the page to skim before you panic and the page to search when something looks broken. Most of these are not real damage; they're the structure doing its job in a way that's unfamiliar. Nothing here requires you to be a git expert. When in doubt, the safest move is almost always "stop and ask a co-author" — listed where it applies.

    Setup and environment¶

    "Rscript / python is not recognized." The program is installed but not on your PATH (the default on Windows). Use the full path from the project's CLAUDE.md instead of the bare name — e.g. "C:\Program Files\R\R-4.4.3\bin\Rscript.exe" code/00_setup.R. If it's genuinely not installed, install R from cran.r-project.org (plain R, you don't need RStudio for setup).

    Dropbox folder looks empty or half-there. Wait for the Dropbox tray icon to show a green tick — that means everything has actually downloaded. A folder that's still syncing looks like missing files but isn't. Don't start work (or git operations) until it's green.

    "My clone has data/ and literature/ folders too — is that duplication?" No. Inside a clone those folders hold only the tracked skeletons (codebooks, .bib) — a few MB. The heavy raw data and PDFs are gitignored and live once in the shared container. Don't "clean up" the skeletons; they're meant to be there.

    Scripts can't find the data. Your clone reaches the shared data through a .data-in-parent marker file at the clone root. If it's missing, create it (touch .data-in-parent) and re-run code/00_setup.*. The setup script's banner should show the data paths pointing at ../data/.

    "Where did my work go?"¶

    A "conflicted copy" file appeared. Two people (or your own two machines) wrote the same file and Dropbox kept both. Don't delete either blindly — open both, reconcile by hand, keep the right content, then delete the "conflicted copy". Prevent it by the golden rule: one writer per file.

    "My file is in Dropbox but a co-author says it's not in git." Both can be true — Dropbox-presence ≠ git-presence. A file is only in the project's real history once you git add + commit + push it. Hand-copying into Dropbox is not enough; commit it too.

    "I think I lost work." Usually you didn't. Unpushed commits still live in your clone (and Dropbox backs the clone up). Check git status and git log in your clone first; the work is very often right there. If still stuck, ask a co-author before doing anything destructive.

    git and clones¶

    Claude opened in the wrong folder / "am I in the right place?" Run the clone-discipline check (or ask Claude "check clone discipline"). It tells you whether you're inside your clone (good) or at the shared container (move into your clone). In the leaderless model there's no "lead" to worry about — the check is purely "are you in a clone?".

    "git push was rejected." Someone else's work landed on the branch first. Pull it in, then push: git fetch origin && git merge origin/main, resolve any conflicts, git push. This is normal, not an error.

    "git pull says up to date but main has clearly moved on." Your clone is pinned to your own branch, so a plain pull only fetches your branch. Bring main in explicitly: git fetch origin && git merge origin/main. Do this every few days and always before opening a pull request.

    "There's a .git at the shared container root." That's a legacy layout from before the leaderless migration, and it's the one genuinely risky state — a shared root repo whose branch can flip under everyone. Don't run git at the root. Work in your clone, and flag it so the project gets migrated (see the canonical spec, "Multi-clone pattern").

    Overleaf¶

    A figure I fixed in Overleaf reverted. Figures travel code → git → Overleaf, one way. Editing a figure inside Overleaf gets overwritten on the next regeneration. Fix the script that makes the figure, commit, then bring it into Overleaf. (See the manual workflow.)

    "Who can change the Overleaf project?" One person coordinates the Overleaf sync (the Overleaf admin role) so two people don't push conflicting versions through the bridge. That's a one-job designation, not a hierarchy — everyone is still an equal co-author.

    "We've been copying .tex from Overleaf by hand"¶

    A common habit worth correcting: someone writes in Overleaf, then copies the .tex (or a PDF) into the Dropbox folder by hand. It looks fine — Dropbox and Overleaf match — but git silently falls behind (Dropbox-presence ≠ git-presence), and you end up with two diverging copies of a file that git is supposed to own.

    The fix, easiest first:

    • Best — sync through git, don't copy. Use Overleaf's own git access to push/pull between Overleaf and git. Then git is always current and there's nothing to hand-copy; Dropbox updates itself via your clone.
    • If a file did get hand-copied (it happens), the one-line rescue is to also commit and push it to git right after — so the canonical history stops trailing what everyone is reading.
    • Stop hand-copying anything that lives in git. Edit it through git and let it flow; copying tracked files by hand is what creates the diverging copies in the first place.

    (The standard flow this replaces is in the manual workflow.)

    When in doubt¶

    Some failure modes — especially multi-clone confusion — are hard to diagnose from a description. Ask a co-author; it's faster and safer than guessing, and it's never the wrong call.
