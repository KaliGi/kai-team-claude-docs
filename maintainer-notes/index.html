    Maintainer notes (for repo owners and people who edit kai-team-claude)¶

    This file is for anyone who pushes to the repo — initially Kai, eventually trusted co-authors with PR access. Predocs and read-only collaborators can skip it.

    Principle: what goes in the repo, what stays in ~/.claude/¶

    A skill / agent / command goes in kai-team-claude if it is:

    • Necessary for team members working on shared papers (would they actually use it?), AND
    • Mature enough to be a stable interface (not a half-finished prototype), OR
    • Pure infrastructure that other items depend on (e.g., agents called by commands).

    A skill / agent / command stays in ~/.claude/ only (never in the repo) if it is:

    • A personal experiment or prototype not yet ready for others
    • Specific to a project the rest of the team isn't on (e.g., something for a consulting engagement nobody else is involved in)
    • Project-internal output you don't want others to see (e.g., a skill that contains sensitive review notes)
    • Something whose value is purely speculative — keep it private until proven

    When in doubt: err on the side of keeping it local first, share later. It's trivial to add a polished local item to the repo (one cp and a commit). It's much harder to retroactively remove or hide an item that's already public.

    How personal items are protected¶

    The install scripts (install.ps1, install.sh) use per-item overlay logic:

    • For each item the repo contains (e.g., skills/kai-writing/), the install script replaces just that one in ~/.claude/.
    • Items in ~/.claude/ that are not named in the repo are left alone.

    Concretely, if your ~/.claude/skills/ contains:

    adversarial-review/         (also in repo)
kai-writing/                (also in repo)
real-data-figure/           (also in repo)
research-presentation/      (also in repo)
tikz-figure/                (also in repo)
_my-private-experiment/     (NOT in repo — local-only)
scientific-writing-analysis-SKILL.md  (NOT in repo — using Anthropic plugin instead)

    Running bash install/install.sh after git pull will: - Replace the five items that are in the repo (with backup of previous versions) - Leave _my-private-experiment/ and scientific-writing-analysis-SKILL.md alone

    So you can safely accumulate personal items in ~/.claude/ without worrying about the install script wiping them.

    Naming convention for local-only items¶

    To make local-only items obvious in directory listings (and to avoid future collisions with new repo items), prefix them with _ (underscore):

    ~/.claude/skills/_my-experiment/
~/.claude/agents/_personal-helper.md
~/.claude/commands/_private-shortcut.md

    This isn't enforced anywhere, just a hygiene convention.

    Auditing what's where¶

    Run the audit script to see, at a glance, what's in your ~/.claude/ vs the repo:

    bash install/audit.sh

    Output groups items into three buckets: - In both — these will be replaced on the next install - Local-only — these will be left alone (your personal items) - Repo-only — these will be added on the next install

    This is the safest way to preview a git pull && install before running it.

    Adding a new item to the repo¶

    If you've polished a personal skill / agent / command and want to share it:

    1. Decide if it really belongs in the repo. Apply the principle above.
    2. Copy from ~/.claude/ into the repo working copy. 
      cp -r ~/.claude/skills/<name>/ ~/code/kai-team-claude/skills/
      (Or for an agent / command: copy the single .md file.)
    3. Read through the file for personal references that shouldn't be public — project paths, draft notes, references to specific people who aren't on the team.
    4. Sanitize anything inappropriate. If the item references Kai's voice or team conventions, that's fine; if it references a specific manuscript or review note, redact.
    5. Commit and push with a descriptive message: 
      cd ~/code/kai-team-claude
git add skills/<name>          # explicit path — never `git add -A` or `git add .`
git commit -m "skills/<name>: add <one-line description>"
git push                       # ask before pushing (see git-workflow rule)
    6. Tell the team so they git pull && install.

    Removing an item from the repo¶

    Sometimes a shared item turns out to be too project-specific or has been replaced by an Anthropic plugin (e.g., scientific-writing-analysis). To remove:

    1. git rm -r the item in the repo working copy.
    2. Commit and push with a clear message: 
      git rm -r skills/<name>
git commit -m "skills/<name>: remove (now provided by <plugin/replacement>)"
git push
    3. Note: removing from the repo does not delete it from collaborators' ~/.claude/. Their local copies stay until they manually delete them. That's usually what you want (no surprise deletions on git pull).

    Editing an item that's in the repo¶

    Edit it in the repo working copy at ~/code/kai-team-claude/, then push. Don't edit in ~/.claude/ first — that creates two sources of truth and you'll forget which one is current.

    If you want to test a change locally before pushing:

    # edit the file in ~/code/kai-team-claude/skills/<name>/SKILL.md
cp ~/code/kai-team-claude/skills/<name>/SKILL.md ~/.claude/skills/<name>/SKILL.md
# test in a Claude Code session
# if good, commit and push
cd ~/code/kai-team-claude && git add skills/<name>/SKILL.md && git commit -m "..." && git push

    Sanitization checklist before pushing¶

    Before any git push to a public-ish repo (even private with several collaborators):

    • [ ] No absolute paths like C:/Users/<name>/... — use ~/... or relative paths
    • [ ] No hardcoded API keys, tokens, or credentials
    • [ ] No project-internal manuscript IDs (e.g., journal submission numbers)
    • [ ] No personal email addresses other than the maintainer's
    • [ ] No references to specific reviewers, collaborators outside the team, or private project decisions
    • [ ] References to style profiles and team conventions are fine and expected

    If unsure: open an Issue rather than push, ask Kai.

    Cutting a release (versioning)¶

    The kit uses two version levels — see "How versioning works" on the Updates page for the rationale. As a maintainer you touch both:

    1. Per-plugin semver. When you change a plugin's behaviour, bump its plugin.json version (major.minor.patch) in the same commit. Patch = fix, minor = additive feature, major = breaking change.
    2. Add a changelog entry. Put a dated ## YYYY-MM-DD — <headline> block at the top of the root CHANGELOG.md describing what changed and, briefly, why. This is the single source of truth — the site's Updates page pulls it in at build time via a snippet include, so never duplicate it into docs/.
    3. Roll the CalVer cut when the month turns (or when a batch of changes is meaningfully a new vintage): edit the root /VERSION file to the new YYYY.MM. That's the version people quote when they ask "are we on the same conventions?".
    4. Run the gate before pushing: RUN_HARNESS=1 bash scripts/release_check.sh (INDEX freshness, recipe tokens, canonical-mirror sync, the 00_setup harness, and the mkdocs build). Push only when it's green.
