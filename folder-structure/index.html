    Folder structure — the full layout¶

    Builds on project-structure (the canonical top-level layout) and the where-to-put-things cheat sheet. Where the canonical layout fixes the top-level tree, this page fills in the detail the cheat sheet doesn't have room for: the internal structure of project_management/, multi-paper projects, the grants convention, and the presentations and submissions sub-patterns. Each section states the rule, gives the reason, shows an anchored example, and notes the variant when the default doesn't fit.

    What this adds (and what is already settled)¶

    The canonical layout in project-structure pins down the top-level tree: data/, code/, output/, paper/, literature/, project_management/, and .claude/tmp/ (session scratch). The cheat sheet pins down most artefact homes inside those. Five things go a level deeper here.

    The five gaps:

    1. The internal layout of project_management/ — which subfolders exist, in what order, and when each one is required vs. optional.
    2. project_management/admin/ — what actually lives there. The folder is referenced in the cheat sheet but not described.
    3. Multi-paper projects. What do you do when one research project produces two papers? Per-paper subtrees, shared layout with suffixes, or split into two projects?
    4. Grants — a separate folder convention. Grants behave like a paper project but they are NOT a paper project. Where do they live, and what is the recommended layout for the writeup itself?
    5. Presentations sub-pattern. The cheat sheet says paper/presentations/<venue>_<date>/; the contents and naming inside that folder are not pinned down.

    Each section below states the rule, gives the WHY, shows one anchored example, and notes the variant when the default doesn't fit.

    §1 The internal layout of project_management/¶

    The rule. project_management/ has five canonical subfolders and two top-level files. Create a subfolder only when you have content for it.

    project_management/
├── TODO.md                      top-level: live task list
├── submission_log.md            top-level: one line per submission round (see submissions)
├── submissions/                 one folder per round; see submissions.md
├── experiments/                 one folder per experiment; see experimental-organization.md
├── notes_and_feedback/          dated meeting / call / feedback / decision notes
├── IRB/                         IRB approvals + ethics correspondence; see §2a
└── admin/                       other institutional paperwork (NDAs, contracts, funding letters); see §2b

    Why this layout. Each subfolder maps to a distinct kind of artefact with its own retention policy. Submissions and experiments are PER-EVENT (numbered, dated, immutable once closed). Notes and feedback ACCUMULATE over the life of the project (dated, queryable, see notes-and-feedback). Admin is one-off paperwork. TODOs and the submission log are the only files small enough and live enough to sit at the top of project_management/ directly.

    Skip-the-folder rule. A solo theory project never runs an experiment, so experiments/ should not exist. A project not yet submitted has no submissions/. Create the subfolder the day you have the first file for it. Empty folders are noise.

    §2a project_management/IRB/¶

    The rule. IRB approvals, ethics committee correspondence, and the institutional paperwork around them. Project-level IRBs live here; experiment-specific IRBs live with the experiment per the experimental-organization page.

    Why a dedicated folder. Most projects that touch human subjects collect at least one IRB document, and "where is the IRB letter?" is a real question that comes up two years into a project. A named folder means one answer. IRB-adjacent paperwork (ethics committee questions and answers, amendment filings, expiration extensions) accumulates around the same letters, so co-locating it saves searching.

    Skip-the-folder rule. A project with no IRB never creates this folder. Theory papers, descriptive analyses of public data, and similar projects skip it cleanly.

    §2b project_management/admin/¶

    The rule. Other institutional paperwork that is neither data, nor a submission, nor an experiment, nor IRB, nor a meeting note. Specifically:

    • Funding award letters, grant administrative correspondence, no-cost extension paperwork (the funded paperwork — grant proposals live in their own folder per §4).
    • Co-author contracts, NDAs, data-sharing agreements.
    • Conference / workshop acceptance letters, formal travel reimbursement paperwork relevant to the project.
    • Any other one-off institutional paperwork the project generates.

    Why split this from IRB/. Two reasons. Semantically, "an NDA in a folder called IRB" reads oddly to a co-author looking for an NDA. Practically, IRB is the recurring item that deserves its own name; the other admin paperwork is a thin catch-all that benefits from being kept distinct so neither folder becomes a junk drawer.

    Skip-the-folder rule. Most projects collect a handful of admin documents at most. If admin/ ends up with one file, that's fine — the folder is a name, not a contract that it must fill up. Most projects without external contracts or grants never create it at all.

    §3 Multi-paper projects¶

    Those five subfolders cover one paper cleanly. The harder question is what happens when a project grows a second paper — which is where the per-event discipline above starts to strain, and where the next rule earns its keep.

    The rule. One project = one paper = one shared pipeline. When a project produces a second paper, GRADUATE the second paper into its own project (the exception — a genuinely shared pipeline — is below). The two then share the data via the standard data/raw/ discipline (whoever owns the raw data keeps it; the second project imports the cleaning code per the data-provenance rule). I default to splitting; the shared-pipeline exception is rarer in practice than it sounds when you first hit it.

    Why this default. A two-paper project layout sounds simple in the abstract ("just add paper_B/ next to paper/") and gets confusing fast in practice. code/02_analysis.R belongs to which paper? Are the figures in output/ shared or per-paper? Co-authors who joined for paper B do not need read access to paper A's revisions. The cleanest answer is to take the seam at the project boundary, where the kit's tools (clones, gitignore, submission folders) already work.

    The exception — share-the-pipeline split. When the two papers genuinely share the analysis pipeline (same data, same cleaning, same 02_analysis.R, different write-ups), per-paper subtrees inside ONE project are acceptable:

    project-root/
├── data/                         shared
├── code/                         shared
├── output/                       shared
├── paper_A/                      first paper: paper_A.tex, references.bib, presentations/, revisions/
├── paper_B/                      second paper: paper_B.tex, ...
├── literature/                   shared (one Zotero project per group of papers)
└── project_management/
    ├── submissions/              flat; per-round folder is NN_<journal>_<paper>/
    └── notes_and_feedback/       shared

    The submission folders carry the paper identifier in the name (05_QJE_paperA/, 06_AER_paperB/) so the submission log stays one file. The canonical paper/ becomes paper_A/ + paper_B/ only when both genuinely share the pipeline; otherwise split.

    Anti-pattern. Long-lived branches for the second paper. Branches are for in-flight work, not for parallel write-ups; a branch that lives for a year is a sign the split should have happened.

    §4 Grants — separate folder convention¶

    A grant raises the mirror image of the multi-paper question: it behaves like a paper project but is not one, so it gets the opposite treatment — its own folder, never nested inside the work it funds.

    Scope caveat. This page deliberately stays short on grants. The rule for where grants live is firm; the how to structure a grant proposal internally is light-touch.

    The rule. A grant proposal lives in its OWN folder, outside any research project. Keep grants out of any single research project so they survive when the project moves on.

    Why. A grant is a writing project with its own bibliography, its own panel-interview slides, and its own submission round (the funder is the journal-equivalent). It draws on past research and seeds future research, but its lifecycle does not match any one paper. Mixing it into a paper folder breaks the paper's clean structure; mixing two grants into a single folder loses the per-grant submission history.

    Suggested layout (per grant) — the paper layout, scaled down. Not prescriptive; treat it as a starting point.

    grant_<funder>_<NN>/
├── proposal.tex                  main writeup
├── references.bib
├── output/                       figures / tables for the proposal
├── presentations/                slides for the panel interview, if any
├── project_management/
│   ├── notes_and_feedback/       feedback from mock review
│   ├── IRB/                      if the grant requires ethics paperwork up front
│   └── admin/                    application paperwork, signed forms, funder correspondence
└── literature/                   reading specific to this proposal

    Anti-pattern. Putting a grant folder inside a research project's project_management/. The grant outlives the project; nesting it loses the grant when the project closes.

    §5 Presentations sub-pattern¶

    Presentations raise a different concern from the boundary questions above: not where the project lives, but whether a folder stays portable when you copy it to a co-author or a conference laptop.

    The rule. A talk lives in paper/presentations/<venue>_<YYYY-MM-DD>/, with the deck and all its assets in the same folder so it compiles cleanly.

    paper/presentations/
├── NBER_2026-04-12/
│   ├── slides.tex                or slides.qmd
│   ├── figures/                  copies of the figures used in this talk
│   ├── logo_nber.png
│   └── slides.pdf                compiled output (small enough; gitignore the build dir)
├── AEA_2026-01-05/
│   └── ...

    Why assets sit next to the deck. A talk deck references figures, logos, a photograph the venue asked for. If those live in a separate assets/ sub-folder, the deck breaks when you copy the folder to share it. Co-located assets keep the talk folder self-contained.

    Naming. <venue>_<YYYY-MM-DD>/. Venue is short (NBER, AEA, RESTAT-revise); date is the talk date, not the prep date. Sorting by name then sorts by venue, which is usually what you want when you re-use a talk for a similar audience.

    Skip-the-folder rule. Reuse a deck across two venues by COPYING the folder and editing the copy, not by editing the original in place. The previous venue's deck is the historical record; reusing in place erases what you actually presented.

    Worked example — a complete project tree¶

    Each rule above governs one corner of the tree. Here is how they compose into a single real project, with the skip-the-folder rule visible in what's absent. The default solo-paper project that ran for two years, was presented twice, and is currently at QJE R&R:

    gehring2026narrative/
├── CLAUDE.md
├── README.md
├── data/
│   ├── raw/
│   ├── processed/
│   └── documentation/
├── code/
│   ├── 00_setup.R
│   ├── 01_clean.R
│   ├── 02_analysis.R
│   └── 99_run_all.R
├── output/
│   ├── figures/
│   ├── tables/
│   └── figures_external/
├── paper/
│   ├── paper.tex
│   ├── references.bib
│   ├── revisions/
│   │   └── QJE/
│   │       ├── response_to_referees.tex
│   │       └── referee_reports_formatted.tex
│   ├── presentations/
│   │   ├── NBER_2026-04-12/
│   │   └── AEA_2026-01-05/
│   └── old/
├── literature/
│   └── _wiki/
├── project_management/
│   ├── TODO.md
│   ├── submission_log.md
│   ├── submissions/
│   │   ├── 01_AER/
│   │   ├── 02_QJE/
│   │   └── 03_QJE_revision/
│   ├── notes_and_feedback/
│   │   ├── 2026-03-15_meeting_with_Arne.md
│   │   ├── 2026-04-10_decision_framing_for_intro.md
│   │   └── 2026-05-22_transcript_AEA_session.md
│   ├── experiments/                 (does not exist — no experiment)
│   └── IRB/
│       └── IRB_2024-09.pdf
└── .claude/tmp/

    Notice experiments/ is absent — the project has no experiment, so the folder does not exist. output/figures_external/ exists because one figure is a photograph. revisions/QJE/ exists because the paper is currently at R&R.

    Anti-patterns — the five traps, collected¶

    Each section above flagged its own trap; here they are in one place for a quick pre-flight scan:

    • A project_management/ populated with empty submissions/, experiments/, IRB/, and admin/ folders "in case we need them." Create the folder when you have the first file for it.
    • A second paper started inside the first paper's project as paper2/ without per-paper-subtree (no paper_A/ / paper_B/). Pick the split, don't half-do it.
    • Grant proposals inside a project's project_management/admin/. Grants live in their own folder.
    • Presentation assets in a sibling assets/ folder. Co-locate with the deck.
    • Reusing a talk folder in place for the next venue. Copy the folder; the previous deck is the historical record.
