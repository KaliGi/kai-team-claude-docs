    Literature¶

    The recommended literature workflow for LLM-era research: Zotero as the source of truth for citations, literature/ as the local PDF mirror, a markdown wiki as the LLM-readable layer. Each step is a thin transform that keeps your citation manager honest while making the same papers cheap for Claude to read.

    The pipeline at a glance¶

    Zotero  (citation manager — source of truth for metadata + citekeys)
   ↓  /sync-pdfs   (copies PDFs from Zotero's storage into the project)
literature/<citekey>.pdf
   ↓  /lit-corpus  (PDF → markdown, incremental, SHA-256 tracked)
literature/_wiki/
   ├── index.md          (one-row-per-paper: title, authors, year, abstract, JEL, keywords)
   └── papers/<citekey>.md   (full cleaned text, YAML frontmatter)

    Each arrow runs on demand. Add a paper to Zotero, run /sync-pdfs, the PDF lands at literature/acemoglu2001colonial.pdf. Run /lit-corpus and it appears as literature/_wiki/papers/acemoglu2001colonial.md with the abstract pulled into the wiki index. Both /sync-pdfs and /lit-corpus are incremental — they hash files and skip what hasn't changed, so re-running on a 500-paper library takes seconds, not minutes.

    What goes where¶

    Artefact Location
    PDFs literature/<citekey>.pdf (one file per paper, named by Zotero citekey)
    Markdown corpus literature/_wiki/ (built by /lit-corpus; gitignored — regeneratable from the PDFs)
    Wiki index literature/_wiki/index.md (~400 tokens per paper — abstract + metadata)
    Per-paper markdown literature/_wiki/papers/<citekey>.md (~3000-4000 tokens — cleaned full text)
    Literature-review notes NOT here — those are research artefacts, go in project_management/notes_and_feedback/ (see notes-and-feedback)

    Example file pair: literature/acemoglu2001colonial.pdf + literature/_wiki/papers/acemoglu2001colonial.md. The <citekey> here is the Zotero citation key in authorYEARkeyword form — it is the spine of the whole pipeline, and the citekey convention section below covers how it is generated.

    Why a markdown version of every paper¶

    A typical 25-page econ paper costs around 12,000 tokens to read as a PDF, and Claude has to scan the whole thing every time you ask about it. The markdown wiki produces an index entry of about 400 tokens per paper and a full-text version of about 3,000-4,000 tokens. When Claude is helping with a literature task, it can scan the entire index in one read and pull individual papers' markdown on demand. For a 200-paper library that is the difference between a triage pass costing 2.4 million tokens (200 × 12,000) and one costing 80,000 tokens (200 × 400). Same library, same triage outcome, two orders of magnitude difference in cost.

    The other half of the case is that markdown is grep-able. You can Grep across _wiki/papers/ for "Rubin causal model" or "first stage F > 10" and get hits in milliseconds; you cannot do that against a folder of PDFs without a full text-extraction pass each time. The wiki is the search index your literature folder has wanted all along.

    What the conversion captures and what it loses¶

    PDF→markdown conversion is a lossy transform. Some losses are unavoidable; others depend on which engine you run. Knowing the difference matters because it changes which papers you should also read directly.

    Permanently lost — text can never recover these¶

    These are inherent to going from a layout-rendered document to running text. No engine, present or future, gets them back:

    • Raw figure pixel data — bar heights, scatter cloud shape, RDD discontinuity visuals, event-study confidence bands. Even a perfect caption tells you "the figure shows X" but not "the discontinuity is 0.27 SD wide."
    • Colour-coded series in multi-line plots — which line is treatment, which is control.
    • Network-graph topology (trade networks, citation graphs).
    • Choropleth map shading and exact geographic boundaries.
    • Hand-drawn theory diagrams — game trees, signalling diagrams, model schematics.
    • Visual emphasis in tables — bold coefficients, asterisks indicating the author's preferred specification.
    • Exact figure axis scales when not stated in the caption (log vs linear, truncation).

    When a paper's contribution lives in any of these — a new identification strategy with a striking RD plot, an event-study with sharp pre-trends, a network paper — read the PDF directly. The markdown is for the rest of it (the argument, the methods, the regression numbers).

    Recoverable with a strong engine — lost with the default¶

    These are NOT inherent to PDF→markdown; they depend on the converter. Our current engine (pymupdf4llm) loses them; stronger engines (marker-pdf, docling, Mistral OCR) recover them:

    • Figure captions as discrete blocks. The caption alone is roughly 80% of a figure's informational value for a text reader. Default engine: caption text gets mixed into body. Strong engine: typed Caption: block, queryable.
    • Regression-table cell structure. Coefficient row, SE row, t-stat row, N, R². Default engine: tables mangled, especially wide ones. Strong engine: structured grid, cells preserved.
    • Inline math. Default engine: β = 0.27 (Unicode mush). Strong engine: $\hat{\beta} = 0.27$ (LaTeX, renders properly).
    • Display equations with subscripts intact.
    • Multi-column reading order on two-column journals (JEEA, JPubE), where the default engine sometimes interleaves columns.
    • Footnote-to-anchor linkage ([^3] style), so you can follow citations from body text to the footnote.

    The "engine choice" question — when to upgrade — is below.

    Recoverable with GROBID specifically¶

    GROBID is an academic-paper specialist that parses the bibliography into structured {authors, year, title, venue, doi} entries, which no other tool here does reliably. If you want a .bib generated automatically from each paper's references, it is worth running as a sidecar alongside the main engine; it does not replace the main engine.

    The conversion engine — what /lit-corpus runs¶

    Which losses you actually take depends on the engine you pick, so the engine choice is the practical lever. /lit-corpus ships with three, and the default is chosen to work everywhere rather than to maximise quality.

    Tier Engine flag When Cost
    1 (default) --engine fast Reliable everyday conversion; body text + basic structure Free; CPU ~0.1s/page; no model download
    2 (opt-in) --engine marker Full fidelity: regression tables, LaTeX math, typed figure captions Free, but downloads several GB of models and is heavy on CPU — see the caveat below
    3 --engine mistral Scanned / image-only PDFs (no text layer) ~$0.001/page; requires MISTRAL_API_KEY; free via le Chat for occasional use

    Why fast is the default and not marker. Marker is the quality engine on paper, but it pulls in a multi-gigabyte model stack and, on a CPU-only Windows/Anaconda machine, was observed failing outright with a MemoryError before converting a single page. A default has to work on the machine in front of you, so fast (pymupdf4llm) is the default: it loses table structure and math fidelity, but it runs reliably. If you want marker's fidelity, install it, run --engine marker on a couple of papers, and confirm you get a populated .md before relying on it; if it fails, stay on fast and use mistral for the specific papers whose tables or math you actually need.

    The primary engine auto-falls back to mistral when output is near-empty (<500 bytes), which almost always means a scanned PDF with no text layer. The fallback only fires if MISTRAL_API_KEY is set; otherwise you get the usual "possible scan" warning and can run ocrmypdf first instead.

    In practice: leave the default alone for a normal literature review. Reach for --engine marker only when you specifically need the regression tables and equations parsed AND you have confirmed marker works on your machine. Don't touch mistral unless you're working with old scanned journal archives.

    Citekey convention¶

    The naming pays off here, so the citekey convention is worth getting right once. The Zotero citekey is the spine of the whole pipeline: it names the PDF, names the markdown, and is what your references.bib ends up keying on. Follow authorYEARkeyword (e.g. gehring2025narrative, acemoglu2001colonial). Zotero Better BibTeX generates these directly from a template; configure the template once and every new paper carries a sensible citekey from the moment it lands.

    I keep the keyword slot short and content-bearing — colonial over the_colonial_origins_of_comparative_development. The full title is recoverable from Zotero or from the markdown frontmatter; the citekey is for typing into a .tex file at 11pm.

    The skills involved¶

    • /sync-pdfs — Zotero attachment storage → literature/<citekey>.pdf. Reads your Zotero library's PDF attachments and copies them into the project, renamed to the citekey. Incremental.
    • /lit-corpus — literature/ → literature/_wiki/. PDF-to-markdown conversion + metadata extraction + master index.md generation. Incremental, SHA-256 tracked.
    • pdf-query-recipe — one-shot PDF queries without batch conversion, for when you have a single paper and don't want to run the full pipeline.
    • /lit-review — web search for new papers (different concern: web → corpus → here, not the other direction).
    • bib-audit — pre-submission hallucinated-reference detector. Catches the case where a paper-draft \citep{x} doesn't resolve in the actual .bib.

    Anti-patterns¶

    • PDFs renamed to descriptive titles (Acemoglu Johnson Robinson 2001 - Colonial Origins.pdf). Breaks every citekey-based lookup; the whole pipeline depends on filenames matching citekeys.
    • Literature notes inside literature/. Wrong folder. Lit notes are research artefacts and go in project_management/notes_and_feedback/ per the notes-and-feedback page.
    • Committing literature/_wiki/ to git. It is large, regeneratable from the PDFs, and gitignored by default. Committing it bloats the repo and creates merge conflicts when two clones regenerate independently.
    • Committing PDFs to git. Copyrighted, large, and the wrong layer — Zotero is the source of truth. literature/ is gitignored.
    • Treating the markdown as a replacement for reading the paper. It is a search-and-triage layer. When a paper's contribution lives in a figure or a sharp table, open the PDF.
