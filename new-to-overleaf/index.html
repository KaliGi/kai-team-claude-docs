    New to Overleaf?¶

    Overleaf is a browser-based editor for LaTeX — the typesetting system most economics papers are written in. It's where a lot of co-authors do their actual writing. If you've never used it, this is a short orientation plus the best existing tutorials (Overleaf's own are excellent; no point re-writing them).

    What it is, in one line¶

    Overleaf = write LaTeX in your browser, see the compiled PDF next to it, with several co-authors editing the same document. No local LaTeX install needed to start.

    Do you even need Overleaf? (often no)¶

    Worth saying up front: Overleaf is optional. Everything in a paper compiles locally — latexmk -pdf paper.tex (or your editor's build button) produces the same PDF on your own machine, with no browser and no account. The git- mastered mode keeps paper.tex in git and never touches Overleaf at all.

    The one genuine reason to use Overleaf is track changes — the review/suggesting mode where co-authors mark edits and comments on the prose in the browser and you accept/reject them, the way you would in Word. If your team doesn't need track changes, you can skip Overleaf entirely and compile locally — it's one less moving part. Choose Overleaf for the track-changes review, not out of habit.

    Learn it (external, from Overleaf)¶

    • Learn LaTeX in 30 minutes — the standard beginner tutorial; assumes zero prior LaTeX and walks you through your first document (titles, math, lists, tables, references): https://www.overleaf.com/learn/latex/Learn_LaTeX_in_30_minutes.
    • More tutorials (figures, bibliographies, tables, beamer slides): https://www.overleaf.com/learn/latex/Tutorials.

    How Overleaf fits our workflow¶

    This is the part specific to collaborating with this setup:

    • On Overleaf-mastered papers, the prose lives in Overleaf and everything else (code, figures, the bibliography) lives in git. One person is the Overleaf admin (only the Overleaf project owner can set up the Overleaf↔git sync).
    • The bibliography (references.bib) and figures travel code → git → Overleaf, not the other way. Don't hand-copy files that also live in git — keep git the source of truth. The why and the mechanics are in the manual workflow and common issues.

    Setting it up — the Overleaf owner does this once, first¶

    If a project will use Overleaf, the project owner sets up the Overleaf↔git link, and it's worth doing this first, because it's what connects Overleaf to the GitHub repo — once that link exists, everyone else just clones from GitHub into their folder as usual.

    1. Owner: create (or open) the Overleaf project. In Overleaf, open Menu → Sync → GitHub (or Git) and link it to the project's GitHub repository. (Overleaf's GitHub/Git sync is a paid-plan feature — if Menu → Sync has no Git/GitHub option, the plan doesn't include it; fall back to git-mastered mode and compile locally.)
    2. From then on, syncing Overleaf ↔ git is a manual push/pull through that link — there's no live bridge. The owner (or whoever holds the Overleaf admin role) does the sync so two people don't push conflicting versions.
    3. Everyone else: never set up their own Overleaf↔git link — they clone the GitHub repo into their Dropbox folder (set up your working clone) and edit prose in Overleaf via the browser. Code, figures, and the bibliography still travel code → git → Overleaf.

    (Step-by-step for the routine push/pull cycle is on the roadmap; for now the owner uses Overleaf's own Git/GitHub menu to push and pull.)

    Not every project uses Overleaf — git-mastered papers keep the .tex in git directly, compiled locally. Which mode a project uses is declared in its CLAUDE.md.
