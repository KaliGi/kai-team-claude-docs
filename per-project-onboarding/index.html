    Set up your working clone¶

    Why this page. Joining a shared project means a handful of one-time access steps — folder, repo, bibliography, and (sometimes) Overleaf. Doing them once, in the right order, is what lets everything afterwards "just work". This page is that runbook; whoever set the project up sends it to you with the project-specific details filled in.

    Two roles — make sure you're reading the right one.

    • Setting up the project for the first time (or migrating an existing one to the shared layout)? That's a one-time job for one person — see the setup walkthrough and run /bootstrap-project (new project) or /refactor-structure --migrate-to-multi-clone (existing one). You create the container + your own clone, push main to GitHub, and invite everyone else as collaborators.
    • Joining a project someone else already set up? This page is for you — you receive a few invitations and create your own working clone.

    Once your laptop is set up (see the main README.md for the one-time install), each project you join needs a few separate access invitations.

    Before you start — the accounts and tools you need¶

    Four things must be in place before the clone steps below will work. The first two are the ones people most often miss, and the organizer cannot do them for you:

    1. Your own GitHub account, added as a collaborator on the repo. The repo is private, so without a GitHub account and an accepted collaborator invite you cannot clone it or push to it. Create one free at github.com, then send the organizer your GitHub username/email (below) so they can invite you.
    2. Git installed on your machine — the git program itself. On Windows, install Git for Windows (it also signs you in to GitHub via a browser pop-up the first time); macOS/Linux usually already have git.
    3. The Dropbox container shared with you (accept the share) so the project folder syncs to your machine.
    4. Only if you'll use Claude Code to do the setup: Claude Code installed + a Claude subscription. Two things happen the first time, both normal and worth expecting:
    5. Claude asks permission before it runs a git command. When you ask it to set up your clone, it pauses and asks you to approve each command (e.g. git clone …) — say yes (you can allow git for the whole session). It never runs git silently.
    6. The first clone or push asks you to sign in to GitHub — a browser window opens to log in once. (If it asks for a "password" instead, paste a Personal Access Token, not your account password; the screen stays blank as you paste — that's expected.) It's remembered afterwards.

    What to send the organizer¶

    For each new project, send whoever set the project up the email address you use for each of these services. They'll send invitations against those exact addresses.

    • Dropbox account email
    • GitHub account email (or username)
    • Overleaf account email (only if you'll edit there directly; many people skip this)
    • Zotero account email

    What you'll receive¶

    For each project, expect four invitations:

    1. Dropbox folder¶

    The project's Dropbox folder is the working directory — it contains the LaTeX source, data, code, working drafts, and a CLAUDE.md file that tells Claude Code about the project's conventions and style rules. Once invited, the folder shows up in your Dropbox client and syncs continuously.

    When you start Claude Code from inside the project folder, it automatically reads CLAUDE.md, so the session knows about the project conventions.

    2. GitHub repository¶

    The GitHub repo holds the LaTeX source (*.tex), the bibliography (*.bib), and figures. Whether GitHub or Overleaf is canonical depends on the project's mode — which is declared in the project's CLAUDE.md (## Project mode section). The four modes (Overleaf-mastered, Git-mastered-no-bridge, Git-mastered-with-bridge, Personal-scratch) are defined in principles/project-structure-canonical.md — read that as the source of truth before working in the repo.

    Workflow: - For bibliography updates, follow principles/bibliography-and-literature.md. Do NOT hand-edit the ZOTERO zone of references.bib — those edits are overwritten on /sync-bib. Add citations via Path 1 (just type \citep{...} in .tex), Path 2 (hand-add to the MANUAL zone), or Path 3 (Zotero Connector + /sync-bib). See docs/co-author-onboarding.md for the short version. - For paper text edits, the rule depends on project mode: - Overleaf-mastered: drafting happens locally; the Overleaf admin applies final changes manually in Overleaf. Claude does NOT commit or push .tex content without explicit per-session approval. - Git-mastered: draft directly in the master .tex files; git provides version history. Pushes still ask per principles/git-workflow.md.

    3. Overleaf project¶

    Optional. Many teams keep Overleaf as the writing surface of last resort and have collaborators work in the Dropbox working/ folder. If you are invited to Overleaf, treat it as read-only unless the Overleaf admin says otherwise.

    4. Zotero group library¶

    Each project usually has its own Zotero group library — separate from your personal Zotero. After you accept the invitation, switch to the group library inside a Claude Code session by saying "switch to group library " — whoever manages the project's Zotero library will give you the ID.

    The group library is the source of truth for citations. New citations get added to the group library first, then a Claude Code session converts the entry to BibTeX and appends it to the project's .bib file in the GitHub repo.

    Set up your own working clone (multi-clone projects)¶

    Skip this section if the project's CLAUDE.md has no ## Multi-clone layout block — then you work directly in the shared Dropbox folder per the Quick-start below.

    "But I don't have a clone yet — where do I open Claude Code?" This is the one apparent exception to the open-in-your-clone rule, and it trips every new co-author. You don't need your clone to exist to create it — you create it by cloning from GitHub. So for this one-time setup only, open your terminal (or a Claude Code session) at the container (the shared Dropbox project folder). Once your clone_<XX>/ exists, every session opens inside it as usual. Two accesses must be in place first: the Dropbox container shared with you, and GitHub collaborator access on the repo. (Or just open at the container and ask Claude Code: "set up my working clone, my initials are MC.")

    On multi-clone projects, each co-author works in their own nested git clone inside the Dropbox project folder. The project root is a shared container, not a git repo — there is no "lead" and no canonical root clone, and everyone is equal. You never run git at the root; all your git work happens inside your own clone_<XX>/. Full rationale: principles/project-structure-canonical.md, Multi-clone pattern.

    The single most important fact: cloning does NOT give you the data. data/raw and data/processed are gitignored — the one canonical data copy lives in the parent Dropbox folder. The .data-in-parent marker (step 5 below) makes your clone's scripts find it.

    Two ways to do it — pick one:

    • Ask Claude Code (easiest). Open a session at the container (see the box above) and say: "Set up my working clone — my initials are AW." It runs the commands below for you, pausing to ask you to approve each git command (say yes), and the first git clone triggers the GitHub sign-in described in "Before you start." You stay hands-off after approving.
    • By hand. Run the ~6 commands yourself. Replace AW/aw with your two-letter initials (the ones in the project CLAUDE.md ## Collaborators table). Works the same in Git Bash, PowerShell, or macOS Terminal:
    # 1. Go to the Dropbox project folder
cd "<path-to-Dropbox>/<project>"

# 2. Clone the repo into your per-author folder
#    (someone must have added you as a GitHub collaborator first)
git clone https://github.com/KaliGi/<repo>.git clone_AW

# 3. Enter it, create your branch, and publish it — never work on main
cd clone_AW
git checkout -b AW/exp-sandbox
git push -u origin AW/exp-sandbox   # publish the branch; enables plain `git push`/`git pull` later

# 4. Tell the pipeline that data lives in the parent folder
touch .data-in-parent          # PowerShell: New-Item .data-in-parent -ItemType File

# 4b. Drop the "this is your copy, you can't break it" note into your clone
#     so the foreign files don't alarm you (and gitignore it — it's personal).
cp ../<path-to-kai-team-claude>/templates/clone-readme.md ./README.md
#    (Or just ask Claude Code: "add the clone README to my clone.")

# 4c. Install the paper-PDF hook, so that every time you pull a merge into
#     your clone the container's paper/ folder gets a freshly compiled PDF of
#     main (one obvious place to grab the current paper at submission time —
#     see "The current paper PDF at the container" below). Then run it once to
#     populate the container the first time.
cp ../<path-to-kai-team-claude>/templates/hooks/post-merge-paper .git/hooks/post-merge
chmod +x .git/hooks/post-merge
sh .git/hooks/post-merge            # first-time populate (safe to re-run)
#    (Or just ask Claude Code: "install the paper-PDF merge hook in my clone.")

# 5. Verify: run the setup script — the banner must show your branch
#    and the rawdata/processed paths must point at ../data/
#    (Windows often doesn't have Rscript/python on PATH — use the full
#    executable paths from the project CLAUDE.md if the bare name fails.)
Rscript code/00_setup.R
#    Stata:  "C:\Program Files\StataNow19\StataSE-64.exe" /e do code/00_setup.do
#    Python: python code/00_setup.py

    From now on, every session (Claude Code, R, Stata) starts inside clone_AW/ — never in the parent. Your code, paper edits, and exhibits live on your branch and reach the team via git push + pull request.

    The current paper PDF at the container¶

    Once the hook (step 4c) is installed, the container holds a paper/ folder with the compiled PDF of main. Every time anyone pulls a merge into their clone (git merge origin/main), the hook recompiles main's paper and drops the fresh PDF there. This is the one place to grab the current paper — e.g. at submission time — without opening anyone's clone. It holds only the PDF, not the sources or outputs: every clone already has those from main, so the container deliberately doesn't duplicate them.

    A PAPER_README.md sits next to it: do not edit there — the PDF is regenerated on the next merge and is not in git; all real work happens in your clone and reaches main through a PR. The hook is best-effort: if your machine has no LaTeX or the paper can't bare-compile (e.g. it uses \includepdf), it skips silently and leaves the previous PDF rather than breaking your merge — so refresh happens on whichever machine can compile main cleanly.

    Working in your clone — the two-step session setup¶

    Why this matters: Claude Code acts on the folder you open it in. Open it in your clone and your work lands on your branch; open it in the parent and it would touch the shared container directly. So a co-author session is always:

    1. Open Claude Code in your clone folder (clone_AW/). Desktop app: Open folder → pick clone_AW/. Terminal: cd clone_AW && claude. This is where your git work happens (your branch).
    2. Add the parent folder only if you need Claude to read or add shared files at the project root — the shared data/, literature/, or project_management/. Desktop app: Add another folder → pick the project root. You do NOT need this just to run your code — your scripts already reach the shared data/ on their own through the .data-in-parent re-anchor; step 2 is only for when Claude itself should read/add a shared file (e.g. "save this PDF to literature/").

    What Claude Code asks when you add the parent. It will ask whether the added folder is a git working directory or just a folder to read/write. Answer "just a folder" (a plain added directory) — the parent is the shared container, not a git repo, so there's no git there to manage. Your git stays entirely in your clone_<XX>/. (If you accidentally say it's a git directory, nothing breaks — the container has no .git, so Claude simply finds nothing to act on.)

    Two cautions when the parent is added: (a) only read or add shared resources (data/, literature/, project_management/) — never reach into another person's clone_<XX>/, that's theirs; (b) anything tracked or structural (code, paper, reorganizing folders) goes through your branch and a merge, not by editing the parent directly. Reading shared files and adding literature/notes is fine; the one thing to flag to the team first is overwriting shared data/processed/ (two people can clobber it).

    When your branch produces its first exhibit: copy kai-team-claude/templates/exhibits-note.tex to your clone root and add every exhibit to it as you create it (finding-style section title, a 2-4 sentence interpretation, consistent wording, a transition sentence, \FloatBarrier after each — all scaffolded in the template). Compile with latexmk -pdf exhibits-note.tex from the clone root. This one PDF is how the team reviews your branch's work; full rules in the co-author handbook §2.6 step 6.

    Keeping your branch current (do this every few days, and always before opening a PR): your clone is pinned to your branch, so plain git pull only fetches your own branch — it will say "up to date" even when main has moved on for weeks. Pull main in explicitly:

    git fetch origin
git merge origin/main          # brings the team's merged work into your branch
# resolve any conflicts, then: git push

    Notes: - Your clone syncs via Dropbox like everything else — unpushed work is backed up. Do NOT mark it Dropbox-ignored and do NOT create junctions or symlinks inside it. - If you are a disciplined daily-pusher and prefer a clone outside Dropbox entirely, that variant is supported — see the canonical spec ("Placement"). Be aware: Dropbox does not back that clone up. - One-time at project bootstrap (whoever sets the project up, once): clone_*/ in the root .gitignore, the CLAUDE.md multi-clone block, GitHub collaborator access. It's a chore, not an authority.

    Quick-start: your first Claude Code session on the project¶

    1. Open a terminal and cd into the project's Dropbox folder — or into your clone_<XX>/ clone if the project is multi-clone (see the section above).
    2. Pull the latest content for the project's mode:
    3. Git-mastered project: git pull — in your own clone on multi-clone projects; at the Dropbox project root only on single-clone projects (or in the github-sync/ sub-folder if the project uses that legacy mirror layout).
    4. Overleaf-mastered project: there is no pull step from a Claude Code session — the canonical source is Overleaf. The Overleaf admin's latest manual application of edits arrives via Dropbox sync. Check paper/ for the newest date-stamped PDF.

    If unsure which mode applies, read the ## Project mode section of the project's CLAUDE.md. The four modes are defined in principles/project-structure-canonical.md. 3. Start Claude Code: claude. 4. The first thing Claude Code does is read CLAUDE.md — wait for that to finish. 5. You can now ask things like: - "Read the introduction and tell me what it argues" - "What's on the TODO list right now?" - "Add this paper to our bib file" (paste a DOI or paper title) - To switch to the project's Zotero group library, say: Use zotero_switch_library with library_id="<NUMBER>" and library_type="group" (Whoever manages the project's Zotero library will tell you the group ID.)

    Troubleshooting: "Rscript is not recognized" / R not installed¶

    The step-5 verification fails for two different reasons that look the same:

    • R is installed but not on PATH (the default on Windows — the R installer does not add itself). Use the full path instead of Rscript:
    "C:\Program Files\R\R-4.4.3\bin\Rscript.exe" code/00_setup.R

    (Adjust the version number to whatever sits under C:\Program Files\R\.)

    • R is not installed at all. Install from https://cran.r-project.org/ — pick the latest 4.4.x release. You do NOT need RStudio for the setup check; plain R is enough. After installing, use the full path above.

    The same logic applies to python: if the bare name fails, use the full path from the project CLAUDE.md (on Kai-team Windows machines that is the Anaconda install, e.g. C:\ProgramData\anaconda3\python.exe).

    Project-specific notes¶

    Anything project-specific (target journal, current revision status, naming conventions, co-author preferences) lives inside the project's own CLAUDE.md file, not here. The file in this repo is for the general per-project workflow that applies across all projects.
