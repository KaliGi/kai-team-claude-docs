    Data provenance — raw + cleaning live IN the project¶

    Every replication package must contain the raw data AND the code that cleans it. Importing a cleaned X.dta from another project of yours — even copying its cleaning do-file alongside "for reference" — breaks the chain. A replicator who only has this project must be able to get from the original survey or API export to every analytic file. That is the rule.

    This is the AEA Data Editor and Social Science Data Editors line on what a replication package is. It is not a house preference.

    Where things go (AEA-aligned)¶

    • data/raw/ — raw data files, flat, named clearly so each file is obviously paired with its documentation (MiningSurvey_2024_raw.dta, acled_kenya_2018-2024.csv). The AEA Data Editor's examples are typically flat (data/raw/cps0001.dat). Subfolders by source are also accepted — especially useful when one source ships many files (the AEA template separately notes openICPSR's 1000-file-per-directory cap, an archive limit rather than a structure recommendation).
    • data/documentation/ — codebooks, questionnaires, data-availability statements, dataset-level READMEs. One folder for all per-dataset documentation. Match the filenames so the pairing is obvious: MiningSurvey_2024_codebook.pdf ↔ MiningSurvey_2024_raw.dta.
    • code/01_clean.{R,do,py} — the canonical script that loads raw, applies every transformation, and writes the analytic file(s) to data/processed/. One per language. If a project has multiple data sources, sections inside 01_clean handle each — not a separate cleaning script per source.
    • data/raw/SOURCES.md — one line per raw file: where it came from, when, version/commit if relevant, access terms.

    "I want to use data from another project"¶

    Common case: project A produced a cleaned dataset; project B wants to use it. The easy-but-wrong move is to copy A's data/processed/X.dta into B and treat A's cleaning code as a reference. That violates the rule — B is no longer self-contained.

    The right pattern:

    1. Open a feature branch in B (<initials>/add-survey-data) so the integration is isolated and reviewable before it touches main.
    2. Copy A's raw into B's data/raw/, flat, named consistently with B's other raw. Copy the matching documentation into B's data/documentation/.
    3. Bring the new processing code in as a standalone scratch script on the branch (e.g. code/_exploratory/exp_survey_clean.do), run it, verify it produces the expected data/processed/ output.
    4. Integrate the working logic as a section of B's canonical code/01_clean.{R,do,py} — and delete the standalone scratch script. The merge target is one canonical cleaning file per language; the scratch script is a temporary scaffold, not part of main.
    5. Update data/raw/SOURCES.md with origin project + version/commit + date + access terms.
    6. Run end-to-end, verify, merge.

    "Copy the cleaning code as read-only reference" does not satisfy the rule. The cleaning must actually run in this project.

    Edge cases¶

    • PII / proprietary, but fits on disk. Raw goes in data/raw/ (gitignored where appropriate); provenance in SOURCES.md; the README carries a data-availability statement (how to obtain the data, access terms, ethics approvals). Cleaning code stays in code/.
    • Cannot live locally at all (TB-scale climate reanalysis, restricted-access registry data that the team is licensed to use but not to redistribute in any form). No data/raw/ copy; instead code/00_access.{R,do,py} documents or automates the fetch from the licensed source, and SOURCES.md + the README's data-availability statement carry the access path. The "raw + code in the project" rule applies to whatever portion can move — the access script is the chain's first link.
    • Live-updating sources (an API repulled on a schedule; UCDP / ACLED / WB refreshes). The downloaded snapshot in data/raw/ is dated; the fetch script lives in code/ and is part of the chain; SOURCES.md records the access date and the pinned source version. A re-pull becomes a new data/raw/ file alongside the previous one.
    • Pure theory / simulation. The rule applies trivially: data/raw/ may be empty or absent; processing collapses to the simulation script in code/. The chain "code → outputs" is still self-contained.
    • A published, frozen, citable third-party archive treated as your "raw" (rare but legitimate). The exception applies only if all three are true: (i) the archive has a persistent identifier (DOI, openICPSR study number, Dataverse handle); (ii) the exact version used is immutable and re-fetchable by a third party through that identifier; (iii) the archive is not authored by anyone on the current paper's author list. A sibling project of your own fails (iii); a working-paper replication package on a personal site that you might re-edit fails (ii); an ICPSR study with a fixed version DOI passes all three.

    In the multi-clone (leaderless) model¶

    This rule applies to the container, not each clone. In the multi-clone leaderless layout, data/ lives at the container root and is shared across clones via the .data-in-parent re-anchor — so "into the project's data/raw/" means into the container's single shared data/raw/, not a per-clone copy. The canonical code/01_clean.{R,do,py} lives inside each clone (git-tracked, merges to main like any other code); every co-author runs the same cleaning against the same shared raw.

    Why this rule exists¶

    The AEA Data Editor's policy is short and absolute: every figure, table, and in-text number must reproduce from the deposited package without manual intervention. If your data starts inside another project, you have put a manual intervention at the very first step — "go ask project A's owner for X.dta." A replicator (or a referee, or your future self) cannot do that. The rule rules out the easy version of that defect.

    How to check¶

    /audit-reproducibility and /audit-exhibits walk back from the manuscript's numbers, to outputs, to 02_analysis, to 01_clean, to data/raw/. A data/processed/X.dta with no producing code in code/ is an ORPHAN at the data layer — the same defect class as an orphan exhibit, gated on the same rule.
