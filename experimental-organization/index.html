    Experimental organization¶

    Running an experiment means producing two distinct kinds of artefact, and they belong in two distinct places. The planning lives under project_management/experiments/<NN>/: pre-reg, IRB, randomization script, design memos, pilot notes. The data lives under data/raw/ and data/documentation/ — the actual responses and their codebooks. The split is the load-bearing idea on this page; the rest is just where each thing goes inside it.

    Why split this way: planning artefacts are sensitive (IRB applications quote personal information; pre-regs name hypotheses you haven't yet tested) and they belong in the gitignored project_management/ tree. Data artefacts feed the canonical analysis pipeline through 01_clean and 02_analysis, so they belong in data/. Mixing the two (putting the response data inside project_management/experiments/, or the pre-reg inside data/documentation/) breaks both halves: the analysis pipeline cannot find its inputs, and sensitive planning artefacts leak into the git-tracked layer.

    The two homes¶

    Artefact Where Why
    Pre-registration project_management/experiments/<NN>/ Planning artefact; sensitive
    IRB approval (this experiment) project_management/experiments/<NN>/ Specific to this experiment's design
    IRB approval (project-level / institutional master) project_management/IRB/ Not experiment-specific; lives with other IRB paperwork (folder structure §2a)
    Randomization script project_management/experiments/<NN>/ Design code; runs once to set up, then frozen
    Pilot memos ("what we learned") project_management/experiments/<NN>/ Planning artefact
    Survey instrument drafts project_management/experiments/<NN>/ Planning artefact
    Pre-analysis plan (PAP) project_management/experiments/<NN>/ Planning artefact
    Collected response data data/raw/ Canonical data flow
    Pilot response data data/raw/pilot_<…>.csv (default — cleaned by 01_clean like main data) OR project_management/experiments/<NN>/pilot_data/ if it stays internal only Two valid homes; pick by whether the pilot data feeds the analysis pipeline
    Randomization assignment file data/documentation/ NOT raw data — it documents the experimental design's realisation (who got which treatment); paired by name with the raw response data
    Codebook (REQUIRED) data/documentation/ Canonical home for every dataset; codebooks live with the data

    A reader who already has the rule can stop here and skip to the worked example. The sections below explain what goes inside each home and the codebook rule that is genuinely load-bearing.

    What goes in project_management/experiments/<NN>/¶

    Everything you produce while designing the experiment, plus the artefacts that document that design as it ran. The folder is gitignored, so co-author contracts and sensitive planning material are safe to keep here.

    project_management/experiments/01_mining_RCT/
  preregistration.md           (or the filed pre-reg PDF — both are fine)
  IRB_approval_2025-09.pdf     (experiment-specific approval)
  design_memo.md               (why this design, which alternatives considered)
  randomization.do             (the script that runs once to set up)
  pap.md                       (pre-analysis plan)
  survey_instrument_draft_v3.docx
  pilot_memo_2025-11.md        (what the pilot taught us)

    The randomization script lives here, NOT in code/. The reasoning: code/ is the analysis pipeline you re-run any time the inputs change. The randomization script ran once, produced the assignment file, and is then frozen forever. Re-running it after data collection would invalidate the experiment. Keeping it out of code/ makes the freeze visible.

    Project-level institutional paperwork (the institutional master IRB, NDAs, funding paperwork) does NOT live here — that goes to project_management/IRB/ or project_management/admin/ per the folder-structure conventions. Only paperwork specific to this experiment lives in this folder.

    What goes in data/raw/ and data/documentation/¶

    The collected response data and everything you need to read it correctly. Same rules as any other research dataset (see data-provenance): raw/ is read-only, documentation/ carries the codebook and any data-side metadata.

    data/raw/
  MiningRCT_2026_responses.dta
  pilot_2025-11_responses.csv     (if cleaned via 01_clean; otherwise keep it under
                                   project_management/experiments/01_mining_RCT/pilot_data/)

data/documentation/
  MiningRCT_2026_codebook.md
  MiningRCT_2026_randomization_assignment.csv
                                  (who got which treatment — documentation of the
                                   experimental design's realisation, not raw response data)
  pilot_2025-11_codebook.md

    The randomization assignment file is the subtlest call: it lives in documentation/, not raw/. It is NOT a raw observation — you constructed it deterministically from the randomization script. It documents the experimental design as it actually ran (which subject IDs ended up in treatment vs. control), and that documentation pairs by name with the raw response data the analysis pipeline reads in.

    The codebook rule — load-bearing¶

    Every experimental dataset must have a codebook. There are no exceptions, and the timing matters: the codebook is needed FOR the pre-registration, which means it has to exist before data collection starts.

    I'd reach for stronger framing than usual on this rule because we've seen the failure mode often enough. The chain is:

    1. The pre-registration specifies which variables you will collect and what each one measures. That commitment is the whole point of pre-registering.
    2. To write that section of the pre-reg honestly, you need to know your variable definitions in advance — which is exactly what a codebook is.
    3. Therefore the codebook is drafted BEFORE the pre-reg is filed and lives in data/documentation/ from that moment, even when data/raw/ is still empty.
    4. The pre-registration in project_management/experiments/<NN>/preregistration.md explicitly links to data/documentation/<experiment_id>_codebook.md. The link in both directions makes the pairing impossible to lose.

    The "codebook lives with the data" half of the rule is shared with every other dataset; the "drafted before the pre-reg" half is what makes experimental work special. Together they enforce that you cannot file a pre-registration whose variable definitions you haven't yet written down.

    Naming convention¶

    Per-experiment subfolder is <NN>_<experiment_id> (e.g. 01_mining_RCT, 02_narrative_priming). The <NN> keeps experiments sortable by order in which they ran; the <experiment_id> keeps them recognisable when you go looking for one.

    Data and codebook filenames carry the same <experiment_id> slot:

    • data/raw/<experiment_id>_responses.<ext>
    • data/documentation/<experiment_id>_codebook.md
    • data/documentation/<experiment_id>_randomization_assignment.csv

    So 01_mining_RCT gives you MiningRCT_2026_responses.dta paired with MiningRCT_2026_codebook.md. The pairing is by name; tools and humans can both find the codebook for a given dataset without checking a separate registry.

    What does NOT live here¶

    A few things look like experiments but are not, and putting them under project_management/experiments/ muddles the planning archive:

    • Methodology robustness probes — "what happens if we cluster at the village level instead of the district level?" That is an analytic sensitivity check, not experimental work. It lives in code/02_analysis.<ext> as a section. The clue: the data is already collected; you are only varying the analysis.
    • Grant proposals that fund the experiment — those live in their own folder, outside the research project entirely. See the grants page for the why.
    • A figure showing the experimental design (the treatment-assignment diagram, the timeline) — that is a paper exhibit and lives in output/figures/ if a script produced it, or output/figures_external/ if it is hand-drawn. The fact that the figure ILLUSTRATES the experimental design does not make it experimental work; it makes it a paper exhibit.
    • Day-to-day fieldwork logistics — partner emails, enumerator scheduling, accommodation receipts. Those go in project_management/notes_and_feedback/ with the date prefix, not under experiments/. experiments/ is the design archive, not the operational log.

    Worked example — a full project shape¶

    A multi-author RCT project, one year in, currently at QJE first-round submission:

    mining_RCT_2026/
├── CLAUDE.md
├── README.md
├── data/
│   ├── raw/
│   │   ├── MiningRCT_2026_responses.dta
│   │   └── pilot_2025-11_responses.csv
│   ├── processed/
│   │   └── MiningRCT_analysis.dta
│   └── documentation/
│       ├── MiningRCT_2026_codebook.md
│       ├── MiningRCT_2026_randomization_assignment.csv
│       └── pilot_2025-11_codebook.md
├── code/
│   ├── 00_setup.do
│   ├── 01_clean.do
│   ├── 02_analysis.do
│   └── 99_run_all.do
├── output/
│   ├── figures/

├── paper/

│   └── revisions/
│       └── QJE/

    ├── TODO.md
    ├── submission_log.md
    ├── submissions/
    │   └── 01_QJE/
    ├── experiments/
    │   └── 01_mining_RCT/
    │       ├── preregistration.md
    │       ├── IRB_approval_2025-09.pdf
    │       ├── design_memo.md
    │       ├── randomization.do
    │       ├── pap.md
    │       ├── survey_instrument_draft_v3.docx
    │       └── pilot_memo_2025-11.md
    ├── notes_and_feedback/
    │   ├── 2026-02-12_meeting_with_partner_NGO.md
    │   └── 2026-03-08_call_with_enumerator_lead.md
    ├── IRB/
    │   └── IRB_institutional_master_2024.pdf
    └── admin/
        └── partner_NGO_data_sharing_agreement.pdf

    What is and isn't here is the point of the example. The design timeline figure lives in output/figures_external/, not under experiments/. The institutional master IRB lives in project_management/IRB/, not under experiments/01_mining_RCT/ (the experiment-specific approval does live there). The partner NGO meeting note lives in notes_and_feedback/ with a date prefix, not under experiments/. None of those distinctions matter the day you make them; all of them matter the day a co-author joins and tries to find something.

    Anti-patterns¶

    • Codebook saved inside project_management/experiments/. Breaks the canonical "codebooks live in data/documentation/" rule and means the analysis pipeline cannot find the variable definitions for the data it is loading.
    • Randomization script in code/. It is not part of the analysis pipeline; it ran once to set up. Putting it in code/ invites someone (or 99_run_all.do) to re-run it, which would invalidate the experiment.
    • Re-running the randomization script after data collection. The randomization assignment is now part of the experimental design's history, not a regenerable artefact. Treat the script as frozen the day data collection starts.
    • Methodology robustness probes labelled as "experiments". A sensitivity check on cluster level is not an experiment; it is an analysis section. Calling it an experiment muddles both folders and the conceptual chain (the pre-reg becomes meaningless if every analysis variant counts as a new experiment).
    • Day-to-day fieldwork logistics in experiments/. Partner emails and enumerator schedules belong in notes_and_feedback/ with date prefixes. experiments/ is the design archive, not the daily operational log.
    • A pre-registration filed before the codebook exists. The pre-reg names the variables; the codebook defines them. Filing in the wrong order means the pre-reg's variable list is provisional — and the whole point of pre-registering is that it isn't.
