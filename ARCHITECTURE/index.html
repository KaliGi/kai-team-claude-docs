    Architecture — how this repo is organised and how it ships¶

    Audience: Kai, future-Kai, co-authors who clone this repo, and any Claude Code session reading the repo to orient itself. Last substantive revision: 2026-06 (staleness pass after the Sprint 1+2 hardening; plugin count, docs set, and workflow commands updated to match the tree).

    This doc explains what lives where, how things activate in a session, and how content is shared across machines and co-authors. If something here is out of date, it's the doc that's wrong, not the code — fix it.

    1. The two-layer model¶

    Every workflow capability in this repo sits on one of two layers:

    Layer Made of Portable? Co-author needs …
    Skills (design-time guidance) Pure markdown — SKILL.md, references/, templates/ Yes — works in any Claude Code session, any OS, no runtime deps Nothing beyond Claude Code itself
    Pipelines (skill + hard gates) A skill + Python scripts that enforce mechanical checks Files always portable; execution needs Python on the user's machine Python installed locally (Anaconda or equivalent)

    Important: the skill is the load-bearing piece. Gate scripts are enhancements layered on top. If a co-author has the skill but no Python, the skill still produces good output — they just don't get the mechanical guardrails (lockdown audit, slide-count check, etc.). Skills never gate behind script execution.

    2. Three distribution mechanisms¶

    We use all three, on purpose, for different jobs:

    Mechanism What it syncs Direction Trigger
    git (GitHub remote at KaliGi/kai-team-claude, private) Committed state of the repo Across people (you ↔ co-authors) git push / git pull, manual
    Dropbox (~/Dropbox/GitHub/kai-team-claude/) Entire working tree including uncommitted edits Across YOUR devices (laptop ↔ desktop ↔ phone) Continuous, automatic, background
    install.sh / install.ps1 Repo → ~/.claude/ on a single machine Local, repo → user-level Claude config Run once after git pull

    The three are independent. GitHub doesn't know or care about Dropbox; Dropbox doesn't know about git; install.sh doesn't know about either — it just copies files from a local repo clone.

    A future improvement (deferred): change install.sh to create junctions/symlinks instead of file copies. Junctions mean ~/.claude/skills/<x>/ and the team-repo working tree are the same directory at the OS level — edits in either location appear in both, eliminating the drift problem we hit in May 2026. Not urgent; doesn't change co-author UX.

    Top-level skills/ vs plugins/<bundle>/skills/¶

    • Top-level skills/ = bulk-installed via install.sh. Everyone on the team gets all of these. Use this for items every teammate should have (basic writing skills, figure tools).
    • plugins/<bundle>/skills/ = selectively installable via /plugin install. Use this for items where some teammates want them and others don't (specialised workflows, opinionated pipelines).

    Currently 7 skills live at top-level and 6 bundles live under plugins/. New workflow-specific bundles should be wrapped as plugins so co-authors can pick and choose; only universally wanted items go top-level. docs/INDEX.md is the generated catalog of everything installable — regenerate with scripts/generate_index.py whenever a skill or command is added or its description changes.

    4. Where things live on a co-author's machine after install¶

    ~/.claude/                          [USER-LEVEL Claude Code config]
├── CLAUDE.md                       global user instructions
├── CONTEXT.md                      reference material (folder layouts, conventions)
├── skills/                         copied from team-repo skills/ by install.sh
├── agents/                         copied from team-repo agents/
├── commands/                       copied from team-repo commands/
├── principles/                     copied from team-repo principles/
├── templates/                      copied from team-repo templates/
└── plugins/                        managed by Claude Code; selective install
                                    (talks, coord, r/stata-research-workflow, …)

    <paper-repo>/                       [PER-PAPER repo, e.g., ~/Dropbox/virality/]
└── _presentations/state/           [PER-PAPER pipeline state — NOT in kai-team-claude]
    ├── paper_extract.csv           lockdown CSV (every numeric claim)
    ├── paper_extract_addendum_v*.csv  fix-pass extensions
    ├── identification.md           named estimator + 10 hostile Q
    ├── figure_inventory.md         use-as-is vs rebuild decisions
    ├── defensive_appendix_priorities.md
    ├── outline.md
    └── venues/<venue>/
        ├── deck.tex / .pdf
        ├── adversarial_review_v*.md
        └── lessons.md              post-talk debrief

    Confidentiality boundary: - ✅ Generic infrastructure (skills, agents, gates, templates) → kai-team-claude/ (team-shared) - ❌ Paper-specific data (coefficients, deck.tex, reviews) → that paper's OWN repo (paper-author-shared)

    The team repo never contains unpublished paper-specific data. The boundary is enforced by where files live, not by access controls.

    5. Activation — what happens in a new Claude Code session¶

    You open Claude Code (any working directory, VS Code or app)
        ↓
Claude Code reads ~/.claude/ at startup:
  • Loads CLAUDE.md (global instructions, always in context)
  • Indexes SKILL.md descriptions from ~/.claude/skills/* (metadata only — not full content)
  • Registers ~/.claude/commands/*.md as available slash commands
  • Registers ~/.claude/agents/*.md as invocable agents
        ↓
You type a natural-language request:
  "draft a 60-minute seminar talk on the virality paper"
        ↓
Claude matches against skill descriptions, sees research-presentation triggers
        ↓
Claude reads the full SKILL.md (only now, on demand)
        ↓
SKILL.md points at:
  • its plugin's scripts/ + agents/ via ${CLAUDE_PLUGIN_ROOT} (resolves to
    the installed plugin folder on any machine)
  • per-paper state convention: <paper-repo>/_presentations/state/
        ↓
Claude proceeds through Phase 0 → A → B → … → F
        ↓
At Phase F (pre-ship adversarial gate), Claude invokes:
  "<python>" "${CLAUDE_PLUGIN_ROOT}/scripts/lockdown_grep.py" <deck.tex> <csv> …
        ↓
Gate exits 0/1 → Claude reads the report → loops fix-pass until clean

    You don't "activate the pipeline." The skill triggers from natural language. Gates are invoked when the workflow reaches them. Slash commands are available the whole time (/academic, /bootstrap-project, etc.) and are entered with /.

    6. Common workflows¶

    Edit a skill or pipeline gate¶

    cd ~/Dropbox/GitHub/kai-team-claude
# edit skills/<name>/SKILL.md  or  plugins/<bundle>/scripts/<script>.py
git diff                                 # eyeball changes
git add skills/<name>/SKILL.md           # explicit paths — never `git add -A`
git commit -m "skill X: ... (why)"
bash scripts/release_check.sh            # pre-push drift guard (must pass)
git push                                 # propagate to GitHub for co-authors

# Then sync the change into your live ~/.claude/
bash install/install.sh                  # bulk re-copy (overwrites local edits with repo state)

    If you edited inside ~/.claude/skills/<x>/ instead of the repo (the drift trap), copy back to the repo before committing: 

    cp -r ~/.claude/skills/<x>/. ~/Dropbox/GitHub/kai-team-claude/skills/<x>/

    Add a new pipeline (e.g., grants, papers, presentations)¶

    Two patterns:

    (a) Top-level folder — bulk-installed for everyone via install.sh. Good for items every teammate uses. No live example anymore: the last one (talks-pipeline/) was converted to a plugin in May 2026, and new pipelines should default to pattern (b).

    (b) Plugin bundle (the default — matches all 6 current bundles): 

    kai-team-claude/
└── plugins/
    └── grants/
        ├── .claude-plugin/plugin.json
        ├── skills/grant-writing/
        ├── agents/grant-intake-agent.md
        └── scripts/budget_check.py
    Add to .claude-plugin/marketplace.json. Co-authors install with /plugin install grants@kai-team-claude. Good for opinionated workflows not every teammate wants.

    Share with a new co-author¶

    They run: 

    git clone https://github.com/KaliGi/kai-team-claude.git ~/Dropbox/GitHub/kai-team-claude
cd ~/Dropbox/GitHub/kai-team-claude
bash install/install.sh           # macOS/Linux — or install.ps1 on Windows

    They now have all top-level skills/agents/principles/templates. Plugins are opt-in via /plugin install (the README's persona table says which bundles fit which role).

    If they have their own personal ~/.claude/skills/<x>/ that collides with a team skill, install.sh backs it up to ~/.claude/_backup_<timestamp>/ before overwriting. They recover the personal version if needed.

    Switch laptops¶

    # On new laptop, after Dropbox finishes syncing:
cd ~/Dropbox/GitHub/kai-team-claude
git pull                                 # in case anything was committed since
bash install/install.sh                  # populates a fresh ~/.claude/

    The repo is the portability mechanism. No special "claude-portability" infrastructure needed.

    7. Conventions worth keeping¶

    • Per-paper data never lands in this repo. Paper-specific lockdown CSVs, decks, reviews, lessons go in each paper's own repo at <paper-repo>/_presentations/state/. The team repo is generic infrastructure only.
    • Skills are markdown-only at heart. When a skill needs Python, the Python lives in plugins/<bundle>/scripts/ and the skill's SKILL.md references it via ${CLAUDE_PLUGIN_ROOT} — never a hardcoded install path. Skills themselves stay portable to Python-less machines.
    • Slash commands work without plugins. Anything in ~/.claude/commands/<name>.md becomes a /name command. Plugins are needed only for selective distribution.
    • Don't auto-commit. Edits land in the working tree; you review with git diff before pushing. This catches the "paper-specific data accidentally in team repo" failure mode.

    8. Decisions still open (June 2026)¶

    • Convert install.sh from copy-based to junction-based? Lower priority now: scripts/release_check.sh + the generated docs/INDEX.md catch the drift the junctions were meant to eliminate. Revisit only if drift recurs despite the guard.
    • Wrap any other top-level skills as plugins (e.g., tikz-figure, real-data-figure, adversarial-review)? Only if a co-author has explicitly said they want a subset.
    • Move kai-writing into a plugin too? Probably not — every co-author wants it; bulk install is right.
