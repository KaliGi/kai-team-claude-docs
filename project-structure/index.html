    What goes where — the project structure¶

    Why a fixed structure at all. When several people share a project, the single biggest source of friction is not knowing where things live — so figures get lost, two people invent two data/ folders, and "where's the latest draft?" becomes a daily question. A shared, predictable layout removes that friction.

    This is a working solution, not the solution. The goal here is not a structure that is theoretically perfect for economists — it's one where several people stay coordinated with low friction and it works in practice. If your team prefers a different arrangement, fine; what matters is that everyone uses the same one and that it keeps you out of the failure modes in why collaboration is hard. The layout below is the one this kit is built around, and the tools assume it.

    The layout¶

    project-root/                  (the Dropbox folder; in multi-clone, a container)
├── CLAUDE.md                  project conventions Claude Code reads on entry
├── README.md                  human-facing: what this project is
├── data/
│   ├── raw/                   ORIGINAL data — read-only, never edited
│   ├── processed/             analysis datasets, built from raw by code
│   └── documentation/         codebooks, data dictionaries (git-tracked)
├── code/                      00_setup · 01_cleaning · 02_analysis · 99_run_all
├── output/                    figures/ · tables/ · maps/  (generated by code)
├── paper/                     paper.tex · references.bib · dated PDFs · old/ · presentations/
├── literature/                reference PDFs — LOCAL ONLY (gitignored)
├── project_management/        TODO, notes, submission log
└── temp_claude/               scratch (gitignored)

    (On multi-author projects each person works in a nested clone_<XX>/; data/ stays once at the container — see why collaboration is hard.)

    R --> T["temp_claude/ — scratch (gitignored)"]

    What belongs in each folder — and why¶

    Folder What goes here Why
    data/raw/ The original data, exactly as obtained It's the one thing you can't regenerate. Read-only, so a script can never corrupt your ground truth.
    data/processed/ Analysis datasets built from raw by code Derived = reproducible; if it's lost, you rebuild it. Keeps raw pristine.
    data/documentation/ Codebooks, variable dictionaries Small text that benefits from version control, so it's git-tracked while the heavy data isn't.
    code/ Numbered scripts (00_setup→99_run_all) One ordered pipeline anyone can run top to bottom; 00_setup owns all paths so nothing is hard-coded.
    output/ Figures, tables, maps — generated Every exhibit is reproducible from code/; nothing here is hand-made and unexplained.
    paper/ paper.tex, references.bib, dated PDFs The manuscript and its bibliography in one place; old drafts in old/.
    literature/ Reference PDFs Copyrighted + large → kept local, never committed.
    project_management/ TODOs, notes, submission log The admin layer, separate from the scientific work, so it doesn't clutter code or paper.
    temp_claude/ Throwaway scratch A clearly-disposable place so scratch never pollutes the real folders.

    The deeper rationale (the two-layer model, the canonical-file rule) is in the ideas behind it; the full machine-readable spec is the canonical structure reference.

    Turning a messy project into this¶

    Most real projects don't start this clean. Here's the before→after — and the one rule that comes first.

    flowchart LR
    subgraph BEFORE["A typical messy project"]
        direction TB
        b1["Paper final v3/"]
        b2["Data and stuff/"]
        b3["analysis_FINAL.do"]
        b4["refs.bib"]
        b5["figures everywhere"]
    end
    subgraph AFTER["After: the shared layout"]
        direction TB
        a1["paper/  (paper.tex, references.bib)"]
        a2["data/  (raw, processed, documentation)"]
        a3["code/  (00_setup … 99_run_all)"]
        a4["output/  (figures, tables)"]
    end
    BEFORE ==>|"BACK UP FIRST, then restructure"| AFTER

    Back up before you restructure — always. Restructuring renames and moves files; a mistake mid-move can lose work. So first: commit everything to git on a clean branch, AND/OR copy the whole project folder once (e.g. my-project_backup_2026-06-15/). With a backup, every later step costs nothing if it goes wrong.

    Where you run this — and the order. A messy existing project has no clones yet, so you do the restructuring in a Claude Code session opened at the project folder itself (the existing messy root), not in a clone_<XX>/. The sequence is:

    1. Open Claude Code at the project folder → back up → restructure.
    2. If it's a multi-author project, --migrate-to-multi-clone then turns that folder into the shared container and helps you create your own clone_<XX>/.
    3. From then on, you open sessions inside your clone_<XX>/ for daily work (see set up your working clone). So the one-time restructure happens at the root; everyday work happens in your clone.

    Then, three ways to get from messy to clean — pick what you're comfortable with:

    • With Claude Code (recommended): run /refactor-structure. It first shows a read-only plan (what it would rename/move), you confirm each step, and only then does it act — it never deletes. For multi-author projects, /refactor-structure --migrate-to-multi-clone then sets up the leaderless container + clones.
    • By hand: make the folders above and move files into them following the "what belongs where" table; then git add the new paths.
    • Starting fresh (new project): run /bootstrap-project — it scaffolds the whole layout + a CLAUDE.md for you. (Or create the tree by hand.)

    Whichever you choose, the destination is the same layout — so the next person who opens the project already knows where everything is.
