    Why structure matters (even solo)¶

    This page is tool-agnostic. It's about how to organize an empirical research project so it stays sane over years — no AI, no special software assumed. The toolkit automates a lot of it later, but the principles below stand entirely on their own, and they're worth following even if you work alone in a plain folder.

    Why structure at all — even working solo¶

    The person most likely to need your project organized is future-you, six months from now, reopening it for a revision. A predictable structure means you can answer, instantly: where's the raw data? which script made Figure 3? which file is the current draft? Without that, every reopening starts with archaeology. So the payoff isn't bureaucratic tidiness — it's that the project stays reproducible and resumable by you, and later by anyone else.

    The principles (the part that doesn't depend on any tool)¶

    1. Separate raw from processed, and never edit raw. The data exactly as you obtained it is the one thing you can't regenerate. Keep it read-only; build everything else from it with code. If a cleaning step was wrong, you fix the code and re-run — the ground truth is untouched.
    2. Code is the source of every exhibit. Each figure, table, and number in the paper should come from a script you can re-run, not from a one-off you can't reconstruct. "Reproducible" just means: delete output/, run the code, get it back.
    3. One canonical file per artefact. No analysis_v2.do, final_FINAL.tex. One 02_analysis file, one paper.tex — history lives in version control (below) or dated archive copies, not in the filename.
    4. A runnable pipeline. Number your scripts so the project runs top to bottom (00_setup → 01_cleaning → 02_analysis → 99_run_all), with one setup file owning all paths so nothing is hard-coded to your machine.
    5. Write down what isn't obvious. A short codebook / data dictionary and a README turn "what was this variable again?" into a lookup.

    That's the whole core. The concrete folder map that implements it is what goes where; the deeper rationale is the ideas behind it. A standard, reproducible structure is also exactly what a replication package needs — so if you work this way, the package is almost free.

    Required vs. recommended¶

    Not everything here carries equal weight, and it's worth being honest about which is which — so nobody feels bossed into preferences, and nobody treats a genuinely load-bearing rule as optional.

    Required — break these and something real goes wrong:

    • Never overwrite or edit raw data. It's the one thing you can't get back.
    • To share work, commit and push it to git. Saving (Dropbox) is not sharing; the canonical record is git. (Solo with no git, this doesn't apply.)
    • One writer per file at a time (on a team) — two people editing the same file means one silently loses their work.
    • Exhibits trace to code. A number or figure you can't regenerate from a script isn't reproducible — and reproducibility is the credibility floor.

    Recommended — sensible defaults you can adapt:

    • The exact folder layout and names (what goes where) — a working solution, not the only one; what matters is everyone uses the same.
    • Keeping clones inside Dropbox, using Overleaf, using Claude Code or the toolkit, the specific multi-clone setup — all genuinely optional choices. Pick what fits; the required rules above hold either way.

    When in doubt: the required list is short on purpose. Everything else is a default you're free to change.

    Working alone vs. with others — and where git comes in¶

    Working solo, the principles above plus a tidy folder are most of what you need. Version control (git) is helpful even then — it gives you a timeline you can roll back and a record of why each change happened — but you can get a long way with disciplined folders and the occasional dated backup.

    The calculus changes the moment more than one actor edits the project — and today that's not just co-authors:

    • Co-authors edit in parallel. Without version control, two people changing the same file means one silently overwrites the other (the classic Dropbox "conflicted copy").
    • AI agents — Claude Code, Codex — make many edits quickly. That's a huge speed-up, but it's also a lot of changes to a lot of files. You want each one to be a reviewable diff you can inspect and undo, not a silent mutation. Git is what turns "the AI changed twelve files" into "here's exactly what it changed, keep or revert each."

    So the rule of thumb:

    You're working… What you need
    Alone, by hand the folder principles above; git optional but nice
    Alone, with an AI agent the principles + git — so every agent edit is a reviewable, revertible diff
    With co-authors (± agents) the principles + git + a collaboration setup so parallel work merges instead of clobbering

    The more hands on the project — human or AI — the more git earns its keep. The folder principles are the foundation either way; git is what lets several actors build on that foundation at once without stepping on each other. How that collaboration setup works is Working together; why the AI agents are safe to let loose on a git-backed project is how Claude Code thinks.
