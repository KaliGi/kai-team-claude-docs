    How it works — skills, processes & gates¶

    People keep asking the same fair question: when the toolkit "does a process" — like iterating over a figure before showing it to me — what is that, actually? Is it a program running in the background? Where does it live on my computer? Once you see how a "process" is built, you can read it, change it, and add your own.

    The short version: everything here is just files on disk — readable text, plus a few small scripts. Nothing runs in the background. A "process" is either a set of instructions Claude follows when you ask, or a script that fires automatically on an event.

    The building blocks¶

    Six things, and they're all plain files you can open:

    • Skill — a folder with a SKILL.md (Markdown instructions) plus, optionally, bundled scripts/ (Python/R) and reference docs. Triggering a skill means Claude reads the instructions and follows them — running any bundled script along the way.
    • Command — a skill you invoke by name with a leading slash (/review-paper). It's the same thing as a skill, just with an explicit handle.
    • Agent — a Markdown spec describing a focused sub-worker (e.g. a bibliography auditor). A skill can dispatch several agents to work in parallel.
    • Plugin — a bundle of related commands + skills + agents (e.g. academic-workflow). Installing one gives you everything inside it.
    • Principle — a shared rules file (the writing, citation, and git conventions in principles/). Skills and agents read these, so fixing a rule once propagates everywhere.
    • Hook — an actual executable script wired into settings.json that runs automatically and deterministically on a tool event (for example, the raw-data guard runs before any write to data/raw/ and asks first).

    Two ways a process is enforced — and the difference matters¶

    There are two levels of enforcement:

    How it's encoded Guarantee
    Soft (a rule) instructions in a skill's Markdown Claude usually does it — it's an instruction the model follows, not a law
    Hard (a gate / hook) an actual script that runs no matter what deterministic — runs every time its event fires

    Most of the toolkit is soft: a skill says "do it properly" and Claude follows. That's flexible and covers the vast majority of work. A hard gate (a hook, or a deterministic check script) is what you reach for when "usually" isn't good enough — safety rails (never overwrite raw data) or a step you want guaranteed to run.

    You can promote a soft rule to a hard gate when it earns it: take an instruction the model sometimes skips, and wire it as a hook so it always fires. This is how the toolkit hardens over time.

    A worked example: iterating over a figure before you see it¶

    You ask for a figure. Behind the scenes the figure skill's instructions say: build it → render it → look for the obvious problems (a legend overlapping a bar, unreadable labels, a wrong unit) → fix them → repeat once or twice → then show you. So what reaches you is a checked draft, not a raw first attempt, and you don't waste time flagging mistakes the agent could see itself.

    Today that loop is soft — it lives as instructions in the figure skill, and Claude follows them when you invoke it. To make it hard (guaranteed, and automatic for any figure, not just ones made via the skill), you'd add a hook that fires after a figure file is written and runs the check itself. That upgrade — auto-firing the self-check — is on the roadmap; see Self-correcting figures for the patterns you can use today (including a global instruction that turns the self-check on everywhere).

    Where it all lives on your computer¶

    Plain files, all version-controlled in the repo and copied to your machine by the install script — nothing is a compiled black box:

    • ~/.claude/skills/<name>/ — skills (SKILL.md + any scripts)
    • ~/.claude/agents/ — agent specs
    • ~/.claude/principles/ — the shared rules
    • plugins — managed by Claude Code's own registry (the slash-commands)
    • settings.json — where hooks are wired to events

    You can open any of them, read exactly what they do, and edit them. That's the point: the "processes" aren't magic — they're instructions and small scripts you own.
