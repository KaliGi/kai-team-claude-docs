    How merging works (and when to coordinate)¶

    Collaborating on code and text comes down to one question: when can two people work at once, and when do they have to take turns? The answer is in how git merges. This page builds it up from the bottom.

    Git's unit is the line¶

    Git stores text as lines and merges line by line. It does not understand meaning — it only asks: did you two change the same lines, or different lines?

    This has a practical consequence you've probably felt:

    • In code (R, Python, Stata) you naturally write one statement per line, so git's line-unit lines up with logical units. Two people editing different statements are editing different lines, and git merges them cleanly.
    • In LaTeX a whole paragraph is often one long line, so two people editing the same paragraph are editing the same line — git sees a clash even if they changed different sentences. The fix is a real best practice: write .tex with one sentence per line (semantic line breaks). Then git's line-unit works for prose too, and a clash shrinks to the actual sentence in dispute instead of the whole paragraph.

    Three things that happen when two people's work meets¶

    1. Clean merge — different lines — safe and automatic¶

    flowchart LR
    Anc["common version"] --> A["Ann edits line 3"]
    Anc --> B["Ben edits line 9"]
    A --> M["git keeps BOTH"]
    B --> M
    M --> R["line 3 = Ann's,<br/>line 9 = Ben's<br/>no conflict"]

    Different lines (or different files) → git takes both, automatically. You edit the abstract, your coauthor edits the appendix → both land, even straight on main.

    2. Textual conflict — same line — git stops you (safe)¶

    flowchart LR
    Anc["line 3: original"] --> A["Ann: line 3 = version A"]
    Anc --> B["Ben: line 3 = version B"]
    A --> C{"same line,<br/>two versions"}
    B --> C
    C --> H["git STOPS and marks a conflict;<br/>a human picks. Annoying, never lost."]

    The same line changed two ways → git refuses to guess, marks a conflict, and a human chooses. This is the safe kind: git won't let it slip past you.

    3. Logical conflict — different lines, but broken — git stays SILENT (the danger)¶

    flowchart LR
    Anc["code uses variable: income"] --> A["Ann (line 10):<br/>rename income to inc"]
    Anc --> B["Ben (line 80):<br/>new code uses income"]
    A --> M["different lines →<br/>git merges cleanly,<br/>NO conflict flagged"]
    B --> M
    M --> X["line 80 now breaks:<br/>income no longer exists.<br/>git never warned you."]

    Different lines, but one change breaks the other's assumptions → git merges with no warning, and the result is broken. Git reads lines, not meaning. This is the one to watch for — the conflicts git shouts about are the safe ones; the silent break is the dangerous one.

    "Both add something after line 150 — whose goes first?"¶

    Two cases, and the difference matters:

    • Different actual lines (Ann adds after line 150, Ben after line 160) → git keeps both, in file order — line 150's addition, then line 160's. No conflict.
    • The same spot (both add right after line 150) → git does not pick an order. It raises an "add/add" conflict at that point, shows both, and a human decides the order (or keeps both).
    flowchart LR
    Anc["line 150"] --> A["Ann adds X right after 150"]
    Anc --> B["Ben adds Y right after 150"]
    A --> M{"same insertion point"}
    B --> M
    M --> H["add/add CONFLICT —<br/>a human chooses the order.<br/>git will not decide."]

    Important: the order you merge in does not auto-decide the result. Merging Ann-then-Ben vs Ben-then-Ann doesn't make one "win" — git still surfaces the clash and whoever resolves it chooses. In the pull-request flow this is tidy: the first PR merges cleanly; the second PR is now behind main, so its author pulls main, hits the add/add conflict, and picks the order before merging.

    So when can you work in parallel?¶

    Situation What git does What you do
    Both ADD independent things (a new analysis block, a new figure script in a new file, different paper sections) merges cleanly, and it works work in parallel — nothing special
    Both edit the SAME lines (same paragraph, same function) conflict — git stops you resolve by hand, or agree who does it. Annoying, not dangerous
    One changes a SHARED FOUNDATION (data cleaning, variable definitions, the early analysis others build on) often merges silently, then breaks downstream coordinate: one person at a time, announce it, everyone re-pulls and re-runs after. git will not protect you here

    The pattern: independent additions are the safe parallel case; shared-foundation changes must be serial and announced — because that's exactly the silent, logical break git can't catch.

    Branches and pull requests: where a human catches what git can't¶

    flowchart LR
    BR["your branch<br/>(work in isolation)"] --> PR["pull request"]
    PR --> RV["review:<br/>a human reads the meaning"]
    RV --> MG["merge to main"]

    Branches keep each person's half-finished work off main. The review step is where a person catches the logical conflict git can't see — "wait, you renamed the variable my new code uses." Git merges the text; the review merges the meaning. That is the real reason the workflow routes everything through a PR instead of letting everyone push straight to main.

    Resolving a conflict, step by step¶

    First figure out which kind you have — they live in different systems and you fix them in different places:

    • A git conflict — on your tracked files (code, paper) when you pull main into your branch and the same lines were changed two ways. You fix it in your own clone, locally (not on GitHub).
    • A Dropbox "conflicted copy" — only on the shared container files that live in Dropbox and are not in anyone's git clone (data/processed/, literature/, project_management/). Two people edited the same shared file at once, so Dropbox kept both and renamed one. You fix it in Dropbox.
    • The silent logical break (different lines, one breaks the other) is not flagged by either system — a person catches it. Covered last.

    A git conflict¶

    You see it after git merge origin/main (or when opening a PR): git prints CONFLICT and lists the files.

    Say: "I have a merge conflict — show me each one, explain both sides, and propose a resolution." Claude reads the markers, tells you what each side changed and why, proposes the merged text, and (once you approve) stages and commits. You never touch the marker syntax. If you want to bail out: "abort the merge" puts you back where you started.

    1. git status — lists the conflicted files.
    2. Open one. The clash is wrapped in markers: 
      <<<<<<< HEAD          (your branch)
your version
=======
the incoming version (from main)
>>>>>>> origin/main
    3. Edit that region to what you want — keep yours, keep theirs, or combine — and delete all three marker lines.
    4. git add <file> to mark it resolved. Repeat for each file.
    5. git commit (finishes the merge), then git push.
    6. Wrong turn? git merge --abort returns you exactly to the start — nothing lost.

    Either way it happens in your clone, locally — that's where the files and the merge live. GitHub's web editor can handle a trivial one-file conflict, but local is the normal path, and Claude Code makes it painless. So no: a git conflict is not something you can only fix "on GitHub."

    A Dropbox conflicted copy¶

    Dropbox leaves a second file next to the original, named like TODO (Ann's conflicted copy 2026-06-16).md. Nothing is lost — both versions are sitting there.

    Say: "Dropbox made a conflicted copy of <file> — diff it against the original, merge the two into one, then delete the copy." Claude shows the differences, merges them, and removes the stray file.

    1. Open the original and the "(conflicted copy)" file side by side.
    2. Copy any edits that exist only in the conflicted copy into the original.
    3. Save the original and delete the conflicted-copy file.
    4. Unsure what changed? Dropbox's Version history on the original shows the timeline.

    This only ever happens on the shared container files. To prevent it: give each shared file an owner, edit it one person at a time, or — for anything that benefits from history — keep it in git instead of the plain container.

    The silent logical break¶

    Neither git nor Dropbox flags this one (different lines, but one change breaks the other's assumptions). A person catches it — usually at PR review, or when a script suddenly errors. The fix isn't mechanical: re-pull, re-run, and talk to whoever changed the shared foundation so you both build on the new version. That's exactly why foundational changes are coordinated up front rather than merged blindly.
