    Git¶

    Read this once, before any setup guide, if you've never used git or GitHub. Nothing here requires installing anything; after it, the install guides read as steps instead of incantations. (New to the terminal or Claude Code? Each has its own page in this section.)

    The whole workflow in one paragraph¶

    Your project lives in a Dropbox folder, like always. Two things are added on top. First, git — a version system that lets you take numbered snapshots of your work ("commits") and keeps every snapshot forever, so paper_v7_final_FINAL.tex filename gymnastics disappear: there is ONE file, and the history lives behind it. Snapshots are shared through GitHub (a website that hosts the project's history), so co-authors exchange work as reviewed, deliberate packages instead of silently overwriting each other in Dropbox. You never need to master git — you need ~10 concepts and 5 habits (below), and an assistant like Claude Code can handle the actual syntax while you approve each step. It's a fast assistant, not autopilot.

    The concepts (each with the economist's translation)¶

    Term What it means for you
    repository ("repo") The project's shared folder plus its full edit history — a Dropbox folder that also remembers every draft ever made.
    clone Your personal, complete copy of a repository, kept in sync with the shared original on GitHub. Every project has exactly ONE repo — the project root, every clone_<XX>/ folder, and GitHub's copy are all clones of it. Nobody creates a "second repo" for a co-author; they get another clone.
    commit A numbered draft snapshot with a one-line note — paper_v7 without you managing the numbering. You can always return to any commit.
    push Upload your snapshots to GitHub so co-authors can get them. Saving alone shares nothing — this is the #1 surprise.
    pull Download co-authors' snapshots into your copy. Do it before you start working.
    branch A parallel working draft — like a "robustness-checks version" of a do-file — that cannot disturb the main version until it's reviewed.
    main The one version guaranteed to compile: the journal-submission copy. You never edit it directly.
    pull request (PR) Asking the team to referee your branch and fold it into main — peer review for code and text.
    merge The step that brings branches together: combines two branches' commits into one history. Automatic — unless both touched the same lines (next row). Merge combines text; it does not check conventions. The PR review is where conventions get checked.
    merge conflict Two people edited the same lines; git shows both versions and asks a human to choose. Annoying, never fatal.
    gitignored Files on a "never goes into git" list (.gitignore): data, PDFs, private notes. Git acts as if they don't exist, so they can't leak.
    terminal / CLI A window where you type commands instead of clicking. See docs/terminal-101.md — 10 minutes.
    PATH The list of folders your computer searches when you type a program's name. "X is not recognized" usually means: close and reopen the terminal, or the program isn't installed.
    markdown (.md) A plain-text file with light formatting. Open in any editor, or read it nicely rendered on github.com.
    Claude Code An AI assistant living in the terminal. It reads the project's rule file (CLAUDE.md) on every start and asks before doing anything risky.
    token The unit your Claude subscription meters — like mobile data. Pasting documented commands is nearly free; asking Claude to figure out a setup conversationally burns hours of it. Hence: copy-paste the documented blocks.
    Personal Access Token (PAT) A generated stand-in for your GitHub password. When git asks for a password and you paste it, the screen stays blank — that's normal; press Enter.
    MCP server A small bridge program that lets Claude Code talk to an outside service (e.g. Zotero). Install once, forget.
    Node.js / npm The runtime Claude Code is built on, and its installer. Install once in Step 1, never think about it again.

    The five habits (all you actually need)¶

    1. Pull before you start. git pull — get the team's latest before editing. (One command, or ask Claude: "pull the latest".)
    2. Save ≠ Commit ≠ Push. Save (Ctrl-S) protects against a crash. Commit creates a snapshot. Push shares it. All three, in that order, make work safe AND shared.
    3. Branch before editing. Never work directly on main. Ask Claude: "make a branch for the robustness tables".
    4. Commit at every clean checkpoint, push at the end of every session. Your own branch — push freely; that's your backup.
    5. When anything feels wrong: stop, don't improvise — run git status, or ask Claude "what's the state here?", or email Kai with the exact message. Almost nothing here is unrecoverable if you stop and ask before improvising — improvised "fixes" (and force-pushes) are the only real danger.

    Why the team works this way (the 60-second logic)¶

    Dropbox alone can't say which version of the code produced Figure 3, or let two people edit the same file without silently overwriting each other. Git alone can't hold gigabytes of data or sync it instantly. So the system uses both, each for what it's good at: Dropbox carries the files (especially data — one canonical copy, never duplicated), GitHub carries the meaning (who changed what, what was reviewed, what is production). Every rule in the handbook follows from that split — the full reasoning, with diagrams, is in docs/concepts.md.
