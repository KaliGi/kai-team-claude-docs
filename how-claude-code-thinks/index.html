    How Claude Code thinks (so you know what to expect)¶

    Why this matters. Most frustration with AI tools comes from a wrong mental model — expecting magic and getting a literal-minded assistant, or expecting a chatbot and getting something that can actually change your files. This page gives you an accurate picture of what Claude Code is, so your expectations match reality. No overpromising: knowing the limits is what lets you use it well.

    What it actually is¶

    Claude Code is an assistant that runs in a folder on your computer and can do three concrete things, with your permission:

    1. Read the files in that folder (and ones you point it at).
    2. Run commands — git, R, Python, LaTeX — the same ones you'd type yourself.
    3. Edit files — make the change, not just describe it.

    That's the whole superpower: it's not a chat window that gives advice, it's something that can do the work in your project. Everything else follows from those three.

    Chat vs. a "harness" — the distinction that trips people up¶

    If the only AI you've used is a chat window (claude.ai, ChatGPT), the key shift is this: a chat can only talk back. You paste text in, you get text out; it never touches your computer. Claude Code is a harness — software that wraps the same underlying model and gives it hands: it can open your files, edit them, and run commands, right where your project lives.

    Chat (claude.ai) A harness (Claude Code, Codex)
    Sees your files no — only what you paste yes — the folder you open it in
    Changes files / runs code no yes, with your approval
    Good for quick questions, drafting in the window doing the actual work in your repo

    The word "harness" is borrowed from the idea of a harness on a working animal: it doesn't make the model smarter, it lets it pull the cart — act on your machine instead of just describing what to do. The trade for that power is the permission step: because it can act, it asks before anything consequential (next section). It is not autopilot.

    The three things to internalize¶

    flowchart TD
    F["The folder you open it in<br/>= its whole world"]
    P["It asks permission<br/>before changing things"]
    M["No memory between sessions<br/>unless it's written down"]

    1. It acts on the folder you open it in. This is the single most important fact. Claude Code's "world" is the folder you start it in. Open it in your clone_<XX>/ (your personal copy of a shared project — explained in Working together; ignore the term for now if you're working solo) and your work lands there; open it at the shared container and it would touch shared files. This is why the collaboration setup insists you open it in your own clone — it's not bureaucracy, it's how the tool is wired. (See why collaboration is hard.)

    2. It asks before doing anything consequential. Editing files, running commands, pushing to git — you approve these. You're never one typo away from disaster; there's a checkpoint. You can tell it to stop at any point, and local changes are easy to roll back (git keeps your history). The one thing that isn't a free undo is something already pushed and merged to the shared main — that's why pushes ask first. Treat the approval prompts as a feature, not friction: glance at what it's about to do.

    3. It has no memory between sessions — unless it's written down. Close the session and it forgets everything. What persists is what lives in files: most importantly a CLAUDE.md in the project, which it reads at the start of every session. That's how a project teaches Claude its conventions ("we use R and tidyverse", "this paper is Overleaf-mastered", "never edit raw data"). If you want it to remember something, the answer is usually "put it in CLAUDE.md", not "tell it again".

    What it's good at, and where to be careful¶

    Good at Be careful with
    Boilerplate, refactors, "do this 40 times" Anything it can't verify — it can state a wrong fact confidently
    Remembering rules so you don't have to Numbers and citations — check them like a referee would
    Driving git/LaTeX/R you'd have to look up Big irreversible actions — read the diff before approving
    First drafts you then sharpen Treating its output as final — it's a strong first pass, not a verdict

    The honest summary: it's like a fast, tireless, occasionally overconfident RA. It will save you real time, and it will sometimes be wrong in a way that sounds right. The workflow around it — approvals, git history, reading the diff — exists precisely so that "sometimes wrong" is cheap to catch and undo.
