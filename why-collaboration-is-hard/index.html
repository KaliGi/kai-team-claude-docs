    Why collaboration is hard (and what we do about it)¶

    Where to start. This is the conceptual page — the why behind the collaboration workflow. If you're on a team already using this, you can skip straight to the co-author quickstart. If you're sizing this up for your own team, you're in the right place. New to git? The terms clone, branch, commit, repo are defined in the 10-minute primer — or just read on and trust the conclusions; the mechanics come later.

    Collaborating on a shared paper — text, code, data, and figures, all changing at once across several people and machines — has a handful of failure modes that every team hits. The point of this page is to name them, because the whole structure exists to make exactly those failures impossible or cheap to undo. In short, the bad days it prevents are:

    • lost edits (two people save the same file; one version quietly wins),
    • "which version is current?" (paper_final_v3_REALLY.tex),
    • "it works on my machine" (code that depends on one person's paths/data),
    • drifting data copies, and no real project-wide history.

    If the structure ever feels like overhead, it's almost always preventing one of these. The rest of this page walks through them and the options for solving them.

    These aren't new problems — they're the general challenges of organizing a research project, amplified. Keeping raw data safe, knowing which file is current, making results reproducible: every researcher faces these alone. Collaboration doesn't add a different category of problem — it takes the same ones and makes them harder, because now several people and machines change the same project at once. So the collaboration workflow isn't a separate discipline; it's the same discipline, scaled up with a few extra guardrails.

    The problem¶

    Here is what actually goes wrong, in roughly the order teams hit it:

    • Silent overwrites. Two people edit the same file; Dropbox keeps the last save and quietly makes a "conflicted copy" of the other. Hours of work vanish into a file nobody opens.
    • "Which version is current?" paper_final_v3_KG_REALLY_final.tex. When there's no single source of truth, everyone hedges by copying, and the copies multiply.
    • "It works on my machine." Code that depends on one person's folder paths or one person's data download. Nobody else can reproduce the table.
    • Data duplication and drift. The 4 GB raw dataset gets copied into everyone's folder. Then someone re-cleans their copy and the numbers stop matching.
    • No real history. Dropbox versioning is per-file and shallow. You can't ask "what changed in the whole project between the submission and now?"

    A good setup has to beat all of these at once — fixing one by making another worse (the usual trap) isn't good enough.

    What we actually want¶

    Five things, and the tension between them is the whole design problem:

    1. Everyone has the files locally and backed up automatically.
    2. No one can silently overwrite someone else's work.
    3. One canonical copy of the data — never N drifting copies.
    4. Full project history you can read, diff, and roll back.
    5. It has to work for people who don't know git — the structure can't assume everyone is a power user.

    Dropbox is great at (1) and terrible at (2) and (4). Git is great at (2) and (4) and indifferent to (1). Neither alone gives you all five. The options below are really different ways of combining them.

    The options¶

    Option A — Everyone works in a local git clone outside Dropbox¶

    Each person git clones the repo to a normal folder on their laptop. Git handles merging; Dropbox isn't involved.

    flowchart TD
    GH[("GitHub<br/>main — the shared truth")]
    A["Ann's laptop<br/>~/projects/paper (git clone)"]
    B["Ben's laptop<br/>~/projects/paper (git clone)"]
    A -- "push / pull" --> GH
    B -- "push / pull" --> GH
    GH -. "no automatic backup<br/>of unpushed work" .-> X{{"if you forget to push,<br/>it's only on your laptop"}}

    Honest assessment: this is the "correct" software-engineering answer and it nails (2), (3), (4). It fails (1) and (5). Unpushed work isn't backed up — forget to push before your laptop dies and it's gone. And it asks everyone to live in git fluently, which is a real barrier for co-authors who just want to edit prose. Great for an all-engineer team; rough for a mixed one.

    Option B — One shared Dropbox folder that is itself a git repo¶

    The intuitive move: put the git repo straight into the shared Dropbox folder so everyone sees the same files and gets Dropbox backup.

    flowchart TD
    GH[("GitHub<br/>main")]
    D["Shared Dropbox folder<br/>= ONE git repo (.git at root)"]
    A["Ann edits here"] --> D
    B["Ben edits here"] --> D
    D -- "Dropbox syncs the .git folder too" --> CONFLICT{{"two people, one .git →<br/>corrupted history,<br/>HEAD flips under your feet"}}
    D --> GH

    This looks like it gives you everything — and it's the trap. A git repo's internals (.git/) are a live database. When Dropbox syncs that between two people working at once, it corrupts. Worse, one person switching branches flips the shared HEAD (git's pointer to "which branch you're on right now"), so a teammate's next commit silently lands on the wrong branch. This is not hypothetical — it's exactly the incident this kit was hardened against. Option B fails (2) and (4) in the most damaging way: it looks fine until it isn't.

    Option C — Shared Dropbox container + one git clone per person inside it¶

    This is what we use. The Dropbox folder is a plain container — it is not a git repo. It holds the single shared data copy and one nested git clone per person (clone_AB/, clone_CD/, …). Each person works only in their own clone; git lives inside each clone, never at the shared root.

    flowchart TD
    GH[("GitHub · main<br/>owned by no one")]
    subgraph DBX["Shared Dropbox container (NOT a git repo)"]
        DATA["data/ — one canonical copy<br/>literature/ · project_management/"]
        CA["clone_AB/ (Ann's git clone)<br/>on branch AB/..."]
        CB["clone_CD/ (Ben's git clone)<br/>on branch CD/..."]
    end
    CA -- "push → PR → merge (anyone)" --> GH
    CB -- "push → PR → merge (anyone)" --> GH
    GH -- "pull" --> CA
    GH -- "pull" --> CB
    CA -. "scripts read shared data via<br/>.data-in-parent re-anchor" .-> DATA
    CB -. ".data-in-parent" .-> DATA

    How this hits all five:

    • (1) local + backed up — every clone lives inside Dropbox, so unpushed work is still synced and recoverable. You get git and Dropbox backup.
    • (2) no overwrites — you only ever edit inside your own clone. Two people can't touch the same working file, and merges happen deliberately through git, not by Dropbox guessing.
    • (3) one data copy — the heavy data sits once in the container; each clone's scripts reach it through a tiny .data-in-parent marker instead of copying it.
    • (4) full history — each clone is a real git repo; main on GitHub is the shared, diffable, roll-back-able truth.
    • (5) works for non-git people — Claude Code can drive the git parts; the human just stays in their own folder. The manual workflow spells out the by-hand path for those who want it.

    The cost — there's exactly one, and we don't hide it — is below.

    Why "leaderless", and why that matters¶

    Option C has a tempting shortcut: make one person's clone the "main" one at the container root and have everyone else nest under it. We deliberately don't. There is no lead and no root clone. The container root is just a folder; every co-author's clone_<XX>/ is equal; main lives on GitHub, owned by no one.

    Two reasons. First, social: a paper's co-authors are peers, and baking a "lead's canonical copy" into the folder structure creates a hierarchy that doesn't reflect how the work actually happens. Second, technical: the moment the root is someone's clone (a .git at the root), you've quietly slid back into Option B's failure mode — a shared repo whose HEAD can flip. Keeping the root a plain container makes that specific incident — the shared .git two people fight over — structurally impossible: there's no shared repo at the root to corrupt. (Each person's own clone_<XX>/ still has a live .git; that can rarely corrupt if you run the same clone from two machines at once, but it's single-writer and re-cloning from GitHub fixes it in ~30 seconds with zero loss of pushed work.) Equality and safety turn out to be the same design choice.

    The one honest cost¶

    Because git lives inside each clone, you open your tools in your clone folder, not at the shared root. In Claude Code that means opening the session in clone_<XX>/ (and only adding the parent folder when you need a shared file like the data). It's one extra habit at setup time. That's the whole price — and in exchange the five failure modes above stop being your problem. We think that's a good trade; the handbook makes the habit concrete.

    Bringing this to your own team¶

    If you're not on a team that already uses this and want to adopt it, two practical notes:

    • You don't need Dropbox. The happy path is Claude Code + Dropbox (every safety rail on automatically), but the workflow also runs on pure GitHub — the clones just live in an ordinary folder instead of inside a Dropbox container, and you take on a bit more manual care (Dropbox no longer backs up your unpushed work). The mechanics of that variant are flagged in set up your working clone and the manual workflow.
    • Explaining it to co-authors. The argument that lands is the one above: not "use this tool," but "here are the five bad days every paper has, and here's the cheapest way to make them impossible." Lead with the failure modes they've personally lived. One person sets the project up once (anyone can — there's no lead) and invites the others as collaborators; the one constraint is that Overleaf's git integration can only be configured by the Overleaf project owner.
